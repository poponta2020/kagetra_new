# entry-group-page（申込グループページ）要件定義完了（2026-08-20）

大会の申込運用をグループ単位の新ページ `/admin/entries/[groupId]` へ集約し、日ページ（`/events/[id]`）は
会員が「その日に出るか」を答える画面に純化する。**entry-groups の「グループ専用画面なし」決定の撤回**でもある。

## 起点の発見（本番 read-only 実測 2026-08-20）
- entry_groups 33 / 複数日 9 / 最大3日。**ボード母集団 18グループ中 複数日は3つだけ＝83%がシングルトン**
- **グループ内で日ごとに進行状態が食い違う実例が複数**（多摩CDE: C=申込済 / D・E=申し込まない、
  全日本30周年: ABC=申込済 / A=申し込まない）→ 日程表が「日×状態」でないと表せない
- 杉並AB はユーザーの例そのままの実在グループ（杉並B 9/5 + 杉並A 9/6・締切 8/7）
- `deriveEntryGroupName` が **null を返す実例**あり（九段E + 九段CDE。残りが `E` と `CDE` で級文字1文字でない）

## 主要な設計判断（ユーザー選択）
- **閲覧は全ロール・操作 UI は管理者のみ**（ボードが PR #378 で会員全員に開放済み＝リンク先を管理者専用に
  すると死んだリンクになる）
- **進行管理は日ページから外してグループへ移設**。日×状態の表＋日を選んで一括適用。
  **現行の伝播確認ダイアログ（GroupToggleDialog）は役目を終えて撤去**
- **ボードの全行（シングルトン含む）が常にグループページへ着地**。代わりに日ページの戻り導線を
  シングルトンでも常時表示にして袋小路を塞ぐ
- 日ページから外すのは管理者向けのみ（LINE紐付け・申込書・参加費集計・関連メール）。
  **名簿・オープンチャットは両方に残す**
- **共通7項目（= 既存 PROPAGATABLE_FIELD_KEYS と同一集合）の編集をグループページへ移設**し、
  日ページの編集は日固有項目のみに
- 一括操作は**後退方向3種（未申込に戻す・申し込まない・未払に戻す）も対象**
- フロー帯の集約規則＝**「申し込まない日を除いた残りが全部揃ったら完了」**（本番4形で検算）。
  当日＝最初の開催日。`buildEntryFlow` は変更せず集約入力を作る純関数を足す

## 技術調査で解決した論点
- ★**ボードの `classify()` は既にイベント単位の純関数**（`EntryBoardItem` も1イベント1件）。
  日程表のフェーズ1語は同じ関数を日ごとに回すだけでよく、判定を二重に持たない
- `classify` は「申し込まない」と「未申込かつ希望者0名」を**どちらも `no_applicants`** に畳むので、
  日程表では `entryStatus` で 申込なし / 希望者なし に割り直す
- **バルク Server Action で足りないのは `setEntriesNotApplying` の1本だけ**（他は `false` 引数で後退も賄える）
- 共通項目の一括保存は `propagateFieldsToGroup` を再利用（昇順ロック・group_id 併記の fail-closed がそのまま効く）
- ボトムナビは変更不要（`matches: ['/admin/entries']` が前方一致・`/admin/entries/42` のテストが既にある）
- **マイグレーション無し**（既存の group 帰属データを本来の場所へ置き直すだけ）

## デザイン（/design-screen Path D・round 2 で locked）
`chosen_direction: C` = 日程表の状態を**進行フェーズ1語**（要申込/抽選待ち/要振込/完了/申込なし/締切前/中止）に
集約し、**語彙をボードの区画名と一致**させる。実測: 行高38px・大会名89px（案A=59px / 案B=147px・行高59px）。
不採用理由は design-spec §2。**長い大会名は3案とも救えず**、接頭辞を抜く案は当の実例で破綻する
（共通接頭辞が伸びて片方の残りが空文字）ため、**級の列を truncate しない**ことを忠実度チェックリストに固定。
