# guest-role 要件定義（2026-08-11）

正典: `docs/features/guest-role/requirements.md`（AC §4・**37件すべて auto-test**）/ `implementation-plan.md`（8タスク）

## 何を作るか

大会の参加登録だけができる第4ロール **`guest`**。対象は「サークル活動には参加しているが協会への登録会が他会である人」。**最終目的は match-tracker へ渡す「出場予定者」の母集団を会員以外へ広げること**で、連携 API は今回作らない。出場予定は既存の `event_attendances.attend=true` × `events.event_date` で既に表現できているため、**新テーブルを作らず母集団に人を足せるようにする**のが実体。

## ★中心にある発見（調査で判明）

- **`is_invited` ではゲストを判別できない**。ゲストも出欠回答のために `is_invited=true` が必要なので、`is_invited` で絞っている母集団（参加費集計）には `role='guest'` の除外を**追加で**書かねばならない
- **除外が要る5箇所（E1-E5）は母集団定義がバラバラ**: 申込書xlsx=`attend ∧ 退会でない`（roleも招待も見ない）／参加費=`attend ∧ is_invited ∧ 対象級`／申込ボード=`event_attendances` 単独カウント（users を join していない）／**督促LINEは申込ボードとコードを共有しておらず、`collectOverdueEntries` の相関サブクエリという独立実装**（要件初稿の「E3と連動」は誤りで訂正済み）
- **`api/**` は `(app)/layout.tsx` のガードで守れない**。`api/mail/attachments/[id]` と preview は「ログイン会員なら誰でも」叩ける実在ルートなので、許可リストは **middleware**（API もページも matcher に入っている）で持つ。ただし Edge の `token.role` は Node の jwt callback が DB 再同期するまで stale になりうるため **Node 側でも判定する二段構え**
- **`parseUserRole` は guest を受理し `ROLES_HIGH_TO_LOW` には入れない**（同ファイル内で逆を向く）。前者がないと実効ロールが `'guest'` として下流認可に届かず、後者を入れると `/api/auth/session` 経由で管理者がゲストビューへ入れてしまい、ゲスト設定画面には切替セクションが無いので**復帰不能になる**

## 決めた仕様（ユーザー確認済み）

- 入口=**ゲスト用招待リンク**（発行時に会員用/ゲスト用を選ぶ・種別はトークン側で固定）→ 本人 LINE ログイン → **表示名・級・所属会の3項目のみ**（PII は取らない）
- できること=`/events`・`/events/[id]`（出欠回答）・`/events-archive`・`/settings`（表示のみ）。**ナビはイベント＋設定の2タブ**・入口は `/events`・それ以外は `/403`（fail-closed 許可リスト）
- 回答条件=**対象級は縛る・会内締切は縛らない**（会の申込準備の締切はゲストに無関係。出場予定の鮮度優先）
- 表示=参加者欄にゲスト印つきで**人数にも含める**／ホームのタイムラインにも印つき／**「あなたの参加費」は出さない**
- **確定名簿との非対称**: 会員は名簿が正・ゲストは自己申告が正。確定名簿があるグループでもゲストだけは `attend=true` を合流させる（しないと名簿取込の瞬間にゲストが顔ぶれから消える）
- 通知は一切送らない／ロール変更UIを4択化（ゲストへの変更に昇格制限は課さない）／**`unlinkLine` は member 限定のまま据え置き**＝未紐付けゲスト行が発生せず `/self-identify` に手を入れずに済む
- 申込ボードの参加希望者数と督促はゲストを**含めない**（人数の問いが「顔ぶれ」と「会として何人申し込むか」で違うため、大会詳細とは意図的に母集団を分ける）
