# 年度確認（全日協の登録更新）

> **責務:** 年度替わりの全日協（全日本かるた協会）登録更新に向けて、前年度登録会員の「所属継続の有無」と「登録情報の変更有無」を本人の自己申告で集め、管理者が名簿の写しを見ながら紙の届出を書ける状態にする。あわせてサークル所属者の学年を 4/1 に自動反映する
> **関連画面:** `/renewal`（会員）・`/admin/members/renewal`（管理）・`/settings/club-line-group`（会 LINE グループ設定）・`/dashboard`（登録確認バナー）・`/admin/members/[id]/edit`（公認資格）
> **主要実装:**
> - `apps/web/src/lib/membership-renewal/`（純ロジック＋store＋バッチ本体）
> - `apps/web/src/app/(app)/renewal/`（S1）・`apps/web/src/app/(app)/admin/members/renewal/`（S2）
> - `apps/web/src/app/(app)/settings/club-line-group/` ＋ `apps/web/src/lib/club-line-group.ts`（S3）
> - `apps/web/src/lib/line-chat-tasks.ts` ＋ `apps/web/src/app/api/line-chat-worker/**`（送信タスクとワーカー契約 → [notifications.md](notifications.md) が正典）
> - `apps/web/scripts/renewal-daily.ts` ＋ `apps/web/systemd/kagetra-renewal-*.{service,timer}`
> - `apps/web/src/lib/member-profile-fields.ts`（名簿の列の形式検証。会員編集と共用）

## 機能仕様

### 全体像

毎年 3 月、全日協から「会員名簿（確認用・3/1 現在）」が届く。従来は管理者が個別に聞いて回り、退会届・変更届を紙で書いていた。この機能はその**確認と集計まで**を置き換える（提出物の作成・郵送・会費振込は引き続き人が行う）。

1. 管理者が年度確認を**開始**する（対象年度・回答締切・案内に添える一言）
2. 会員が `/renewal` で「今年度も登録する／登録しない」と「4 月からの学年」を答える
3. 会 LINE グループへ案内と未回答者リマインドが流れる
4. 管理者が名簿の写しボードで集計・差分を見ながら紙を書き、提出・確定後（5 月頃）に**登録完了**を押す

### 対象者（開始時に固定）

- **全日協セクション**: 開始時点で `zen_nichikyo = true` ∧ `deactivated_at IS NULL` ∧ `role ≠ guest`
- **学年セクション**: 開始時点で `is_circle_member = true` ∧ 同じ条件（全日協の有無と独立）
- 両方に該当する会員は両セクション。どちらにも該当しない会員は行を作らない
- **対象集合は開始時点で確定**し、開始後に `users` のフラグを変えても増減しない。★これは書き込み側だけの性質ではなく**読み出し側の規約**でもある —— ボードも `/renewal` も対象判定を `users` から再導出せず、必ず `membership_renewal_members` の行を見る
- 開始後に退会処理された対象者は集計の母数から外し、ボードでは「退会」印で残す。リマインドの列挙からも外す
- **会員区分（正会員／准会員）は保存しない**。定款第 6 条（対象年度の 3/31 時点で満 20 歳なら正会員）から `resolveMembershipKind` が毎回導出する。生年月日が無ければ「未判定」

### 開始の前提（満たさないと開始できない）

1. 進行中（`status='open'`）の年度確認が無い
2. 同一年度の年度確認が実施済みでない（`fiscal_year` の UNIQUE が DB 層でも保証。やり直しは不可）
3. 会 LINE グループ（S3）が設定済み
4. `PUBLIC_BASE_URL` が設定済み（案内に `/renewal` の絶対 URL を載せるため）
5. 回答締切が今日より後

開始は**スナップショットの保存と案内タスクの作成を 1 トランザクション**で行う（片方だけ残る状態を作らない）。`PUBLIC_BASE_URL` と文面の解決はトランザクションの**外**で先に済ませ、env 未設定は「スナップショットを入れてから巻き戻す」ではなく単なる入力エラーとして返す。トランザクション内では `club_line_groups` を `FOR UPDATE` でロックしてから前提を確認する（S3 の「プールへ戻す」とのレースで宛先の無いタスクを作らない）。

### スナップショットと差分

開始時に対象者ごとの**スナップショット**（名簿の列＋学部区分・学部等名・学年）を `membership_renewal_members.snapshot`（jsonb）へ保存する。キーは `ROSTER_FIELDS` で固定し、値が無い項目も `null` を明示的に持つ（キー欠落と NULL を区別しない）。読み出し時は zod で検証する（`lib/membership-renewal/snapshot.ts`。`packages/shared` は zod に依存しないので検証境界は web 側）。

**「変更あり」は本人の宣言ではなくスナップショットと現在値の差分から導く**（`diffRoster`）。管理者が年度中に会員編集で直した分も差分に出る。紙の変更届が「変更前／変更後」欄なので、差分そのものが提出物の材料になる。郵便番号だけは 7 桁へ正規化してから比較する（表示は保存値のまま）。

スナップショットは住所・電話・生年月日を含む **PII** なので `users` と同じ扱い（本人と admin/vice_admin 以外の RSC payload へ渡さない・ログに出さない）。LINE へ出す個人情報は**氏名だけ**。

### 回答（S1 `/renewal`）

- 認可は**ログイン会員本人のみ**。`renewalId` と `userId` はフォームから読まず**セッションから決める**ので、他人の id を送っても他人の行は書けない。store 側も `user_id` を WHERE に含めて二重に塞ぐ。ゲストは対象外（ゲスト許可リストに `/renewal` を入れない）
- 選択肢は 2 つ。**「登録する」を選ぶには必須項目**（姓・名・ふりがな・生年月日・性別・級・郵便番号・住所1・電話。段位は A 級のみ）が全て埋まっている必要があり、欠けていればどの項目かを返して保存しない。**「登録しない」は欠けていても回答できる**（退会届に載る内容の確認だけで足りる）
- 「登録する」の画面では名簿の列をその場で修正でき、`users` へ**直接保存**する。形式検証は会員編集と同じ規則（`lib/member-profile-fields.ts` が正典。**必須／任意の判断だけが呼び出し側の関心事**で、管理者編集は全項目任意のまま）。★`users.name`（合成表示名・UNIQUE）は**再合成しない**（既存の会員編集・招待登録と同じ規則）
- 回答は登録完了まで何度でも上書きでき、回答者（本人／管理者代理）と回答日時を記録する。**回答者は毎回上書きする** —— 管理者が代理回答した後に本人が答え直したら「管理者が代理回答」の印は消える
- 該当しないセクションは見出しごと出さない

### 学年（R4・4/1 反映）

- 既定値は現在の学年を選択肢の並びで 1 つ進めたもの。**最終学年**（学部 4 年／6 年制は 6 年、修士 2 年・博士 3 年・専門職 3 年）は既定値を置かず「進学／卒業／留年」の 3 択にする。★`defaultNextSchoolYear` は最終学年を見ないので、**呼び出し側は必ず `isFinalSchoolYear` を先に判定する**
- 回答は**絶対値**（`next_faculty_kind` / `next_faculty` / `next_school_year`）で保存し、反映時に種別から再計算しない。3 月の回答を 4/1 に反映するまでの間に基準値が動いても、本人が答えた値がそのまま入る
- **反映は対象年度の 4/1（JST）以降**。4/1 以降の回答は保存と同じトランザクションで即時反映し、それ以前の回答は `school_year_applied_at` を NULL のまま残して日次バッチが拾う。二重反映は `WHERE school_year_applied_at IS NULL` の CAS で防ぐ
- 「卒業（サークルを離れる）」は `is_circle_member = false` にし、学部等名・学年は残す
- 学年の反映は年度確認が登録完了していても続く（登録完了は 5 月、学年は 4/1 という別の期日）

### 管理ボード（S2 `/admin/members/renewal`）

- 認可は admin / vice_admin。ページ側と Server Action 側の両方が判定する
- **主集計は全日協の「N / M 確認済み」**（退会処理済みは母数から除外）。学年は副集計
- 4 タブ（未回答／継続・変更なし／継続・変更あり／登録しない）で絞り込み、**正会員／准会員の区分見出し**で分ける（紙の名簿がその順）
- 行を開くと名簿の列。「変更あり」タブでは差分だけを 前→後 で並べ、変更のない項目は畳む
- 行のメタ情報: LINE 紐付けの有無・リマインドに載った回数（送信タスクの対象リストから数える。専用の列を持たない）・回答日時と回答者
- **代理回答は 2 択だけ**。登録情報の修正は既存の会員編集で行い、差分は同じ導出で出る。LINE 未紐付けでログインできない対象者はこの経路で処理する
- **締切変更**は今日以降の日付へ。以後のリマインド日程を新しい締切で計算し直し、新しい対象日集合に無い**未送信のリマインド**だけを取り消す。★送信済み・未送信を問わず**案内は取り消さない**

### 登録完了（取り消せない）

1. 「登録しない」と回答した対象者（**未退会のみ**）の `zen_nichikyo` を `false` にする
2. 未送信の送信タスクを取り消す
3. 年度確認を `completed` にする（以後 S1 は閲覧のみ・ホームのバナーも消える）

未回答者が残っていても実行できる（確認ダイアログに未回答の人数と氏名を出す）。未回答者のフラグは変えない（＝継続扱い）。巻き戻しは会員編集で個別に行う。

### LINE 配信

会 LINE グループへの案内・リマインドは Messaging API の push（人数分課金）ではなく **OAM のチャット予約送信**を使う。送信タスクのキューとワーカー契約（`/api/line-chat-worker/**`）の仕様は [notifications.md](notifications.md) の `line-chat-worker` 節が正典。ここでは年度確認側の規則だけを書く。

- **案内**: 開始と同じトランザクションで 1 件作る。送信予定＝現在時刻 + 15 分を 10 分境界へ切り上げ
- **リマインド**: 対象日の 19:30 の日次バッチが、その時点の**全日協未回答者**を集計して同日 20:00 のタスクを作る。対象日＝開始日 +3 日ごと・締切前日・締切当日（重なる日は 1 件・締切超過なし）。未回答が 0 人なら作らない。同日に二重に作らない
- **20:00 の 5 分前を過ぎた起動では作らない**（Persistent timer の catch-up 起動で過去分を送りつけない）。その日の分は送られず、次の対象日に改めて集計する
- **メンション**: 未回答者ごとに Bot の「グループメンバープロフィール取得」API で LINE の表示名を引き、タスクに載せる。ワーカーが OAM の入力欄で `@` を打って候補から選ぶ。**本文は常に氏名をテキストで列挙した完成形**なので、表示名が引けない・候補が一致しない・グループ ID が未捕捉のいずれでもリマインド自体は成立する（フォールバックが契約レベルで担保される）
- 1 通あたりのメンション上限を超える人数は 20:00・20:10・… と 10 分ずらした複数タスクに分ける
- **学年だけが未回答の会員はリマインドに載せない**（会グループの在籍前提は登録会員全員であり、サークル員全員ではない）。学年はホームのバナーで促す
- 失敗・要確認・OAM セッション失効の先回り警告は**管理者個人 LINE**（`system_notify` チャネル）へ。グループへの push フォールバックはしない

### 会 LINE グループ設定（S3 `/settings/club-line-group`）

- プールの Bot（`line_channels` の `purpose='event_broadcast'` ∧ `status='available'`）から 1 体を `purpose='club_chat'` へ転換する。★**`purpose` だけでなく `status` も同じ UPDATE で `available` から外す** —— 大会側の予約は `status` しか見ないので、`purpose` だけ変えると同じ Bot を取られる（級別グループと同形の CAS）
- **OAM のルーム URL を 1 本貼る**だけで `U…`（アカウントパス）と `C…`（ルーム ID）を取り出す。グループ表示名は OAM の見出しと**完全一致**が必要なので、末尾の人数の括弧は保存時に機械的に除去する
- **ID を 2 系統持つ**: `oam_chat_room_id`（ワーカーが Playwright で開く先）と `line_group_id`（webhook が送ってくるグループ ID・メンションの表示名取得に使う）は**別の値**。後者は Bot 招待の `join` webhook でしか取れないので NULL 可
- 転換した Bot の webhook は大会・級別のハンドラに流れない。`join` でグループ ID を捕捉し、**`leave`（Bot 自身が外された）でだけ** NULL 化する。★`memberLeft`（会員が 1 人抜けた）では消さない —— 消すと期間中に誰か 1 人が退出しただけで表示名解決が死に、再捕捉は Bot の再招待でしか起きない。グループ内の発言は完全に無視し、reply も返さない
- 「プールへ戻す」は進行中の年度確認、または未終了（`PENDING`/`RESERVING`/`CANCEL_PENDING`）の送信タスクがあれば拒否する

### 公認資格（`users` の 2 列）

読手（なし／B 級公認／A 級公認・`reader_certification`。**「なし」は列の NULL**）と準公認審判員（`is_associate_referee`）。全日協への申請で決まる値なので**管理者だけが編集**し（会員編集 S5）、年度確認では読み取り専用で表示する。名簿の「公認資格」欄にそのまま出る。詳細は [auth-admin.md](auth-admin.md)。

## 画面

- **`/renewal`**（ログイン会員本人・ゲスト不可）: 回答状態バー → 全日協の登録（2 択カード → 名簿の列 → 会員区分・公認資格の読み取り専用行）→ 4 月からの学年 → sticky の回答ボタン。対象外は「対象ではありません」の 1 行
- **`/admin/members/renewal`**（admin / vice_admin）: 未開始＝開始フォーム＋前提チェック＋文面プレビュー／進行中＝集計・4 タブ・区分別の名簿の写し・代理回答・締切変更・登録完了／完了後＝同じボードの読み取り専用
- **`/settings/club-line-group`**（admin / vice_admin）: Bot 選択・招待手順・ルーム URL と表示名・グループ ID の捕捉状態・直近の送信タスク（読むだけ＋失敗の再試行）
- **`/dashboard`**: 進行中で自分に未回答のセクションがあるときだけ「登録確認」バナー（既存の未回答アラートと同じ行型）。締切後も登録完了までは出し続ける

## フロー

### 年度確認の開始〜登録完了

1. 3 月・管理者が S3 で会 LINE グループを設定済みにする（初回のみ）
2. S2 で対象年度・締切・一言を入れて開始 → 対象者のスナップショット＋案内タスクを 1 tx で作成
3. 15 分後に案内が会 LINE グループへ予約送信される
4. 会員が S1 で回答（名簿の修正は `users` へ即時保存・学年は 4/1 まで保留）
5. 対象日の 19:30 バッチが未回答者を集計 → 20:00 のリマインドを予約
6. 4/1 の 00:05 バッチが学年を `users` へ反映
7. 提出・確定後（5 月頃）に管理者が S2 で登録完了 → 「登録しない」のフラグを落とし、未送信タスクを取り消す

### 日次バッチ

| バッチ | 時刻 | 内容 |
|---|---|---|
| `renewal-daily.ts --reminders` | 19:30 JST | ①`reconcileTasks`（`RESERVING` 30 分超 → 要確認、送信時刻−5 分超過の `PENDING` → 失敗）②対象日ならリマインドタスクを作成 |
| `renewal-daily.ts --apply-school-year` | 00:05 JST | 対象年度の 4/1 以降の未反映の学年回答を `users` へ CAS で反映 |

どちらも `--dry-run` で候補の列挙だけができる。冪等（同日再実行で二重作成・二重反映をしない）。

## API（Server Actions）

すべて `'use server'` の named export で、Next.js の RPC として直接到達できるため各関数が自分で認可する。

- `apps/web/src/app/(app)/renewal/actions.ts`
  - `submitRenewalAnswer(prevState, formData)` — 本人の回答。ゲスト不可。`renewalId` 以外の対象は**セッションから決める**
- `apps/web/src/app/(app)/admin/members/renewal/actions.ts`
  - `startRenewalAction` / `proxyAnswerAction` / `changeDeadlineAction` / `completeRenewalAction` — すべて admin / vice_admin
- `apps/web/src/app/(app)/settings/club-line-group/actions.ts`
  - `saveClubLineGroupAction` / `revertClubLineGroupAction` / `retryClubLineGroupTaskAction` — すべて admin / vice_admin

route handler（`/api/line-chat-worker/**`）は [notifications.md](notifications.md) を参照。

## 既知のギャップ・未確認事項

- **ログイン後に S1 へ直接戻す導線が無い**（`?next=` 対応は認証周りの変更になるため Non-goal）。案内文に「ログイン後はホームの『登録確認』から開けます」を添えて代替している
- **メンションの取りこぼし**（表示名の重複・絵文字・候補不一致）は解消しない。一致しない人はテキスト列挙で足りるとする
- **氏名変更時の `users.name`（合成表示名）は追随しない**。S2 の差分行に注記を出すに留める（別 Issue）
- OAM のメンション操作は match-tracker 側の PoC ゲート付き。不成立ならメンションなし（全員テキスト列挙）で運用する
