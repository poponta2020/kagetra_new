# entry-overdue-alert 要件定義書

会内締切超過の未申込大会を管理者へ毎日アラートし、併せて「申込者なしのため申し込まない」という終端状態を進行管理に追加する。

**位置づけ:** `event-lifecycle-notify`（PR #85 / #118）に対する delta。同機能の §7 範囲外で明示的に見送っていた 2 項目を反転させる:

- `docs/features/event-lifecycle-notify/requirements.md:245`「締切超過後の継続催促（毎朝送信）」
- 同 `:247`「管理者専用グループへの出し分け（今回は参加者グループに集約）」

正典の機能仕様は `docs/spec/notifications.md`（通知）と `docs/spec/events-attendance.md`（イベント・進行管理）で、本ファイルは今回の変更分の要件を持つ。

---

## 1. 概要

### 目的
1. 会内締切を過ぎても会として主催者に申し込んでいない大会を、**管理者個人の LINE へ毎日 1 通のサマリ**で通知し、申込漏れを検知できるようにする。
2. 「申込者がいないため今回は申し込まない」という運営判断を進行管理に記録できるようにし、それをアラートの停止条件かつ大会申込一覧からの非表示条件とする。

### 背景・動機
- 既存の申込締切リマインド（`entry_deadline_advance` / `entry_deadline_day`）は **once-ever**（`event_lifecycle_notifications` の `UNIQUE(eventId, type)`）で、締切 3 日前と当日に 1 度ずつ鳴って終わる。**締切を過ぎた後は無音**になる。
- 既存リマインドの宛先は**大会ごとの LINE グループ**で、送信には `event_line_broadcasts.status='linked'`（Bot 紐付け済み）が必須。グループ未紐付けの大会には 1 通も飛ばない ＝ **申込漏れが一番起きやすい大会ほど無音**。
- 管理者個人宛の LINE 経路（`line_channels.status='system'` の system_notify Bot）は既にあるが、用途はメール取込・バックアップ失敗といった**異常検知専用**で、業務リマインダーは載っていない。
- 「申込者ゼロなので見送る」判断は、将来的には出欠回答から自動判定したいが、**システム移行過渡期で参加予定者が必ずしも出欠登録するとは限らない**ため、当面は管理者の手動判断とする。

---

## 2. ユーザーストーリー

**対象ユーザー:** 管理者・副管理者（実運用は管理者 1 名）

- 管理者として、朝 LINE を見れば「会内締切を過ぎたのに、まだ主催者へ申し込んでいない大会」が一覧で分かり、申込漏れのまま大会申込締切を迎える事故を防ぎたい。
- 管理者として、出欠回答が集まらず今回は見送ると決めた大会をワンタップで畳み、以後そのアラートが鳴らず、大会申込一覧にも出てこない状態にしたい（もう操作することがないため）。
- 管理者として、畳んだ後にやはり申し込むことになった場合、大会詳細ページから元に戻せるようにしたい。

**利用シナリオ:**
1. 会内締切（`internal_deadline`。通常は大会申込締切の 6 日前）を過ぎた翌朝から、その大会が毎朝のサマリに載る。
2. 管理者は LINE のリンクから大会詳細を開き、主催者へ申し込んだら「申込済にする」を押す → 翌朝からサマリに載らない。
3. 申込者が 0 名で見送ると決めた場合は「申し込まない」を押す → 翌朝からサマリに載らず、大会申込一覧からも消える。

## 3. 機能要件

### 3.1 画面と遷移（画面インベントリ＋ナビゲーション地図）

見た目の詳細は `design-spec.md` を参照。

| 画面 | 変更内容 |
|---|---|
| `/events`（大会申込一覧） | `entry_status='not_applying'` の大会を一覧から**除外**する。件数カウント・フィルタ・並び替えの母集団からも外れる |
| `/events/[id]`（大会詳細） | 進行管理パネル（管理者のみ）に「申し込まない」操作を追加。進行状態ピル（会員も見える読み取り専用）に 3 つ目の状態「申込なし」を追加。**「申し込まない」から戻す唯一の導線** |
| `/events-archive`（過去のイベント） | **変更なし**。開催日を過ぎれば `not_applying` の大会も従来どおり並ぶ |
| `/dashboard` | **変更なし**（events を参照していない） |
| 管理者個人の LINE | 画面ではないが本機能の主出力先。サマリ各行から `/events/[id]` へ遷移する |

**遷移:** `/events` → `/events/[id]`。

`not_applying` にした大会の到達経路は次のとおり。`/events` は未来日、`/events-archive` は過去日を出す排他的な 2 画面なので、**開催日が来るまでの期間はどちらの一覧にも現れず、詳細 URL の直叩きだけが到達手段になる**。開催日を過ぎれば `/events-archive` に従来どおり並ぶ。アラート対象からも外れるため LINE サマリのリンクにも載らない。

これは「申込者がいないので申し込まない＝もう操作することはない」という運用前提を受けた意図的な設計（2026-07-25 ユーザー合意）であり、誤操作の復旧は詳細 URL の直叩きで行う。

### 3.2 ビジネスルール

#### 3.2.1 毎日アラート（管理者個人 LINE）

**対象条件** — 以下をすべて満たす大会を対象とする（JST 基準）:

| # | 条件 | 根拠 |
|---|---|---|
| 1 | `events.status != 'cancelled'` | 中止大会に申込を催促しない（既存リマインドバッチと同じ扱い） |
| 2 | `events.event_date >= 今日` | 開催日を過ぎた大会は永久に鳴り続けさせない |
| 3 | `events.entry_status = 'not_applied'` | `applied`（申込済）と `not_applying`（申込なし）は対象外 |
| 4 | **基準締切** `COALESCE(internal_deadline, entry_deadline)` が非 NULL かつ `< 今日` | 会内締切が主。未入力なら大会申込締切で代替する。どちらも NULL なら対象外（判定不能） |

**送信ルール:**
- **1 日 1 回・1 通のサマリ**。対象 0 件のときは送信しない（毎朝の無害な通知でオオカミ少年化させない）。
- 宛先は `line_channels` の `status='system'` 行に設定された管理者 LINE userId（既存の system_notify 経路）。**大会 LINE グループの紐付け有無に一切依存しない**。
- **冪等性を持たせない**。毎日繰り返し鳴ることが機能そのものであるため、`event_lifecycle_notifications` の once-ever 機構（`UNIQUE(eventId, type)`）は使わない。同日中に再実行すれば同じ内容が再送される（運用上はタイマーが 1 日 1 回起動する）。
- 送信失敗はリトライしない（翌朝また対象になる）。失敗はログに残す。
- 配信時刻は **JST 07:00 前後の新規タイマー**。既存の `kagetra-lifecycle-reminders.timer`（JST 00:00）には相乗りしない（管理者の端末が毎日深夜に鳴るため）。

**並び順・件数:** 基準締切の**超過日数が大きい順**（＝古い順）。上位 5 件を明細で出し、超過分は「他 N 件」に畳む（既存の `buildNewDraftsMessage` と同じ形式）。

**文面に含める情報**（1 大会 1 行 + 補助行）:
- 大会名
- 会内締切の日付と超過日数（基準締切が `entry_deadline` 代替のときはその旨が分かる表記）
- 大会申込締切の日付と残日数（既に過ぎている場合は超過表記）
- 出欠回答で「参加」を選んだ会員数（`event_attendances.attend = true` の件数）
- 大会詳細への**絶対 URL**（`PUBLIC_BASE_URL` + `/events/{id}`。LINE 上でタップできる必要があるためパス表記にしない）

#### 3.2.2 「申し込まない」状態

**意味:** 「申込者がいないため、会として今回は主催者へ申し込まない」。会内締切を過ぎて出欠回答が締まった後にはじめて確定する判断であり、押した時点で当該大会に対する運営操作は終わる。

- `events.entry_status` に 3 値目を追加する（表示名「申込なし」）。
- 設定・解除ができるのは **admin / vice_admin のみ**（`/events/[id]` の進行管理パネル）。
- **設定時に LINE 通知は一切送らない**（参加者グループにも管理者にも）。確認ダイアログも不要（通知が飛ばないため）。
- 設定後、その大会は `/events` 一覧から消える。`/events-archive` は従来どおり。
- 会員が詳細 URL を直接開いた場合、進行状態ピルに「申込なし」が表示される。
- **出欠回答の可否は変更しない**。従来どおり会内締切・対象級・`isInvited` で判定する（会内締切を過ぎている時点で既に一般会員は回答不可になっている）。

**状態遷移:**

| 遷移 | 通知 | 備考 |
|---|---|---|
| `not_applied` → `not_applying` | なし | 見送り確定 |
| `not_applying` → `not_applied` | なし | 誤操作の復旧・方針転換。一覧に戻り、翌朝から再びアラート対象になりうる |
| `not_applied` → `applied` | **送る** | 既存挙動のまま（参加者向け・会計向けの 2 通、once-ever） |
| `applied` → `not_applying` | なし | 申込後の取り下げ。想定は低いが状態機械として塞がない |

**`not_applying` → `applied` の直接遷移は UI に用意しない。** 復帰は必ず `not_applying` → `not_applied` → `applied` の 2 ステップを踏ませる（状態機械を単純に保ち、既存 `setEntryApplied` の遷移ガード `WHERE entry_status = 'not_applied'` を**変更せずに済ませる**ため）。2 ステップ目の `not_applied → applied` は既存経路そのものなので、申込完了通知 2 通は従来どおり送られ、once-ever（`UNIQUE(eventId, type)`）も維持される（一度 `applied` になったことがある大会を復帰させた場合は再送されない — これも既存挙動と同じ）。

**既存リマインドへの影響:** `send-lifecycle-reminders.ts` の申込締切リマインドは `entry_status = 'not_applied'` を条件にしているため、`not_applying` の大会は**自動的に対象外**になる（条件式そのものは変更しない）。

#### 3.2.3 エラー・境界条件

- **失敗ポリシーの適用順序**（重要。順序で挙動が変わるため固定する）: ①対象抽出 → 0 件なら何もせず正常終了 → ②system_notify チャネル解決 → ③`PUBLIC_BASE_URL` 解決 → ④文面組立 → ⑤push。
  - ② system_notify チャネルが未設定（`status='system'` の行なし）／`notification_line_user_id` が未設定 → **送信をスキップし警告ログを出す。バッチは異常終了しない**（未設定の環境で毎朝 exit 1 を出さない）。
  - ③ `PUBLIC_BASE_URL` 未設定 → **エラーで停止する**（リンクなしの通知を送るより設定漏れを気づかせる方が安全）。②の後に置くことで、チャネル自体が未構成の環境ではここに到達しない。
- 基準締切が今日と等しい日（＝締切当日）は**対象外**。超過（`< 今日`）してから鳴り始める。
- LINE の 1 メッセージ長制限を超える場合でも、上位 5 件＋「他 N 件」形式のため通常は収まる。大会名が極端に長い場合に備え、行単位で切り詰める。
- 同一大会が複数級で複数 events 行に分かれている場合、**events 行ごとに 1 行**としてサマリに載る（会レベルの申込は events 単位のため。集約はしない）。

### 3.3 変わらないもの（回帰対象）

以下は今回一切変更しない。実装後も従来どおり動くことを回帰 AC で担保する。

- 既存 6 種のリマインド通知（申込締切／事前支払締切／現地払い × 事前・当日）の対象条件・文面・宛先（大会 LINE グループ）・once-ever 保証
- 申込完了通知（`entry_applied` / `entry_applied_treasurer`）・支払完了通知（`payment_paid`）
- 会内締切による一般会員の出欠回答ロック、対象級・`isInvited` の判定
- `/events-archive` の表示条件（開催日が今日より前の全イベント）
- system_notify チャネルの既存用途（新着メール取込・連続失敗・バックアップ失敗）
- 大会 LINE グループへのメール配信（`broadcastMailToEvent`）・要綱送信

## 5. Non-goals

**機能面:**
- 出欠回答者 0 名からの「申し込まない」自動判定（移行過渡期で参加予定者が必ずしも出欠登録しないため、当面は手動判断。将来の拡張点）
- 会員個人への催促通知（出欠未回答者へのリマインド等）
- 支払い側の締切超過アラート（今回は申込のみ。支払いは既存の once-ever リマインドのまま）
- 大会 LINE グループへの毎日催促（宛先は管理者個人のみ）
- 通知文面の編集 UI・テンプレカスタマイズ
- 「申し込まない」にした大会の一覧画面（管理画面）。復帰は詳細 URL の直叩きで足りる
- Web Push（PWA バッジ）への同アラートの配信
- 会内締切が未入力であること自体を知らせる別アラート

**技術面:**
- `event-lifecycle-notify.ts` と `line-broadcast.ts` の push 実装の統合リファクタ（event-lifecycle-notify §6.9 から据え置き中の課題。今回も触らない）
- 通知履歴の永続化（毎日鳴る通知にログ表を持たせない）

## 6. 技術的制約・契約

**壊してはいけない既存挙動:**
- `event_lifecycle_notifications` の `UNIQUE(eventId, type)` による once-ever 保証。**毎日アラートはこの表を使わない**（毎日鳴ることが要件のため構造的に載らない）
- `send-lifecycle-reminders.ts` の `eq(events.entryStatus, 'not_applied')` 条件式。3 値目の追加によって `not_applying` が自動的に除外される設計に依存しているため、この条件を「`applied` 以外」に緩めてはならない
- system_notify チャネルの既存 3 用途（新着メール・連続失敗・バックアップ失敗）

**保持すべきデータ・移行:**
- `events.entry_status` は `NOT NULL DEFAULT 'not_applied'`。既存行の値は変更しない（enum への値追加のみ）
- PostgreSQL の enum への値追加はロールバックできないため、値名は実装前に確定させる

**セキュリティ・権限:**
- 「申し込まない」の設定・解除は admin / vice_admin のみ（既存 `requireAdminSession()` パターンを踏襲）
- 進行状態ピルは会員にも見える読み取り専用表示（既存 `LifecycleStatusBadge` と同じ扱い）
- 管理者個人の LINE userId は `line_channels` に既に保持済み。新たな個人情報の保存は発生しない

**利用技術上の制約:**
- Drizzle enum への値追加は migration 必須（`pnpm db:generate` → `db:migrate`）。本番は `db:migrate`（`db:push` は interactive prompt で詰む）
- 新規 systemd タイマー・サービスは `apps/web/systemd/` の既存 2 組（broadcast-cleanup / lifecycle-reminders）と同じ構成で追加する
- `PUBLIC_BASE_URL`（既に `line-broadcast.ts` / `line-broadcast-guidelines.ts` が使用）を絶対 URL の origin に流用する
- 日付判定は JST の `YYYY-MM-DD` 文字列比較（既存 `jstTodayIso` / `addDaysIso`）

**未解決の技術論点（→ 技術計画フェーズで解決）:**
1. 管理者個人 LINE への push を apps/web 側からどう呼ぶか。`apps/mail-worker/src/notify/line.ts` の `pushSystemNotification` を共有化するか、web 側に同等の薄い実装を置くか（パッケージ境界・`@line/bot-sdk` の依存位置）
2. バッチの置き場所（`apps/web/scripts/` に新規 or 既存 `send-lifecycle-reminders.ts` に相乗り）。宛先・冪等性・配信時刻がすべて異なるため分離が有力

## 7. 設計判断の根拠

1. **宛先を管理者個人にした:** 既存リマインドは `linked` なグループが必須で、グループ未紐付けの大会には 1 通も飛ばない。申込漏れが一番起きやすいのはまさにその大会なので、グループ経路に載せると機能が成立しない。system_notify Bot は既に管理者個人へ到達する実績のある唯一の経路。
2. **once-ever 機構を使わない:** `event_lifecycle_notifications` の `UNIQUE(eventId, type)` は「生涯 1 回」を機械的に保証する仕組みで、毎日繰り返すという要件と真逆。新しい enum 値を足して再送を作り込むより、通知ログを持たない別経路にする方が単純で壊れにくい。
3. **1 日 1 通のサマリ:** 大会ごとに push すると、3 件溜まった日は毎朝 3 通届く。既存の「📬 新規大会案内 N 件」と同じサマリ形式なら管理者の受信体験が一貫し、上位 5 件＋「他 N 件」の実績ある畳み方も流用できる。
4. **基準締切を `COALESCE(internal_deadline, entry_deadline)` にした:** 会内締切は手入力（AI 抽出対象外）のため未入力が起こりうる。未入力なら黙るという仕様では、締切を入れ忘れた大会＝一番危ない大会が検知できない。
5. **開催日経過を停止条件に入れた:** これがないと、過去の未申込大会が永久にサマリに載り続けて通知が形骸化する。
6. **「申し込まない」を `entry_status` の 3 値目にした（別フラグにしない）:** 既存の申込締切リマインドが `entry_status='not_applied'` で絞っているため、3 値目にすれば見送った大会が既存リマインドからも自動的に外れる。別フラグにすると `not_applied` のまま残り、リマインドを止めるための条件追加が別途必要になる。
7. **「申し込まない」を一覧非表示の条件にした:** 「申込者がいないので申し込まない」は会内締切後にしか下せない終端判断で、押した後にその大会へ行う操作は存在しない。一覧に残すと期限切れの大会が積み上がる。
8. **復帰導線を詳細 URL の直叩きにした:** 復帰は例外ケースであり、専用の管理一覧を作るのは費用対効果が悪い。詳細ページは削除していないため退路は常に残る。
9. **設定・解除で通知を送らない:** 「申し込まない」は対外的なアクションを伴わない内部判断。参加者グループに「申し込みません」と流す運用要求は出ていない。
10. **配信時刻を朝にした:** 既存バッチ（JST 00:00）に相乗りすると管理者のスマホが毎日深夜に鳴る。タイマーを分けるコストは小さい。

## 8. UI 決定事項

規模が小さい delta（ボタン 1 つ・ピル 1 つ）のため `/design-screen` の収束ループは回さず、既存パターンの踏襲で以下を確定した（2026-07-25 ユーザー合意）。

- **操作の形:** 進行管理パネルの「申込状態」行に、既存の 2 値ボタンと並べて「申し込まない」ボタンを追加する。`not_applying` のときは同行のボタンを「未申込に戻す」1 つだけにする（そこから直接「申込済にする」へは進ませず、必ず `not_applied` を経由させる — 状態機械を単純に保つ）
- **`not_applying` のときのパネル:** 支払いタイプ・支払状態の操作はそのまま残す（畳むと復帰時に見えなくなる）。締切・参加費の参照行も従来どおり
- **進行状態ピル:** `not_applying` は tone `info`・文言「申込なし」。**`not_applying` のときは支払いピルを表示しない**（申し込まない大会に支払い状態は無意味で、`info`（現地払い）と同トーンのピルが 2 つ並ぶのも避ける）。既存は 未申込=`neutral` / 申込済=`success`
- **誤操作防止:** 「申し込まない」押下時のみ `window.confirm`（「この大会は大会申込一覧に表示されなくなります。よろしいですか？」）を出す。LINE 通知は飛ばないが一覧から消える不可視化を伴うため。解除側（「未申込に戻す」）は確認なし
