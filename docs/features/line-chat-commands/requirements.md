# line-chat-commands 要件定義書

## 1. 概要

- **目的**: 大会別 LINE グループで Bot をメンションして「申し込みました」「振り込みました」と送るだけで、景虎の申込ステータス・支払ステータスが進むようにする。
- **背景・動機**: いまは Bot が締切リマインドを一方通行で流すだけで、実際に申し込んだ・振り込んだあとは景虎を開いて進行管理から操作する必要がある。報告と操作が二度手間になっており、操作を忘れるとリマインドが鳴り続ける。報告そのものを操作にする。
- **実現可能性は実測済み**: LINE webhook の payload で「Bot 自身がメンションされたこと」「発言者が誰か」を判定できることを本番で確認済み（`.claude/memory/reference_line_webhook_mention_payload.md`）。

## 2. ユーザーストーリー

| 対象 | 目的 | シナリオ |
|---|---|---|
| 管理者 | 主催者へ申し込んだ直後、その場で申込済みにしたい | 大会グループで `@Bot 申し込みました` と送る。景虎を開かずに申込済みになり、参加者向け・会計向けの完了通知が同じグループに流れる |
| 会計担当（副管理者） | 振込を済ませた直後、その場で支払済みにしたい | 大会グループで `@Bot 振り込みました` と送る。支払済みになり、完了通知が流れる |
| 一般会員 | （対象外） | 真似して送っても何も起きない。グループは荒れない |

## 3. 機能要件

### 3.1 画面と遷移

**景虎側の画面変更は無い。** 入口は LINE グループの発言のみで、出口は既存の進行管理画面（`/admin/entries/[groupId]`）の表示が変わることと、既存のライフサイクル通知が流れること。

### 3.2 ビジネスルール

#### 3.2.1 発火条件（すべて満たしたときだけ実行する）

1. **大会別 LINE グループからの発言であること** — `line_channels.purpose = 'event_broadcast'` かつ、そのチャネルの `event_line_broadcasts` が `status='linked'` で `line_group_id` が発言元グループと一致する。級別グループ（`grade_broadcast`）では反応しない（対象大会を特定できないため）
2. **Bot 自身がメンションされていること** — `message.mention.mentionees[]` に「この Bot を指す要素」があること
3. **本文に対象アクションの語を含むこと**（3.2.2）
4. **否定表現を含まないこと**（3.2.4）
5. **発言者が権限を持つこと**（3.2.3）

#### 3.2.2 アクションと語

| アクション | 語（部分一致・いずれか1つで成立） | 効果 |
|---|---|---|
| 申込済みにする | 申込 / 申し込み / 申込完了 / 申込済 / 申し込みました / 申し込んだ | グループ内の全開催日を `entry_status: not_applied → applied` |
| 支払済みにする | 振込 / 振り込み / 振込完了 / 振り込みました / 入金しました / 支払いました / 払いました | グループ内の全開催日を `payment_status: unpaid → paid` |

- **対象は申込グループ内の全開催日**（`status='cancelled'` を除く）。LINE 起点では日を選ばせない
- **1つの発言に両方の語が入っていたら両方実行する**（例「申し込んで振り込みました」）

#### 3.2.3 権限

| 実行者 | 申込済みにする | 支払済みにする |
|---|---|---|
| 管理者（admin） | ○ | ○ |
| 副管理者（vice_admin） | × | ○ |
| 一般会員・ゲスト・LINE 未紐付け・退会者 | × | × |

- 判定は `source.userId → users.line_user_id → users.role` を毎回 DB から引く。**引けなければ実行しない（fail-closed）**
- `users.is_treasurer` は認可に使わない（既存方針どおり。会計担当は `role='vice_admin'` で運用）
- **権限が無い人の発言は黙って無視する**（返信もしない）

#### 3.2.4 否定表現

本文に否定表現（「ません」「ない」「まだ」「未」等）を含む場合は**実行せず**、判定できなかった旨を返信する。「まだ申し込んでません」で申込済みになる事故を防ぐ。

#### 3.2.5 Bot の返信

**成功したときは返信しない。** 既存のライフサイクル通知（申込＝参加者向け・会計向けの2通／支払＝1通）が同じグループに流れ、それが事実上の完了報告になるため。返信するのは次の場合だけ:

| 状況 | 返信 |
|---|---|
| すでに完了している（全開催日が applied / paid） | すでに完了している旨 |
| 否定表現を含み判定できない | 判定できなかった旨（操作は行っていないこと） |
| 現地払いが混ざっていて一部だけ進めた | 進めた日と対象外の日 |
| 進められる日が1日も無い（事前払いの日がゼロ 等） | 対象が無い旨 |
| 実行に失敗した | 失敗した旨 |
| 権限が無い / メンションが無い / 語を含まない | **返信しない（完全に無視）** |

#### 3.2.6 支払の対象

既存ロジックと同じく `payment_type='advance'` の日だけを支払済みにする。現地払い・未設定の日が混ざっていた場合は、事前払いの日だけ進めて、対象外の日を返信で知らせる。

#### 3.2.7 その他の境界条件

- 既存の6桁招待コードの処理は従来どおり（先に判定し、コードならこの機能は動かない）
- メンションが無い発言・語を含まない発言は従来どおり完全に無視する
- 同じ発言が LINE のリトライで二重に届いても、状態遷移のガード（`WHERE entry_status='not_applied'` 等）により二重実行にならない
- `cancelled` の大会に対する通知抑止など、既存の `setEntriesApplied` / `applyPaymentsPaid` の挙動はそのまま踏襲する

## 5. Non-goals

- **遠征届の作成**（LINE から呼び出してまでやることではない、というユーザー判断）
- **「今回は申し込まない」（`not_applying`）への遷移** — 終端判断であり、チャットから打てるようにしない
- **会員個人の出欠回答**（会員が「出ます」と送って `event_attendances` を更新する）— 別機能として切り離す
- **級別グループでの利用** — 対象大会を特定できないため構造的に載らない
- **取り消し・巻き戻し** — 「やっぱり違いました」で戻す経路は作らない（画面から戻す）
- **誰が LINE から実行したかの監査記録** — 既存の画面操作も実行者を記録していないため、ここだけ記録しない（構造化ログには残る）
- **AI による意図判定** — キーワード方式に倒す（コスト・遅延・非決定性を持ち込まない）
- **日を選んでの部分実行** — LINE 起点は常にグループ内の全開催日

## 6. 技術的制約・契約

- **認可は webhook 側で新規に組む。** `requireAdminSession()` はセッション前提で webhook からは使えない。グループ在籍は権限ではない（グループには一般会員も非会員もいる）ため、`line_user_id` からの解決に失敗したら必ず実行しない
- **Bot 自身へのメンション判定**は `isSelf` に加えて mentionee の `userId` と `line_channels.webhook_destination_id` の一致でも判定できる（両方が本番で成立することを実測済み）。どちらを正とするかは技術計画で決める
- **状態遷移は既存の共通ロジックを再利用する。** `setEntriesApplied` / `applyPaymentsPaid` が持つガード（旧状態の WHERE 併記・`entry_group_id` の fail-closed 再検証・`cancelled` の通知抑止・once-ever スロットの claim）を webhook 経路でも同じように通す。同等ロジックを二重に書かない
- **once-ever 通知スロット**（`event_lifecycle_notifications` の UNIQUE(event_id, type)）の意味は変えない。LINE 起点でも初回遷移でのみ通知が飛び、戻して再度進めても通知は飛ばない（既存仕様のまま）
- **既存の webhook 処理順序を壊さない。** 6桁招待コードの判定が先、この機能は後
- 変更対象は LINE webhook のハンドラ層。景虎の画面・スキーマ・マイグレーションは不要（新規テーブル・新規カラムなし）
- **未解決の技術論点**（技術計画で解決する）
  - 語のマッチングと否定判定をどの層に置くか（純関数として切り出してテストするのが既存の流儀）
  - 返信メッセージの組み立てを既存の `line-mention.ts` / `buildTextMessage` に載せるか
  - webhook のタイムアウト内に状態遷移＋通知 push が収まるか（既存の招待コード処理は reply + 要綱 push まで行っているので前例はある）

## 7. 設計判断の根拠

- **メンション必須にした理由**: 申込済みへの遷移は LINE 通知2通を伴う対外アクションで、once-ever スロットを消費する。戻しても通知は取り消されず、再度進めても二度と通知が飛ばない＝**誤爆が実質的に取り消せない**。キーワードだけで発火させるには危険すぎるため、明示的なメンションを意思表示とみなす
- **成功時に返信しない理由**: 既存のライフサイクル通知が同じグループに流れるため、返信を足すと1操作で3通になる。通知そのものを完了報告として使う
- **否定表現を弾く理由**: 「申込」「振込」のような短い語を許容した結果、「まだ申し込んでません」が申込済みを引き起こす経路ができてしまう。取り消せない操作なので安全側に倒す
- **申込を管理者限定にした理由**: 画面より厳しくなるが、取り消せない操作をチャットから打てる人を絞るというユーザーの明示的な判断。副管理者は会計関連（支払）に限る
- **全開催日を対象にする理由**: 画面は選択ダイアログで日を選べるが、チャット1発言にその情報は乗らない。「グループ全部」と決め打つことで曖昧さを消す
