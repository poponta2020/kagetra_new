# 会員向け 受信メール検索・閲覧 デザイン仕様（design-spec）

> `/design-screen` が出力する確定仕様。**レイアウトの詳細は `design-mock/` の HTML が正。** このファイルは HTML から読み取れない「意図・判断・データ要件・宿題」と、実装の完了ゲートである忠実度チェックリストを記述する。
> ロジック（検索対象・履歴の導出条件・権限）は `requirements.md` が正典。ここでは再記述しない。

## 1. 対象と狙い
- **対象画面:** `/mail`（一覧＋検索）・`/mail/[id]`（詳細）・`/mail/attachments/[id]`（添付ビューア）
- **狙い:** 会の共用メールに届く大会連絡を、一般会員が自力で探して読めるようにする。あわせて「会としてどう処理したか」を日付つきで示す。
- **主ユーザー / 主な使い方:** 一般会員。大会名で検索して要項・名簿・抽選結果に辿り着く／LINE で流れてきたものを後から見返す。

## 2. 採用した方向性
- **方向性: 案A（履歴＝タイムライン）＋ ユーザーによるラウンド2の修正2点。**
  - 縦レール＋ドット。日付を見出し行に置き、その下に自然文で「○○大会 の連絡としてLINEグループへ配信（本文と添付2件）」。依頼時の言い回しにそのまま対応する。
  - **ラウンド2でユーザーが確定させた変更（claude.ai/design 上で直接編集）:**
    1. **詳細のセクション順を「ヘッダ → 添付ファイル → 本文 → 処理の記録」に変更**（元案は 処理の記録 が本文の前）。会員が最初に欲しいのは添付そのもので、処理の記録は確認事項なので最後に置く。
    2. **一覧カードから差出人行を削除。** 差出人は詳細ヘッダにのみ残す。
- **不採用案と理由: 案B（履歴＝行リスト）。** 日付列＋色分けラベルで走査性は高いが、処理ラベルを4色のピルに割り当てるとカード内の色数が増え、既存画面（和紙×藍の低彩度・ピルは状態表示に限定）から浮く。履歴は1通あたり多くても3行で、走査性より読みやすさが勝つと判断した。
- **視覚の正:** `design-mock/`（プロジェクト: Kagetra Design System）
  - `list-normal.html` — 一覧（既定・検索ヒット）
  - `detail-a-timeline.html` — 詳細（履歴3行・日付なし）★確定形
  - `history-variants.html` — 処理の記録 H0〜H6 の全分岐
  - `edge.html` — 検索0件・長大・本文も添付も無い未処理
  - `viewer.html` — 添付ビューア（PDF／不可／画像）

## 3. 視覚の正に現れない設計判断
- **詳細のセクション順（添付 → 本文 → 処理の記録）はユーザーの明示的判断。** 順番を入れ替えないこと。会員の主目的が「添付を開く」ことなので、長文本文に押し出されない位置に置く。
- **一覧カード末尾の「↳」行＝履歴の最新1行。** 詳細を開かずに「会として対応済みか」が分かることが本機能の価値の半分。差出人を落としてこの行を入れたのは、一覧では差出人より「会の対応」の方が情報価値が高いという判断。
- **検索ヒットの抜粋は件名以外で当たったときだけ出す。** 件名ヒットは件名自体のハイライトで足りる。抜粋の先頭に出所（`本文 ／` `添付 ○○.pdf ／`）を置き、どこで当たったかを明示する。
- **日付のない履歴行（H5）はドットを砂色（`--kg-border-strong`）に落とす。** 他の行と同じ見た目だと日付の欠落が実装の事故に見えるため、意図的な欠落だと分かる差を付ける。日付見出し行自体を出さない。
- **未処理（H6）は「処理の記録」セクションごと描画しない。** 空の枠を出すより、ピルだけの方が「まだ何もしていない」を正確に伝える。
- **H0（試合結果として取り込み）だけ大会名を出さない。** `result_drafts` は events に素直に解決できないため（`requirements.md` §3.4）。
- **本文は既定で畳む**（`.dbody.clamped` ＋「全文を表示」）。長文が多く、畳まないと処理の記録が画面外に押し出される。
- **検索0件の空状態は、絞り込みが効いているときだけ「外す」提案を書く。** 0件の原因が「添付ありのみ」であることが多い。

## 6. 必要データ
`requirements.md` §3.3（検索対象フィールド）・§3.4（履歴導出）が正典。

**仮データのまま確定した項目 ★実装で必ず実配線する:**
- **差出人はすべて架空**（`@example.jp`）。実データの差出人は他会関係者の個人情報なのでモックに入れていない。実装では `from_name` / `from_address` を出す。
- 添付のサイズ表記（`PDF · 1.2 MB`）は `mail_attachments.size_bytes` から算出。種別ラベル（PDF/Word/Excel/画像/ZIP）は `content_type` から導出。
- 一覧の総件数（`292 件`）・ヒット件数はクエリ結果。
- 検索ヒット抜粋（`.msnip`）の本文は、ヒット位置の前後を切り出して生成する。モックの文面はダミー。
- 履歴行の大会名は `deriveEntryGroupName` の結果（例「第46回九段大会AB」）。モックの文字列はその出力を模したもの。

## 7. インタラクション / レスポンシブ
- 検索バーはスクローラー内で `sticky top:0`。
- 一覧は初回20件＋「もっと読み込む」。
- 添付チップ／添付行のタップでビューアへ。ビューアの ✕ は `?from=` の元画面へ `replace` 遷移。
- 375px 基準。長いファイル名チップは `min-width:0` ＋省略記号（無いと横スクロールが出る）。

## 8. 忠実度チェックリスト ★実装の完了ゲート
- [ ] 詳細のセクション順が上から: ヘッダ（受信日時・ピル・件名・差出人）→ 添付ファイル → 本文 → 処理の記録。**この順序はユーザーの明示的判断なので入れ替えない**
- [ ] 一覧カードに差出人を出していない（差出人は詳細ヘッダのみ）
- [ ] 一覧カード末尾に履歴の最新1行（`↳ M/D …`）が出る。履歴が無いメール（未処理）では出ない
- [ ] 履歴は縦レール＋ドット形式。日付は行の見出しとして独立し、その下に自然文。大会名は `/events/[id]` へのリンク（`--kg-brand-fg` ＋下線）
- [ ] 日付のない履歴行はドットが `--kg-border-strong`（砂色）で、日付見出しを出さず「処理日時の記録がありません」を `--kg-fg-muted` で添える
- [ ] 未処理のメールでは「処理の記録」の見出しごと描画されない（空カードを出さない）
- [ ] H0（試合結果として取り込み）の行に大会名・リンクが出ていない
- [ ] 検索ヒット抜粋は件名以外でヒットしたときだけ出て、先頭に出所（`本文 ／` / `添付 <ファイル名> ／`）が付く
- [ ] ピルのトーンが 種別＝`brand` / 処理済み＝`success` / 未処理＝`warn` / 添付チップ＝`info`。独自色を足していない
- [ ] 375px で件名は一覧2行クランプ・詳細は全文折り返し。添付ファイル名は省略記号で、横スクロールが発生しない
- [ ] 検索0件で「添付ありのみ」が有効なときだけ、それを外す提案が空状態に出る
- [ ] ボトムナビが一般会員6タブ（ホーム/イベント/統計/申込管理/メール/設定）で、メールタブが active

## 9. ガードレール準拠メモ
- **このアプリはダークモードを持たない**（実コードに `prefers-color-scheme` / `dark:` の使用箇所ゼロ）。和紙ライト一系統のみで設計した。
- 色・フォント・radius・shadow は `colors_and_type.css` の `--kg-*` のみ使用。**トークン逸脱は往復を通して発生せず、実コードへのトークン追加は不要。** 例外は2つだけ:
  - `--mms-paper-*`（添付のページ画像を模した紙面ダミー）— 実装ではサーバー生成 JPEG の `<img>` に置き換わり、この CSS 自体が存在しない。
  - ボトムナビの `11px` — 実コード `bottom-nav.tsx` の `text-[11px]` に合わせた同値。
- 絵文字は添付の種別アイコンにのみ使用（既存 `pickAttachmentIcon` の踏襲。データ装飾には使っていない）。

## 10. 残課題・実装への申し送り
- ローカルでのピクセル実測は未実施（in-app プレビューが `file://` を静的スナップショット化するため計測できない）。375px の確認は claude.ai/design のカード上で行った。
- 一覧カードの `.msum`（履歴の最新1行）は、履歴導出を**一覧のN件ぶん**回すことになる。N+1 を避けるため、導出に必要な行（`tournament_drafts` / `event_broadcast_messages` / `result_drafts` / `linked_event_id` と対応イベント）は一覧クエリで一括 JOIN する前提。
- `detail-b-lines.html`（不採用の案B）はラウンド1の記録として残っている。実装は参照しないこと。
