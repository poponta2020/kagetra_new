# ホーム「会の出場予定」要件定義書

改修モード（delta）。ホーム（`/dashboard`）は当初 `/design-screen` の
[`design-spec.md`](design-spec.md) を要件成果物として出荷したため requirements.md を
持っていなかった。本書は**現行挙動の薄いベースライン**（§3.1）に、今回の変更
（大会ステータスピルの4値化）を載せたもの。画面レイアウトの正は引き続き design-spec と
[`design-prototype.patch`](design-prototype.patch) で、本書はレイアウトを再記述しない。

## 1. 概要

- **目的:** タイムライン行・今日カードの大会名の横に出ているピルを、「確定／希望」
  （名前チップの確度）から、**大会の進行状況を表す4値**（参加受付中／締切済／申込済／
  名簿確定）に置き換える
- **背景・動機:** 「希望」「確定」の2文字では会員に意味が伝わらない（ユーザー指摘・
  2026-09-21）。会員が知りたいのは「まだ出ると言えるのか」「会が申し込んだのか」
  「出場者が決まったのか」という進行状況であり、名前リストの出所ではない

## 2. ユーザーストーリー

- **対象ユーザー:** 会員全員（ホームを開く人。ゲストはホームに入れない＝guest-role AC-9）
- **目的:** ホームで大会ごとの顔ぶれを眺めるとき、その大会が今どの段階にいるかを
  一目で知る
- **利用シナリオ:**
  - 「参加受付中」を見て、まだ出欠を出せる（出ると言える）大会だと分かる
  - 「締切済」を見て、会内の受付は終わり、会がこれから主催者へ申し込む段階だと分かる
  - 「申込済」を見て、会が主催者へ申し込んだ（あとは抽選・名簿待ち）と分かる
  - 「名簿確定」を見て、主催者の確定名簿が出た（出場者が決まった）と分かる

## 3. 機能要件

### 3.1 画面と遷移（現行ベースライン・今回不変）

- **対象画面:** `/dashboard`（ボトムナビ「ホーム」）のみ。構成は上から
  未回答アラート → 今日の大会カード → 「出場予定」タイムライン（初期4件＋もっと見る）
- **遷移:** アラート行・今日カード・タイムライン行 → `/events/{id}`。
  見出しの「大会申込へ」→ `/events`
- **母集団:** `/admin/entries` と同じ（`event_date >= 今日(JST)` ∧ `status <> 'cancelled'`
  ∧ `kind = 'individual'`）。出場者0名の大会は載せない
- **名前チップの出所（今回不変）:**
  - その大会の申込グループに**パース済みの確定名簿**（`roster_type='confirmed'` ∧
    `superseded_at IS NULL`）があれば、名簿の「出場する人」（`status IN ('confirmed','carried_up')`
    ∧ `selection_outcome NOT IN ('waitlisted','rejected')`）。級は名簿の級を優先
  - 無ければ出欠「出る」（`event_attendances.attend = true`）の会員（対象級内・招待済み）
  - ゲストは名簿の有無にかかわらず出欠「出る」から合流する
- ピルは各タイムライン行（`size="sm"`）と今日カード（`size` 既定）の大会名の横に1つずつ出る

### 3.2 ビジネスルール（今回の変更）

#### 3.2.1 大会ステータス（4値）

大会（`events` の1行＝開催日単位）ごとに、次の**上から順に最初に当てはまったもの**を
ステータスとする。

| 優先 | ステータス | 条件 |
|---|---|---|
| 1 | **名簿確定** | その大会の申込グループが「確定名簿あり」（下記 3.2.2）。`entry_status` は問わない |
| 2 | **申込済** | `events.entry_status = 'applied'`（進行管理で「申込済にする」が押された状態）。会内締切前でも申込済 |
| 3 | **締切済** | 基準締切（3.2.3）があり、基準締切 < 今日（JST） |
| 4 | **参加受付中** | 上記のいずれにも当たらない（基準締切 ≥ 今日、または基準締切なし） |

- **締切当日は「参加受付中」**。翌日から「締切済」。申込管理ボードの区画分類
  （`classify` の `base >= todayStr` = 締切前）と同じ境界
- **`entry_status = 'not_applying'`（申し込まない）は新しいステータスを作らない。**
  `not_applied` と同じく日付どおり（参加受付中／締切済）に判定する。ホームに載せる
  大会の範囲も変えない
- ステータスは現在の状態から都度導出する。「申込済」を未申込へ戻す操作
  （誤操作の戻し）をすれば、表示も日付どおりのステータスへ戻る

#### 3.2.2 「確定名簿あり」の判定

申込管理ボード・申込フロー帯と**同じ正典**（`lib/events/confirmed-roster.ts` の
`isConfirmedRosterSettled`）を使う。次の4材料のどれか1つでも立てば「確定名簿あり」：

1. パース済み確定名簿（`roster_type='confirmed'` ∧ `superseded_at IS NULL`）
2. 採用済み原本ファイル（`tournament_entry_roster_files` の `roster_type='confirmed'`）
3. 確定名簿メール（`mail_kind='confirmed_roster'` ∧ `triage_status='processed'`）
4. 手動フラグ（`entry_groups.confirmed_roster_override`）

- **名前チップの出所は 3.1 のまま変えない。** そのため 2〜4 だけで「名簿確定」に
  なったグループでは、ピルは「名簿確定」、チップは出欠「出る」の会員のままになる
  （名前入りの名簿が無いので、落選・補欠の人を除けない）。これは承知の上での仕様
  （ユーザー判断 2026-09-21：「その大会が名簿確定フェーズに移ったら名簿確定」）

#### 3.2.3 基準締切

基準締切 = `COALESCE(internal_deadline, entry_deadline)`（会内締切、未入力なら大会の
申込締切で代替）。申込管理ボードの `baseDeadlineOf`・未回答アラートと同じ規約。
両方未入力なら基準締切なし＝「参加受付中」。

#### 3.2.4 ピルの見た目

既存の `Pill` トーンだけを使う（新しい色・トークンを作らない）。

| ステータス | トーン |
|---|---|
| 名簿確定 | `brand`（旧「確定」と同じ） |
| 申込済 | `info` |
| 参加受付中 | `warn` |
| 締切済 | `neutral` |

- 朱（`accent` / `danger`）は使わない。朱は引き続き未回答アラートだけ（design-spec §3）
- ピルの文字数が2字→最大5字（参加受付中）に増えるぶん、タイムライン行の大会名が
  早めに省略記号（`truncate`）になる。レイアウト構造は変えない

## 5. Non-goals

- 名前チップの出所の変更（手動フラグ・メールだけの名簿確定で、チップを名簿から出す
  ことはしない — 名前が取れないため）
- 外部API の `confidence`（`confirmed`/`hoped`）の変更
- 申込管理ボード・グループページ・イベント詳細・`/events` 一覧の表示変更
- 4値以外のステータス（申込なし・中止・支払済・完了 等）の追加
- `not_applying` の大会をホームから外す変更（母集団は不変）
- ホームのレイアウト変更（ピルの位置・サイズ・行構造）
- DB スキーマ変更・migration

## 6. 技術的制約・契約

- **互換性:** 外部API（match-tracker 連携）の公開契約を変えない。`upcoming-entrants` の
  出場者判定ロジックを変えない（ホーム・外部APIが共有）
- **判定の正典:** 「確定名簿あり」は `lib/events/confirmed-roster.ts` の
  `loadConfirmedRosterStates` / `isConfirmedRosterSettled` を使い、ホーム側で独自の
  条件を組まない（confirmed-roster-signal §6「判定の正典は1つ」）。基準締切は
  `baseDeadlineOf` と同じ規約
- **時刻:** クライアントで `Date.now()` を呼ばない。今日はサーバーの `todayInJst()` を
  使う（既存方針・hydration mismatch 回避）
- **保持データ・移行:** なし（既存列 `entry_status` / `internal_deadline` /
  `entry_deadline` と確定名簿4材料から導出するだけ）
- **セキュリティ・権限:** 変更なし（ホームの閲覧権限はそのまま）
- **仕様書の同時更新（同じ PR で行う）:**
  - `docs/features/confirmed-roster-signal/requirements.md` §3.2.5 の「メール連動／
    手動フラグだけのグループは、ホームでは『希望』表示になる」を、「ホームのピルは
    『名簿確定』になるが、名前チップは出欠ベースのまま」に書き換える
    （同書 AC-14＝出場者判定不変 は維持されるので AC は変えない）
  - `lib/events/confirmed-roster.ts` 冒頭コメントの同趣旨の記述も同様に更新
  - `design-spec.md` §4・§8 の「確定=brand／希望=neutral」を 3.2.4 の4値へ更新
- **未解決の技術論点（技術計画へ申し送り）:**
  - `getUpcomingEntrants` は `entryStatus` を返していない。追加するか、ホーム側で
    別に引くか（外部API のルートは項目を明示的に詰め替えているので、内部 DTO への
    追加は公開契約に波及しない見込み — 要確認）
  - ホームの DTO の `confidence`（`'confirmed' | 'hoped'`）を4値のステータスに置き換える

    `page.tsx`）

## 7. 設計判断の根拠

- **名簿確定はボードと同じ4材料**: ユーザー判断（「その大会が名簿確定フェーズに移ったら」）。
  ホームとボード・申込フロー帯で「名簿確定」の意味が食い違わないことを優先した。
  代償として、名前入りの名簿が無いグループではチップに落選者が混ざりうる（3.2.2）
- **優先順は 名簿確定 > 申込済 > 締切済 > 参加受付中**: 進行の後段ほど強い。
  会内締切前に申し込んだ大会は「申込済」、申込を押し忘れていても確定名簿が来れば
  「名簿確定」（申込フロー帯が確定名簿で抽選ステップを完了にするのと同じ考え方）
- **会内締切 null は申込締切で代替**: ユーザー判断。ボードの基準締切と揃える
- **not_applying は日付どおり**: ユーザー判断。発生はまれで、新ステータスや母集団の
  変更を持ち込まない
- **トーンは既存から決め打ち**: ユーザー判断（design-screen を回さない）。
  名簿確定は旧「確定」と同じ brand を引き継ぎ、締切済は `/events` 一覧の「締切済」
  （muted）と同じく無彩色、参加受付中はまだ手を動かせる段階として warn（山吹）。
  朱は未回答アラート専用の規約を守る
