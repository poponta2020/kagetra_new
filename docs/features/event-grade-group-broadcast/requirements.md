# event-grade-group-broadcast 要件定義書

## 1. 概要

新しい大会が登録されたとき、その概要を**級別の LINE グループ**へ自動配信する。

### 背景・動機

会員は普段 LINE で情報を受け取っており、アプリを能動的に見に来ない。現状、大会案内は「大会ごとに作られる一時 LINE グループ」へメール全文が配信されるが（`event-line-broadcast`）、そのグループには**その大会に申し込む人しか入らない**。つまり「そもそもこんな大会がある」と知る導線が存在せず、案内を見落とした会員は申込機会そのものを失う。

級別グループへ短い概要を流すことで、会員全体への周知を成立させる。

## 2. ユーザーストーリー

- **対象ユーザー**: 会の全会員（級別 LINE グループの参加者。A〜E 各10名程度）。および管理者（配信を設定・運用する側）
- **ユーザーの目的**: 会員が「自分の級で出られる大会が新しく増えた」ことを、アプリを開かずに LINE で知る
- **利用シナリオ**:
  1. 管理者が大会案内メールの AI 下書きを承認する（または手動で大会を登録する）
  2. その大会の対象級に一致する級別グループへ、概要と要綱 URL が即座に届く
  3. 会員は要綱 URL をその場で開いて内容を確認する（**ログイン不要**）

## 3. 機能要件

### 3.1 画面と遷移

`design_required: false`。すべて既存画面のパターンを踏襲するため design-spec は作成しない。

| 画面 | 新規/変更 | 内容 |
|---|---|---|
| `/admin/line-grade-groups` | **新規** | 級別グループ紐付け管理。A〜E の5行リスト。各行に紐付け状態（未紐付け / 招待コード発行済み / 参加済みコード待ち / 紐付け済み）と操作（招待コード発行・解除）。見た目は既存 `/admin/line-channels` を踏襲 |
| `/events/[id]` | 変更 | 級グループ配信の状況表示（級ごとに送信済み/未送信）と「級グループへ再送」ボタンを追加 |
| `/admin/mail-inbox` の承認フォーム | 変更 | 「LINE告知に載せる要綱」の添付選択を1項目追加（デフォルト未選択） |

遷移:

```
/admin ─→ /admin/line-grade-groups ─→（招待コード発行）─→ LINE グループへ Bot 招待
                                                              │
                                          join webhook ───────┘
                                                              ↓
                                          グループ内で6桁コード発言 → 紐付け確定

/admin/mail-inbox（承認） ─┐
/events/new（手動作成）  ─┼→ events 作成 → 級別グループへ即時 push
/events/[id]（再送ボタン）─┘
```

### 3.2 ビジネスルール

#### 配信方式

- LINE Messaging API の Push を使う
- 送信先は級別 LINE グループ 5つ（A/B/C/D/E に 1:1）
- Bot は**級ごとに専用チャネル 5個**。既存 30 Bot プールから確保し、大会ごとに確保・解放される既存プール（`purpose='event_broadcast'`）とは別扱いにする
  - **根拠**: 無料通数枠はチャネル（公式アカウント）単位で月200通。Bot 1個を全級グループに入れると5グループ合計で月200通＝10名グループなら月20回で枯渇する。級ごとに分ければ各級200通で実質詰まらない

#### 配信対象と絞り込み

- 対象は全ての `events`（他会主催の大会申込・会内行事の両方。`events` にこの2つを判別するカラムは存在しない）
- `events.eligible_grades` に一致する級のグループにだけ送る。**null または空なら全5グループ**（アプリ内の申込可否判定 `isGradeEligible` と同じルール）
- 配信可否のチェックボックスは作らない（全件配信する）

#### 配信タイミングと粒度

- 新規登録の**即時**（レスポンス flush 後の fire-and-forget）。遅延キュー・取消・配信時間帯ガードは持たない
- **送信先グループごとに1通へまとめる**。1回の承認で複数の `events` が作られ、同じ級に複数件該当する場合は1通に連結する
- 大会情報を後から編集しても再送しない（3.2「再送」の手動操作は除く）

#### 文面

```
8/15(土) 大阪ABの案内が来ました！
https://…/api/line-broadcast/attachments/{token}

締切 は7/25です。
```

| 要素 | 出所 | 欠損時 |
|---|---|---|
| 日付 | `events.event_date` を `M/D(曜)` 形式へ | — （必須） |
| 大会名 | `events.title` | — （必須） |
| 要綱 URL | 承認フォームで選択された添付の共有 URL | **行ごと省略** |
| 締切 | `events.internal_deadline`（会内締切） | **行ごと省略** |

- 複数件を1通にまとめる場合は区切り線で連結する
- 会内行事にも同じ文面を使う（判別カラムが無いため出し分けできない）

#### 級グループの紐付け

LINE グループ ID は LINE アプリから見えず、Bot が招待された際の `join` webhook でしか取得できない。既存の招待コード方式を流用する:

1. 管理画面で級を選び招待コードを発行（6桁 + 友だち追加 URL）
2. その級の Bot をグループに招待
3. `join` webhook でグループ ID を捕捉
4. グループ内で6桁コードを発言して紐付け確定

紐付けは**常設**で、大会ごとに解放されない。

#### 冪等性

- **`(大会, 級)` の組で1回だけ**送信する
- 一部の級だけ送信できた場合、**送信できた級のみ「送信済み」として記録し、送れなかった級は未送信のまま残す**（後から紐付けて送り直せるようにするため）

#### エラー・境界条件

| ケース | 挙動 |
|---|---|
| 対象級のグループが未紐付け | その級はスキップし、他の級へは送る。**スキップしたことを管理者の個人 LINE へ通知する** |
| 対象級が1つも紐付いていない | 全スキップ + 管理者通知。大会の登録処理自体は成功させる |
| push が失敗した（通数超過・401 等） | その級は未送信のまま残す。**紐付けは自動解除しない**。管理者の個人 LINE へ通知する |
| `eligible_grades` が null / 空 | 全5グループへ送る |
| 要綱の添付が選択されていない | URL 行を省略して送る |
| `internal_deadline` が未設定 | 締切行を省略して送る |
| 配信処理が例外を投げた | 大会の登録・承認処理は**巻き戻さない**（fire-and-forget） |

#### 再送

- `/events/[id]` の「級グループへ再送」ボタンから、**まだ送信済みでない級にだけ**送る
- 既に送信済みの級には送らない（二重送信しない）
- 権限は管理者のみ

#### 権限

- 級グループの紐付け・解除、再送はすべて **`admin` のみ**（`vice_admin` を含まない）
- 自動配信そのものはシステムが行うため権限判定の対象外

## 5. Non-goals

### 機能面

- 送信後に大会情報が編集された場合の追随・訂正配信
- 級グループに参加していない会員への到達（会員100名超に対しグループは計50名程度。**半数近くには届かない**ことを受容する）
- 既存の大会別グループ配信（`event-line-broadcast`）との統合・置き換え。2系統は併存する（読み手が違う: 会員全体 vs 申込者）
- 遅延キュー・送信取消・配信時間帯ガード（深夜に登録すれば深夜に通知が飛ぶ）
- 級別 LINE グループそのものの作成（人が LINE 上で作る）
- 会内行事と大会申込で文面を出し分けること（`events` に判別カラムが無い）
- 級が未設定の会員への配信
- 配信可否を大会ごとに選ぶ UI

### 技術面

- 通数超過の自動検知・自動抑制・複数 Bot への分散（超過時は手動対応する方針をユーザーが受容済み）
- LINE Official Account Manager のブラウザ自動操作（Playwright / 予約送信）による配信 — §6 の設計判断を参照
- 既存 Bot プール（`purpose='event_broadcast'`）の確保・解放ロジックの変更
- 添付の公開 route（`/api/line-broadcast/attachments/{token}`）の認証方式の変更

## 6. 技術的制約・契約

### 互換性・変更禁止挙動

- 既存の大会別グループ配信（Bot プール確保・招待コード・`join` webhook・要綱送信・自動解放）の挙動を変えない
- `/admin/line-channels` は大会配信用チャネルのみを表示する現状を維持する（級用チャネルを混入させない）
- webhook のチャネル振り分け（`webhook_destination_id` による routing）は既存機構をそのまま使い、新しい振り分け方式を作らない
- 添付の公開 route は**未認証のまま**維持する（`middleware.ts` の matcher 除外を変更しない）。級グループには未登録会員がいる可能性があり、認証を要求すると要綱が開けなくなる

### 公開契約

- 要綱 URL は既存の共有トークン機構（32文字ランダム・60日 TTL・署名なし）をそのまま使う。新しいトークン方式を作らない
- 級グループへの配信は LINE Messaging API Push のみを使う（管理画面の自動操作は行わない）

### 保持データ

- 級 ↔ LINE グループ ↔ Bot チャネルの常設紐付けを保持する必要がある（既存の大会単位の紐付けは大会終了で解放されるため流用できない）
- `(大会, 級)` 単位の送信済み記録を保持する必要がある（冪等性と再送判定のため）
- 承認フォームで選択された「LINE告知に載せる要綱」の添付を保持する必要がある

### セキュリティ・権限

- 紐付け・解除・再送を行う Server Action は `admin` のみ（`vice_admin` を含まない）
- LINE のチャネルアクセストークンをログ・エラーメッセージに出力しない
- 配信本文をアプリケーションログへ出力しない

### 利用技術上の制約

- スキーマ変更は Drizzle のマイグレーション経由（`db:push` は使わない）。**本番 DB への直接操作はユーザー確認必須**
- 実装時のテスト DB 書き込みはテスト DB 限定
- 並行 worktree があるためマイグレーション番号の衝突に注意する

### 未解決の技術論点（→ 技術計画フェーズで解決）

- 級グループ紐付けを既存 `event_line_broadcasts` の拡張で表現するか、専用テーブルを新設するか（`event_id` が UNIQUE かつ NOT NULL のため、そのままでは常設紐付けを表現できない）
- `(大会, 級)` の送信済み記録を既存 `event_lifecycle_notifications` の型（`UNIQUE(event_id, type)`）で表現するか、専用テーブルを新設するか
- 承認フォームで選ばれた要綱添付の保存先（既存 `event_broadcast_guideline_attachments` は `event_line_broadcasts` にぶら下がり、新規登録時点では親行が存在しない）
- 手動作成（`/events/new`）経路では添付が存在しないため要綱選択 UI が不要 — フォームの分岐をどう扱うか
- `line-webhook-handler` の `join` / `message` 分岐を級グループ用にどう拡張するか（既存の大会用フローと排他にする必要がある）

## 7. 設計判断の根拠

### Playwright + LINE 管理画面自動操作を検討して不採用にした

当初の依頼は「match-tracker の札組配信と同じ仕組み（Playwright で LINE 画面を bot 操作）を kagetra_new にも」だった。調査の結果**不採用**とした。

- match-tracker の実体は `line-chat-worker/`（kagetra_new と**同じ Oracle Cloud VM 上の独立 Docker 常駐ワーカー**）。LINE Official Account Manager を Playwright 操作して**「予約送信」を登録するだけ**で、実送信は LINE 側が行う
- あちらが自動操作を選んだ理由: Push API はグループ人数分課金される。70名 × 月20回 = 1,400通 ≫ 無料枠200通。一方 OAM のチャットは無料通数の対象外・無制限
- **1つの LINE グループに参加できる公式アカウントは1体まで**（match-tracker が Bot 10体ローテ作戦を実装した後に判明した制約）

**不採用の理由**: ユーザーが「級ごとに LINE グループを分ける」方針へ転換したことで、1グループ10名程度＝Push でも通数が収まるようになった。これにより既存の Bot プール・webhook・push ヘルパーがそのまま使え、kagetra_new 単独で完結する。match-tracker への依存も、月1回の手動 SSO 再ログインという運用負債も背負わずに済む。

### Bot を級ごとに5個に分ける

無料通数枠がチャネル単位（月200通）であるため。1個を全級で共有すると5グループ合計で月20回の配信で枯渇する。既存プールは30個あるので5個を常設用に確保しても25個残る。

### 即時送信とし、遅延キュー・取消を持たない

当初は「30分後に予約送信し、その間は取り消せる」という誤爆ガードを検討したが、Push は即時配信で取り消せないため、猶予を作るには DB キュー + 定期タイマーが必要になる。ユーザーが実装コストに見合わないと判断し、即時送信＋ガード無しを受容した。

これに伴い配信時間帯ガード（8:00〜21:00）も落とした（実現には同じキューが必要なため）。

### 文面を「概要 + 要綱 URL」に留める

既存の大会別グループ配信はメール全文を流すが、読み手が「その大会の申込者」である。級別グループの読み手は「会全体」で、目的は詳細の伝達ではなく**存在の周知**。したがって短い概要と、その場で開ける要綱 URL に留める。

### 大会名に `events.title` をそのまま使う

AI 承認フローが `composeTitle(短縮名, eligible_grades)` で「大阪AB」形式を A→E 固定順で自動生成し、`events.title` の初期値にしている。系列マスタ（`tournament_series.short_name`）を辿る必要はない。

### 未紐付け・送信失敗を管理者へ通知する

無言でスキップすると「特定の級だけ永久に届いていない」状態に誰も気づけない。既存の `system_notify` チャネル（管理者の個人 LINE 宛）が使えるため、通知コストは低い。

### 送信失敗時に紐付けを自動解除しない

既存の大会別配信は 4xx で紐付けを解除してチャネルをプールへ戻すが、これは「大会が終われば不要になる一時的な紐付け」だから成立する。級グループの紐付けは常設なので、自動解除されると運用のたびに繋ぎ直すことになる。
