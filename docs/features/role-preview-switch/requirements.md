# role-preview-switch 要件定義書

## 1. 概要

- **目的**: 管理者（popon）が、ログアウトや別アカウントを用意することなく、アプリの UI から「副管理者」「一般会員」としての見え方・触れ方へ切り替えて確認できるようにする。
- **背景・動機**: 認証が LINE ログイン一本のため、一般会員としての確認には別の LINE アカウントと招待済み会員行が必要で、実機（スマホ）での確認が事実上できない。会員向け機能をリリースするたび「会員から本当にこう見えるか」を検証できないまま出荷している。

## 2. ユーザーストーリー

- **対象ユーザー**: 環境変数で明示的に許可された 1 名（popon）のみ。他の管理者・会員には機能そのものが存在しないように見える。
- **ユーザーの目的**: 自分のアカウントのまま、表示ロールを下げて画面を回遊し、会員に見えるもの・見えないもの・押せる操作を実機で確認する。
- **利用シナリオ**:
  1. popon が実機（PWA）で `{名前}さん` をタップし、設定シートの「表示ロール」で「一般会員」を選ぶ。
  2. 画面が即座に会員ビューへ切り替わり、ボトムナビの管理タブや管理者専用の導線が消える。ヘッダーには「会員ビュー」バッジが出る。
  3. そのまま各画面を回遊し、大会申込などの操作も会員として実際に試す。
  4. 確認が済んだらヘッダーのバッジ（または `{名前}さん`）をタップして設定シートを開き、「管理者」を選んで元に戻す。

## 3. 機能要件

### 3.1 画面と遷移（画面インベントリ＋ナビゲーション地図）

新規画面は作らない。既存の共通シェルに 2 箇所を追加する。

| # | 画面／要素 | 追加・変更内容 |
|---|---|---|
| S1 | 設定シート `AccountMenu`（全画面のヘッダー `{名前}さん` から開く） | 「表示ロール」セクションを追加。`管理者` / `副管理者` / `一般会員` の3択。**プレビュー許可ユーザーにのみ表示**。 |
| S2 | 共通ヘッダー `AppBarMain`（44px） | プレビュー中のみ、`{名前}さん` の隣に小さいバッジ（`副管理者ビュー` / `会員ビュー`）を表示。バッジのタップで S1 が開く。 |

遷移:

```
任意の画面
  └─ ヘッダー `{名前}さん` タップ ─┐
  └─ ヘッダー プレビューバッジ タップ ─┴→ 設定シート(S1)
                                            └─ 表示ロール選択 → 現在の画面のまま再描画（シートは閉じる）
```

見た目の詳細は既存コンポーネント（`Pill` / 設定シートの行パターン）を踏襲するため design-spec は作成しない（`design_required: false`）。

### 3.2 ビジネスルール

**R1. 誰が使えるか**
- 環境変数 `ROLE_PREVIEW_USER_IDS`（カンマ区切りの `users.id`）に自分の id が含まれるユーザーだけが、切替 UI を見ることも切替操作を実行することもできる。
- 環境変数が未設定・空文字の場合は**機能全体が無効**（fail-closed）。UI も出ず、切替アクションも常に拒否する。
- 許可リストに含まれていても、**本物のロールより上へは切り替えられない**（`vice_admin` の許可ユーザーが `admin` を選んでも拒否）。切替先として選べるのは「本物のロール以下」だけ。

**R2. プレビューの効き方（実効ロール）**
- 切替後、アプリ全体が参照する `session.user.role`（＝実効ロール）が選択したロールになる。UI の出し分けだけでなく、**Server Action / route handler の権限チェックも実効ロールで判定される**。
- したがってプレビュー中は、管理者専用の操作を URL 直打ちや直接呼び出しで実行することもできない。
- 本物のロールは別の経路（`session.user.realRole`）で参照でき、**プレビューの開始・終了の認可にはこちらだけを使う**。

**R3. 権限外 URL へのアクセス**
- プレビュー中に `/admin/*` など権限外の URL を直接開いた場合、一般会員が踏んだときと**完全に同じ挙動**（既存の `/403` へのリダイレクト）とする。403 画面に復帰導線などの差分は加えない。

**R4. 書き込み操作**
- プレビュー中でも、そのロールで許可されている書き込み操作（イベント出欠登録・大会申込など）は**通常どおり実行される**。テストデータの後始末は運用（popon 自身）で行う。
- LINE 通知等の副作用も本番同様に発火する。これは仕様として受け入れる（R2 により管理者専用の一斉配信等はそもそも実行できない）。

**R5. 持続性**
- プレビュー状態は**セッション（JWT）に保持**する。リロード・画面遷移・PWA の再起動をまたいでも維持される。
- ログアウト → 再ログインでプレビューは解除され、本物のロールに戻る。
- 「管理者」（＝本物のロール）を選ぶとプレビューは解除される。

**R6. エラー・境界条件**
- 許可されていないユーザーが切替アクションを直接呼んだ場合 → 拒否（`/403` 相当）。状態は変化しない。
- 本物のロールより上のロールを指定して呼ばれた場合 → 拒否。状態は変化しない。
- 不正な値（enum 外の文字列）を指定して呼ばれた場合 → 拒否。状態は変化しない。
- プレビュー中に該当ユーザーが退会（`deactivatedAt` 設定）された場合 → 既存の再検証でセッションが無効化される挙動が優先される（プレビューは介入しない）。
- プレビュー中に本物のロールが DB 上で降格された場合 → 実効ロールが本物のロールを超えることは無いよう、実効ロールは常に「本物のロール以下」に丸める。

## 5. Non-goals

**機能面**
- **他会員へのなりすまし**（特定の別会員のデータを見る／その人として操作する）。本機能は「同一ユーザー・同一データのまま権限だけ下げる」もので、他人のデータには一切触れない。
- `users.role` の永続的な変更（DB 上のロールは書き換えない）。
- プレビュー中の書き込みブロック／サンドボックス化（R4 のとおり通常実行する）。
- プレビュー操作の監査ログ・通知。
- 一般の管理者が使える汎用機能にすること（許可は環境変数のリスト運用のみ）。
- 403 画面へのプレビュー復帰導線の追加（R3）。

**技術面**
- DB スキーマ変更・migration（JWT クレームのみで完結させる）。
- middleware（Edge）でのロール判定の新設。
- 既存の認可チェックの書き方を横断的にリファクタすること（`session.user.role` を読む既存箇所は無変更で成立させる）。

## 6. 技術的制約・契約

- **単一の切替点**: 実効ロールは `auth.config.ts` の `session` コールバックで決定する。`session.user.role` を読む既存 41 ファイル・162 箇所は**無変更**で実効ロールに追従すること。
- **本物のロールを壊さない**: JWT の `token.role` は常に本物のロールを保持し、プレビュー値で上書きしない。実効ロールは `viewAsRole ?? realRole` の導出として表現する。
- **セッション公開契約の追加**: `Session['user']` に `realRole`（本物のロール）を追加する。既存の `role` の意味は「実効ロール」に変わるが、非プレビュー時は従来と同値。
- **`unstable_update` のパッチ許可リスト**: `auth.config.ts` の `jwt` コールバックは `trigger === 'update'` で `lineUserId` / `lineLinkedAt` / `lineLinkedMethod` の 3 フィールドしか転記しない。新しいクレームを**明示的に追加しないと黙って捨てられる**。
- **`nodeJwtCallback` の毎リクエスト経路**: 現状 `token.role` は `token.id` 未解決時にしか DB から取り込まれない。実効ロールの丸め込み（AC-12）は、この非対称性に依存しない形で実装すること。
- **middleware は DB 不可・Edge**: 現状ロールを見ていないため変更不要。今後もロール判定を持ち込まない。
- **環境変数**: `ROLE_PREVIEW_USER_IDS`（カンマ区切りの `users.id` UUID）。Node 側でのみ参照する。未設定＝無効（fail-closed）。本番でも設定すれば有効になる（`NODE_ENV` では制限しない — 実機確認が目的のため）。
- **セキュリティ要件**: 切替アクションの認可は「許可リスト所属」かつ「本物のロール以下への切替」の二重条件。実効ロールを認可に使ってはならない。
- **並行作業**: `feature/entry-management` ブランチが `components/layout/bottom-nav.tsx` を変更済み（未マージ）。本機能は `account-menu.tsx` / `app-bar-main.tsx` / `mobile-shell.tsx` / `(app)/layout.tsx` を触るため直接の同一ファイル衝突は無いが、`mobile-shell.test.tsx` は双方が触りうる。実装時にリベース順序を管理すること。

## 7. 設計判断の根拠

- **なぜ session コールバックで実効ロールを作るか**: 権限判定が `session.user.role` の 1 箇所に集約されており、ここを差し替えるだけで UI と認可の両方が同時に、抜けなく切り替わる。個別画面にプレビュー分岐を撒く案は 162 箇所の抜け漏れリスクがあり、「本物と同じ見え方」という目的を達成できない。
- **なぜ環境変数の許可リストか**: DB スキーマを増やさずに fail-closed（未設定なら誰も使えない）を作れる。「管理者なら誰でも」は将来管理者が増えたときに意図せず全員へ広がる。
- **なぜ本物のロールを別クレームに保つか**: プレビュー中に実効ロールで認可すると、復帰操作が自分自身を拒否して**管理者に戻れなくなる**。本物のロールを独立して保持することがこの機能の安全装置。
- **なぜ書き込みを許すか**: 「会員がこの画面でどう操作するか」の検証が目的の一つであり、読み取り専用では申込フローの検証ができない。データは popon 自身の行に限られ、管理者操作は R2 により封じられているため、被害範囲が自分の行に閉じる。
- **なぜ 3 状態か**: 副管理者は現状 3 層権限の中間で、admin だけに見えるもの／vice_admin にも見えるものの差分が実機で確認できていない。JWT クレームが enum になるだけで実装コストはほぼ変わらない。
