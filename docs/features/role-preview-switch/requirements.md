# role-preview-switch 要件定義書

## 1. 概要

- **目的**: 管理者（popon）が、ログアウトや別アカウントを用意することなく、アプリの UI から「副管理者」「一般会員」「ゲスト」としての見え方・触れ方へ切り替えて確認できるようにする。
- **背景・動機**: 認証が LINE ログイン一本のため、一般会員としての確認には別の LINE アカウントと招待済み会員行が必要で、実機（スマホ）での確認が事実上できない。会員向け機能をリリースするたび「会員から本当にこう見えるか」を検証できないまま出荷している。

## 2. ユーザーストーリー

- **対象ユーザー**: 環境変数で明示的に許可された 1 名（popon）のみ。他の管理者・会員には機能そのものが存在しないように見える。
- **ユーザーの目的**: 自分のアカウントのまま、表示ロールを下げて画面を回遊し、会員に見えるもの・見えないもの・押せる操作を実機で確認する。
- **利用シナリオ**:
  1. popon が実機（PWA）でボトムナビの「設定」タブを開き、「表示ロール」で「一般会員」を選ぶ。
  2. 画面が即座に会員ビューへ切り替わり、ボトムナビの管理タブや管理者専用の導線が消える。設定タブには「一般会員」バッジが出る。
  3. そのまま各画面を回遊し、大会申込などの操作も会員として実際に試す。
  4. 確認が済んだら設定タブへ戻り、「管理者」を選んで元に戻す。
  5. ゲストの見え方を確かめたいときも同じ手順で「ゲスト」を選ぶ。ナビが「大会」「設定」の2タブになり、設定画面もゲスト用の「表示のみ」になる。戻すときは設定タブの「表示ロール」で「管理者」を選ぶ（ゲストビューでもこのセクションだけは出る）。

## 3. 機能要件

### 3.1 画面と遷移（画面インベントリ＋ナビゲーション地図）

新規画面は作らない。既存の共通シェルの 3 箇所を追加・変更する。

| # | 画面／要素 | 追加・変更内容 |
|---|---|---|
| S1 | 設定ページ `/settings`（ボトムナビ「設定」タブ） | 「表示ロール」セクション。**本物のロールが管理者なら `管理者` / `副管理者` / `一般会員` / `ゲスト` の4択**、副管理者なら `副管理者` / `一般会員` の2択。**プレビュー許可ユーザーにのみ表示**。 |
| S2 | ボトムナビ「設定」タブ | プレビュー中のみタブにバッジ（`副管理者` / `一般会員` / `ゲスト`）を表示。 |
| S3 | 設定ページのゲスト分岐（ゲスト用の「表示のみ」ビュー） | **ゲストビューでプレビュー中のときだけ**「表示ロール」セクションを描画する。これがゲストビューからの唯一の復帰導線。本物のゲストには従来どおり出さない。 |

※ S1/S2 は当初「上部バー `AppBarMain` の `{名前}さん` から開く設定シート `AccountMenu`」だった。nav-settings-hub（PR #351）で上部バーが廃止され、設定はタブ＋独立ページへ移っている。上表は現行の姿。

遷移:

```
任意の画面
  └─ ボトムナビ「設定」タブ → /settings
                                └─ 表示ロール選択 → /settings のまま再描画（新しい cookie を載せた再リクエスト）

ゲストビュー中（ナビは「大会」「設定」の2タブ）
  └─ ボトムナビ「設定」タブ → /settings（ゲスト用の表示のみビュー ＋ 表示ロールセクション）
                                └─ 「管理者」を選択 → 復帰
```

見た目の詳細は既存コンポーネント（`Pill` / 設定ページの行パターン）を踏襲するため design-spec は作成しない（`design_required: false`）。

### 3.2 ビジネスルール

**R1. 誰が使えるか**
- 環境変数 `ROLE_PREVIEW_USER_IDS`（カンマ区切りの `users.id`）に自分の id が含まれるユーザーだけが、切替 UI を見ることも切替操作を実行することもできる。
- 環境変数が未設定・空文字の場合は**機能全体が無効**（fail-closed）。UI も出ず、切替アクションも常に拒否する。
- 許可リストに含まれていても、**本物のロールより上へは切り替えられない**（`vice_admin` の許可ユーザーが `admin` を選んでも拒否）。切替先として選べるのは「本物のロール以下」だけ。
- **例外（締め出し防止）**: プレビュー中のユーザーが許可リストから外された場合でも、**本物のロールへ戻す操作だけは常に可能**とする。実効ロールは下がる方向にしか動かないため、これで権限が広がることはない。
- **ゲストへの切替は本物のロールが `admin` のときだけ**（「本物のロール以下なら選べる」の唯一の例外）。許可リストに載った副管理者・一般会員には「ゲスト」の選択肢を出さず、切替アクション・JWT 更新経路のどちらでも拒否する。

**R2. プレビューの効き方（実効ロール）**
- 切替後、アプリ全体が参照する `session.user.role`（＝実効ロール）が選択したロールになる。UI の出し分けだけでなく、**Server Action / route handler の権限チェックも実効ロールで判定される**。
- したがってプレビュー中は、管理者専用の操作を URL 直打ちや直接呼び出しで実行することもできない。
- 本物のロールは別の経路（`session.user.realRole`）で参照でき、**プレビューの開始・終了の認可にはこちらだけを使う**。

**R3. 権限外 URL へのアクセス**
- プレビュー中に `/admin/*` など権限外の URL を直接開いた場合、一般会員が踏んだときと**完全に同じ挙動**（既存の `/403` へのリダイレクト）とする。403 画面に復帰導線などの差分は加えない。

**R4. 書き込み操作**
- プレビュー中でも、そのロールで許可されている書き込み操作（イベント出欠登録・大会申込など）は**通常どおり実行される**。テストデータの後始末は運用（popon 自身）で行う。
- LINE 通知等の副作用も本番同様に発火する。これは仕様として受け入れる（R2 により管理者専用の一斉配信等はそもそも実行できない）。

**R5. 持続性**
- プレビュー状態は**セッション（JWT）に保持**する。リロード・画面遷移・PWA の再起動をまたいでも維持される。
- ログアウト → 再ログインでプレビューは解除され、本物のロールに戻る。
- 「管理者」（＝本物のロール）を選ぶとプレビューは解除される。

**R6. エラー・境界条件**
- 許可されていないユーザーが切替アクションを直接呼んだ場合 → 拒否（`/403` 相当）。状態は変化しない。
- 本物のロールより上のロールを指定して呼ばれた場合 → 拒否。状態は変化しない。
- 不正な値（enum 外の文字列）を指定して呼ばれた場合 → 拒否。状態は変化しない。
- プレビュー中に該当ユーザーが退会（`deactivatedAt` 設定）された場合 → 既存の再検証でセッションが無効化される挙動が優先される（プレビューは介入しない）。
- プレビュー中に本物のロールが DB 上で降格された場合 → 実効ロールが本物のロールを超えることは無いよう、実効ロールは常に「本物のロール以下」に丸める。

**R7. ゲストビューの特例（復帰導線と忠実度）**
- ゲストビュー中の設定ページは**ゲスト用の「表示のみ」ビューのまま**（表示名・級・所属会＋ログアウト）で、そこに「表示ロール」セクションだけを足す。管理者向けのアカウント／管理セクションは復活させない。
- 「表示ロール」セクションの中身は他ロールのプレビュー時と同じ全選択肢（管理者 / 副管理者 / 一般会員 / ゲスト）。ゲストビュー専用の簡略表示にはしない。
- **本物のゲスト（`realRole === 'guest'`）には、許可リストに載っていてもこのセクションを出さない**。ゲストがプレビュー機能を持つことは無い。
- プレビューで再現されるのは**実効ロールに依存する挙動だけ**（画面の出し分け・ボトムナビ・middleware のゲスト許可リスト・Server Action / route handler の認可）。`users.role` を直接読む処理（申込書の対象抽出・参加希望者数・督促・Web Push の宛先・参加者欄のゲスト印）は本物のロールのまま動くため、プレビュー中の自分はそれらの上では引き続き管理者として扱われる。
- ゲストビュー中の書き込みは R4 のとおり通常どおり実行される。ゲストは会内締切を過ぎても出欠回答できる（guest-role R3）ので、プレビュー中は自分の出欠行に対して同じことができる。

## 5. Non-goals

**機能面**
- **他会員へのなりすまし**（特定の別会員のデータを見る／その人として操作する）。本機能は「同一ユーザー・同一データのまま権限だけ下げる」もので、他人のデータには一切触れない。
- `users.role` の永続的な変更（DB 上のロールは書き換えない）。
- プレビュー中の書き込みブロック／サンドボックス化（R4 のとおり通常実行する）。
- プレビュー操作の監査ログ・通知。
- 一般の管理者が使える汎用機能にすること（許可は環境変数のリスト運用のみ）。
- 403 画面へのプレビュー復帰導線の追加（R3）。
- **ゲストビューで `users.role` 由来の挙動まで再現すること**（申込書の対象抽出・参加希望者数・督促・Web Push の宛先・参加者欄のゲスト印）。再現するのは実効ロールに依存する挙動だけ（R7）。
- **副管理者・一般会員へのゲストビューの開放**（R1 のとおり本物のロールが管理者のときだけ）。
- ゲストビュー中の設定ページを管理者向けの内容に戻すこと（「表示ロール」セクション以外は足さない）。

**技術面**
- DB スキーマ変更・migration（JWT クレームのみで完結させる）。
- middleware（Edge）でのロール判定の新設。
- 既存の認可チェックの書き方を横断的にリファクタすること（`session.user.role` を読む既存箇所は無変更で成立させる）。

## 6. 技術的制約・契約

- **単一の切替点**: 実効ロールは `auth.config.ts` の `session` コールバックで決定する。`session.user.role` を読む既存 41 ファイル・162 箇所は**無変更**で実効ロールに追従すること。
- **本物のロールを壊さない**: JWT の `token.role` は常に本物のロールを保持し、プレビュー値で上書きしない。実効ロールは `viewAsRole ?? realRole` の導出として表現する。
- **セッション公開契約の追加**: `Session['user']` に `realRole`（本物のロール）を追加する。既存の `role` の意味は「実効ロール」に変わるが、非プレビュー時は従来と同値。
- **`unstable_update` のパッチ許可リスト**: `auth.config.ts` の `jwt` コールバックは `trigger === 'update'` で `lineUserId` / `lineLinkedAt` / `lineLinkedMethod` の 3 フィールドしか転記しない。新しいクレームを**明示的に追加しないと黙って捨てられる**。
- **`nodeJwtCallback` の毎リクエスト経路**: 定義時点では `token.role` は `token.id` 未解決時にしか DB から取り込まれなかった。実効ロールの丸め込み（AC-12）はこの非対称性に依存しない形で実装すること。（実装時追記: `realRole` が切替の認可根拠になったため、毎リクエスト経路にも `users.role` の同期を追加して非対称性そのものを解消した。丸め込みは引き続き無条件。）
- **`unstable_update` 以外の update 経路**: Auth.js の `POST /api/auth/session`（`useSession().update()` と同じエンドポイント）は、認証済みクライアントが送った任意のペイロードを `jwt` コールバックの `trigger === 'update'` 分岐へそのまま渡す。したがって切替の認可は Server Action だけでなく **`jwt` コールバックにも置く**（Server Action 側だけでは R1 の許可リストが迂回できる）。`viewAsRole: null`（解除）はどちらの層でも許可リスト判定を通さない。
- **middleware は DB 不可・Edge**: 定義時点ではロールを見ていなかったが、その後 guest-role がゲスト許可リストの早期ゲート（`isGuestAllowedPath`）を middleware に置いた。middleware も同じ `authConfig` の `session` コールバックを通るため、そこが読む `session.user.role` は**実効ロール**であり、ゲストプレビューにもそのまま効く（AC-24 はこの性質に依存する）。middleware のロール参照を `token.role`（本物のロール）へ戻してはならない。
- **`ROLES_HIGH_TO_LOW` への単純追加では足りない**: ランク比較（`guest` は最下位）だけで選択肢を作ると副管理者にもゲストが生える。ゲストは「本物のロールが `admin`」を条件に別立てで足すこと。`jwt` コールバック側の認可にも同じ条件を置く（Server Action 側だけでは `/api/auth/session` から迂回できる）。
- **セキュリティ上の受容点**: `guest` を切替先として認めることで、改竄した JWT クレーム（`viewAsRole='guest'`）で管理者をゲストビューへ落とせるようになる。降格方向のみで権限は増えず、`realRole` は保たれるため復帰できる。昇格不能（AC-12）は従来どおり維持する。
- **環境変数**: `ROLE_PREVIEW_USER_IDS`（カンマ区切りの `users.id` UUID）。Node 側でのみ参照する。未設定＝無効（fail-closed）。本番でも設定すれば有効になる（`NODE_ENV` では制限しない — 実機確認が目的のため）。
- **セキュリティ要件**: 切替アクションの認可は「許可リスト所属」かつ「本物のロール以下への切替」の二重条件。実効ロールを認可に使ってはならない。
- **並行作業**: `feature/entry-management` ブランチが `components/layout/bottom-nav.tsx` を変更済み（未マージ）。本機能は `account-menu.tsx` / `app-bar-main.tsx` / `mobile-shell.tsx` / `(app)/layout.tsx` を触るため直接の同一ファイル衝突は無いが、`mobile-shell.test.tsx` は双方が触りうる。実装時にリベース順序を管理すること。

## 7. 設計判断の根拠

- **なぜ session コールバックで実効ロールを作るか**: 権限判定が `session.user.role` の 1 箇所に集約されており、ここを差し替えるだけで UI と認可の両方が同時に、抜けなく切り替わる。個別画面にプレビュー分岐を撒く案は 162 箇所の抜け漏れリスクがあり、「本物と同じ見え方」という目的を達成できない。
- **なぜ環境変数の許可リストか**: DB スキーマを増やさずに fail-closed（未設定なら誰も使えない）を作れる。「管理者なら誰でも」は将来管理者が増えたときに意図せず全員へ広がる。
- **なぜ本物のロールを別クレームに保つか**: プレビュー中に実効ロールで認可すると、復帰操作が自分自身を拒否して**管理者に戻れなくなる**。本物のロールを独立して保持することがこの機能の安全装置。
- **なぜ書き込みを許すか**: 「会員がこの画面でどう操作するか」の検証が目的の一つであり、読み取り専用では申込フローの検証ができない。データは popon 自身の行に限られ、管理者操作は R2 により封じられているため、被害範囲が自分の行に閉じる。
- **なぜゲストを解禁したか（当初は禁止していた）**: guest-role 定義時の禁止理由は「ゲスト設定画面に切替セクションが無く復帰不能になる」だった。その後の実装で復帰の材料が揃っている（設定タブは `guestVisible`、`/settings` は完全一致でゲスト許可リスト内、解除操作は許可リスト判定を迂回できる = AC-10b、`returnTo=/settings` は `sanitizeReturnPath` を通る）。足りないのは「ゲスト設定画面にセクションを出す」1点だけで、禁止を維持する理由が無くなった。
- **なぜゲスト設定画面を管理者向けに戻さないか**: 実効ロールが `guest` の間は `/settings/*` と `/admin/members` がゲスト許可リストの外にあり、リンクを描画しても押した先で 403 になる。壊れた画面を作るうえに、「ゲストから設定画面がどう見えるか」という確認目的そのものを潰す。
- **なぜゲストへの切替を管理者限定にしたか**: 「本物のロール以下なら選べる」をそのまま適用すると、許可リストに載った一般会員にもゲストビューが生える。本機能は最初から「意図せず広がる形は採らない」方針（環境変数の許可リストを選んだ理由と同じ）で、ゲストも同じ扱いにする。
- **なぜ 3 状態か**: 副管理者は現状 3 層権限の中間で、admin だけに見えるもの／vice_admin にも見えるものの差分が実機で確認できていない。JWT クレームが enum になるだけで実装コストはほぼ変わらない。

## 8. 本番有効化手順（出荷後の残 DoD）

1. 対象ユーザーの `users.id` を確認する（`SELECT id, name FROM users WHERE name = '...'`）。
2. `/opt/kagetra/.env.production` に `ROLE_PREVIEW_USER_IDS=<users.id>` を追記する。
3. web サービスを再起動する（`systemctl restart` — Node 側で `process.env` を読むだけなので再ビルドは不要）。
4. 実機（PWA）で AC-14 / AC-15 / AC-17 を確認する。
5. 無効化したいときは値を空にして再起動するだけでよい（fail-closed）。
