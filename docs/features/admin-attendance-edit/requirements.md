# admin-attendance-edit 要件定義書

## 1. 概要

- **目的**: 大会（イベント）の編集画面 `/events/[id]/edit` に「参加者」管理セクションを設け、管理者・副管理者が任意の登録ユーザー（一般会員・ゲスト・管理者・副管理者を含む）を参加者として**追加・削除**できるようにする。
- **背景・動機**: 出欠回答は現状本人のみ（`submitAttendance` は `session.user.id` 固定）で、管理者であっても他人の出欠を操作する手段がない。実運用では「アプリを開かない会員の分を管理者が代理登録する」「誤登録を取り消す」場面があり、その都度本人に操作を依頼するのは回らない。

## 2. ユーザーストーリー

| 役割 | この機能での関心 |
|---|---|
| 管理者・副管理者 | 本人から口頭・LINE で参加意思を聞いたとき、代わりに参加登録する。誤登録・不参加連絡を受けたとき参加者から外す |
| 会員・ゲスト（追加される側） | 自分でアプリを操作しなくても参加者名簿に載る。自分の回答画面・表示は従来と変わらない |

**利用シナリオ**

1. 会員 X から「○○大会に出ます」と LINE で連絡が来る
2. 管理者が `/events/[id]/edit` を開き、「参加者」セクションで X を検索して追加する
3. 詳細ページ `/events/[id]` の参加者欄・`/events` 一覧の苗字列・ホームの出場タイムラインに、X が自分で回答した場合とまったく同じ形で反映される
4. 後日 X から「やっぱり出られない」と連絡が来たら、同じ画面で X を削除する（未回答に戻る）

## 3. 機能要件

### 3.1 画面と遷移

新規画面は作らない。変更は 1 画面のみ。

| 画面 | 変更内容 |
|---|---|
| `/events/[id]/edit`（管理者・副管理者専用） | 既存フォームに加えて「参加者」セクションを追加。現在の参加者（`attend=true` の全行。対象級外の stale 行も管理者には見せる）を一覧表示し、各行に削除操作、追加用の会員ピッカーを置く |

- 追加・削除は**即時反映**（Server Action。フォームの「保存」送信とは独立。既存の `EntryGroupFieldset` がフォーム内在住なのとは異なり、保存ボタンを押さなくても確定する）
- 見た目の詳細は既存の編集画面のフォーム規約に倣う（design-spec は作らない想定 → §7）

### 3.2 ビジネスルール

**追加**

- 追加候補 = `isInvited=true` の全ユーザー（**ロール不問**: 一般会員・ゲスト・管理者・副管理者）∩ **対象級内**（`eligibleGrades` があればその級のみ。無ければ全級）。**級未設定（`grade=null`）の会員は対象級ありの大会には追加不可**（先に `/admin/members` で級を設定してから追加する運用）。この絞り込みは詳細ページの分母 `eligibleUsers` と同一定義
- 追加 = `event_attendances` へ `attend=true` を upsert。既に「不参加」（`attend=false`）回答済みの会員を追加すると `attend=true` に上書きされる（本人回答の上書きは許容）。既存 `comment` は保持する（`submitAttendance` と同じ条件付き更新規約）
- 既に参加（`attend=true`）の会員は候補に出さない（出しても no-op のため）
- 会内締切後・開催日後・`not_applying` / `cancelled` の大会でも操作可能（管理者は締切に縛られない既存方針と一貫）

**削除**

- 削除 = `event_attendances` の行削除 =「**未回答**」に戻す（不参加の記録ではない）。本人は改めて自分で回答でき、締切 7 日前以降ならホームの未回答アラート対象にも戻る。行削除により `comment` も消える（未回答に戻る以上自然な帰結として受容）
- 削除対象は `attend=true` の行のみ（「不参加」回答の行はこの画面に出さない・消さない）

**波及（すべて既存挙動のまま・変更しない）**

- 管理者が追加した行は本人が自分で回答した行とデータ上区別されない。したがって参加者欄・人数集計・ホームの希望パス・申込書の対象会員・振込総額・ゲスト出し分け（印付き表示・申込書/会計/ボード集計から除外）はすべて既存ロジックがそのまま適用される
- LINE 通知・lifecycle 通知の claim は一切発生しない

**エラーケース**

- 一般会員・ゲストが Server Action を直接叩いた場合は拒否（Forbidden）
- 候補外のユーザー ID（対象級外・級未設定・`isInvited=false`・存在しない ID）をサーバーへ送っても拒否（UI は候補しか出さないが防御。fail-closed）
- 存在しないイベント ID は拒否

## 4. Acceptance Criteria

| ID | 条件 | 検証手段 |
|----|------|------|
| AC-1 | 管理者・副管理者は、対象級内かつ `isInvited=true` の任意ロールのユーザー（ゲスト含む）を参加者として追加でき、`event_attendances` に `attend=true` 行が upsert される | auto-test |
| AC-2 | 対象級外・級未設定・`isInvited=false`・存在しないユーザー ID の追加はサーバー側で拒否される | auto-test |
| AC-3 | 「不参加」（`attend=false`）回答済みの会員を追加すると `attend=true` に上書きされ、既存 `comment` は保持される | auto-test |
| AC-4 | 削除すると `event_attendances` の行が削除され「未回答」に戻る（未回答アラートの判定対象に復帰する） | auto-test |
| AC-5 | 一般会員・ゲストのセッションでは追加・削除 Server Action が拒否される | auto-test |
| AC-6 | 会内締切後・開催日後でも管理者は追加・削除できる | auto-test |
| AC-7 | 追加・削除で LINE push・lifecycle 通知 claim が発生しない | auto-test |
| AC-8 | 編集画面の参加者一覧に `attend=true` の全行（対象級外 stale 行含む）が表示され、追加候補には参加済み・対象級外・級未設定・`isInvited=false` のユーザーが現れない | auto-test |
| AC-9 | 既存の本人回答（`submitAttendance`）の挙動が変わらない。既存テスト・lint・typecheck が CI で green | auto-test |
| AC-10 | 本番の編集画面で会員を追加→詳細ページの参加者欄に反映→削除→消えることを実機確認 | manual |

## 5. Non-goals

- **本人への LINE 通知**: 追加・削除とも送らない（管理者が本人と合意のうえ操作する前提）
- **監査記録**: 誰がいつ追加・削除したかは記録しない（`event_attendances` に操作者カラムを足さない。身内アプリの割り切り）
- **「不参加として記録」する代理操作**: 削除は未回答に戻すのみ。attend=false の代理登録は作らない
- **コメントの代理入力・編集**: 管理者 UI からは `comment` を触らない
- **申込グループページ・複数日一括の参加者管理**: 操作は日（イベント）ごとに各編集画面で行う。複数日グループは日ごとに追加する
- **表示フィルタの変更**: 詳細ページ・ホームの「対象級外 attend=true 行の除外」は変えない（追加候補を対象級内に絞ることで矛盾自体を発生させない）
- **定員超過チェック**: 現状どおり定員は表示専用。追加時に定員を検証しない

## 6. 技術的制約・契約

- **スキーマ変更なし**: `event_attendances` の列・制約は現状のまま。マイグレーション不要
- **既存挙動の互換**: `submitAttendance`（本人回答）・参加者欄/ホーム/申込書/会計の集計ロジック・ゲスト出し分けは変更しない
- **認可**: Server Action 冒頭で `auth()` + admin / vice_admin チェック（既存 `requireAdminSession` パターン）。UI の出し分けだけに頼らない
- **候補の絞り込み定義の同一性**: 追加候補の条件は `/events/[id]` の `eligibleUsers`（`isInvited=true` ∩ 対象級）と同一定義を用いる。定義が 2 箇所に分裂しないよう実装時に共通化を検討する
- **RSC payload**: 候補リスト（会員名簿）は管理者専用画面にのみ載せる。列は必要最小限（id・表示名・級・ロール程度）
- **データ変更後の revalidate**: `/events/[id]`・`/events`・`/admin/entries` 系・`/dashboard` など参加者数・苗字列・タイムラインに影響するパスを漏れなく再検証する（対象パスの確定は技術計画で行う）
- **未解決の技術論点**（技術計画へ申し送り）:
  - 参加者セクションをフォーム内コンポーネントとするか独立セクションとするかの実装形（即時反映の要件は確定済み）
  - 会員ピッカーの形（検索付きリスト等。会員 100 名超を想定）
  - revalidatePath の対象パス一覧の確定

## 7. 設計判断の根拠

- **削除=行削除（未回答に戻す）**: 「不参加として記録」だと本人回答と区別が付かない偽の回答データが生まれる。行削除なら誤追加の取り消しと不参加連絡の反映が同じ操作で済み、「未回答=不参加」のドメインルールとも整合する（ユーザー選択 2026-08-26）
- **追加候補を対象級内に絞る**: 対象級外の attend=true 行は詳細ページ・ホームの表示から除外される既存仕様があり、絞らずに追加可とすると「追加したのに見えない参加者」が生まれる。表示側の級フィルタを緩める案は stale な自己回答の再表示という副作用を伴うため見送り（ユーザー選択 2026-08-26）
- **通知しない**: 管理者が本人との合意のうえで操作する前提のため（ユーザー選択 2026-08-26）
- **設置場所は編集画面**: ユーザー指定。閲覧系の詳細ページに管理操作を増やさない現行方針（運営操作の集約）とも整合する
- **design-spec は作らない想定**: 管理者専用のユーティリティ画面への追加であり、既存フォーム規約・既存プリミティブの範囲で構成できるため（承認時に要否を最終確認）
