# openchat-broadcast（大会オープンチャットの抽出・LINE 配信）要件定義書

## 1. 概要

**目的:** 大会主催者から届く「大会当日用 LINE オープンチャット」の招待 URL を、管理者が
1 操作で抽出・確認し、当該大会の LINE グループへ Flex Message で配信できるようにする。

**背景:** 最近の競技かるた大会は、当日の対戦組合せ・進行を LINE オープンチャットで流すのが
主流。招待 URL は参加者確定後に、メール本文・PDF・Word・QR コード画像と**バラバラの形式**で
届く。現状は管理者が毎回目視で探し、手作業で会員へ転送している。

**「自動検知して自動配信」を採らない理由:** 本番メール286件の実測（正典 =
[feasibility.md](feasibility.md)）により、AI の有無に関わらず 99% の正しさでは回せないと判明した。

- 招待を運ぶ20件のうち、テキストから URL を取れるのは14件（**70%**）。残り6件は QR 画像のみ
- 協会30周年記念大会（当会出場）は「URL は大会用 LINE アカウント内でご案内」＝**メールに URL が存在しない**
- 全286件のうち当会イベントに紐付くのは21件（**7%**）。自動配信は出場しない大会のオプチャを大量にスパム配信する
- 1メールに複数 URL（級別・開催日別・部門別）が普通にあり、**どれを誰に配るかは機械的に決まらない**

したがって**トリガーは人間**（管理者がメールを大会に紐付ける既存操作の延長）とし、
抽出は決定的（AI なし）に行い、**確認画面で人が確定させる**ことで正しさを担保する。

## 2. ユーザーストーリー

- **対象ユーザー:** 管理者・副管理者（抽出・配信）／全会員（閲覧）
- **目的:** 大会当日までに、出場会員全員がオープンチャットへ入室できている状態を作る
- **利用シナリオ:**
  1. 主催者から「確定名簿＋オープンチャット案内」メールが届く
  2. 管理者が `/admin/mail-inbox/mail/[id]` を開き、対象の大会（申込グループ）を選ぶ
  3. 「オープンチャット抽出」を押す → 本文・添付テキスト・QR から候補が列挙される
  4. 級／開催日／ラベル／パスワードを確認・修正し、「保存して配信」
  5. 会員の LINE に Flex カードが届き、タップでオープンチャット参加画面へ遷移する
  6. LINE を見逃した会員は、アプリの大会詳細画面からも同じ URL を辿れる

## 3. 機能要件

### 3.1 画面と遷移（見た目は design-spec.md 参照）

**画面インベントリ**

| 画面 | 追加/変更 | 内容 |

| `/events/[id]`（大会詳細） | 変更 | 保存済みオープンチャット欄を追加（**全会員に表示・読み取り専用**） |

### 3.2 ビジネスルール

#### 3.2.1 保存の単位と属性

- オープンチャットは**申込グループ（`entry_groups`）に属する**。LINE 紐付け
  （`event_line_broadcasts.entry_group_id` が UNIQUE）と同じ単位に揃える
- 1 グループに**複数のオープンチャットを持てる**。各行の属性:

| 属性 | 内容 |
|---|---|
| URL | 必須。`line.me/ti/g2/...` または短縮 URL |
| 対象級 | 複数選択可。**未指定 = 全級共通** |
| 対象開催日 | グループ内の開催日を1つ選択。**未指定 = 全日共通** |
| 表示ラベル | 任意。空なら級・開催日から自動生成。埋めれば Flex のボタン名になる |
| パスワード | 任意（参加コード） |
| 出典 | `body` / `attachment_text` / `qr` / `manual`（監査用・自動記録） |

- **表示ラベルの自動生成規則:** 級と日付の両方あり → 「6/20(土) C級」／級のみ → 「C級」／
  日付のみ → 「6/20(土)」／どちらも無し → 「オープンチャットに参加」
- 「団体戦 / 1年 / 2年 / 選抜の部」のような**級でも日付でもない分かれ方は表示ラベルで吸収する**
  （級・日付は未指定にし、ラベルに「1年の部」と入れる）
- ★**同一グループ内で表示ラベルが重複してはならない**（design-spec の宿題1）。級でも開催日でもない
  分かれ方では自動生成ラベルが全行「オープンチャットに参加」になり、そのまま配信すると
  **同じ名前のボタンが5個並ぶ Flex** が届いて区別できない。重複する行があるときは保存できず、
  重複している行に「ラベルを入力してください」を表示する。判定は**自動生成後の最終ラベル**で行う
  （自由ラベルが空で級・日付も同じ、というケースも重複として扱う）

#### 3.2.2 抽出（AI を使わない・決定的）

抽出は以下の3段で候補を集め、**すべて候補として提示する（自動確定しない）**。

| Tier | 対象 | 内容 |
|---|---|---|
| 1 | メール本文（text / html）・添付の抽出済みテキスト | `line.me/ti/g2/...`・`line.me/R/ti/g...` の正規表現 |
| 2 | 同上 | 短縮 URL（`x.gd` / `ourl.jp` / `lin.ee` / `bit.ly` / `tinyurl`）。**「未検証」印を付ける** |
| 3 | 画像添付（jpeg/png）・PDF/Word のページ画像 | QR コードをデコードし、得られた URL を候補にする |

- **改行で割れた URL を復元する**: メール本文は 76 桁前後で折り返されるため、`https://line.me/ti/g2/`
  に続くトークンが改行を挟んで分断されることがある（実例 mail#208）。改行＋行頭空白を除去して
  結合してから照合する。**復元できない・トークン長が不正な候補は候補に出さない**（壊れた URL の
  配信は「タップしても入れない」事故になる）
- **短縮 URL はサーバーで展開しない**（外部 HTTP 依存を持ち込まない）。「未検証」として提示し、
  管理者が自分で踏んで確かめる
- **重複排除**: 同一 URL が本文と添付の両方に出た場合は1候補にまとめ、出典を併記する
  （Outlook の `<https://...>` 二重表記も同一視する）
- 候補ゼロのときは「オープンチャットの URL が見つかりませんでした」と表示し、
  **手入力で1行追加できる**（URL がメールに存在しないケース＝協会30周年型を人手で救う）

#### 3.2.3 QR デコード

- 対象: `image/jpeg` / `image/png` の添付、および PDF・Word 添付のページ画像
- ページ画像化は**既存の `pdftoppm` / `libreoffice` 経路を再利用する**
  （`apps/web/src/lib/attachment-image-render.ts`。本番ホストに導入済み）
- 走査ページ数には上限を設ける（既存の `RENDER_PAGE_LIMIT` に準じる）
- **デコードできなくても機能は失敗しない**。「QR を読み取れませんでした」と表示し、
  Tier 1/2 の候補と手入力で続行できる
- QR から得た URL も Tier 1/2 と同じ検証（`line.me` 形式か・短縮 URL か）を通す

#### 3.2.4 級・開催日・パスワードの自動推定（初期値。修正可）

- **級**: URL 直前のテキストから `D級:` / `【Ｃ級】` / `C級`（全角半角どちらも）を拾う
- **開催日**: `6/20(土)：` / `6/20` 形式を拾い、グループ内の開催日と一致するものだけ採用する
- **パスワード**: URL 周辺の `パスワード：xxxx` / `合言葉：xxxx` / `参加コード：xxxx` を拾う
  （現行コーパスに実例ゼロのため**推定できなくても正常**。空欄で提示する）
- 推定は**あくまで初期値**で、確認画面で人が上書きできる。推定できなければ未指定のまま提示する

#### 3.2.5 配信

- 配信先は**既存の大会別 Bot グループ**（`event_line_broadcasts` で当該申込グループに紐付いた
  LINE グループ）1つ。**級別に LINE グループを分けない**
- メッセージは **Flex 1通のみ**（リード文テキストは送らない）
  - バブル内のテキストは**「大会オープンチャット」と大会名（申込グループの導出表示名）の2つだけ**。
    説明文・注意書き・利用案内の類を**置かない**（design-spec の宿題4。ボタンを見れば用途は自明で、
    文が増えるほどボタンが下へ押し出されるため）
  - 本文 = 保存済みオープンチャットのボタンを**縦に並べる**。ボタン名 = 表示ラベル
  - パスワードがある行は、ボタンの直下に小さく「パスワード: xxxx」を表示する
  - 各ボタンは `uri` アクションでオープンチャット参加画面を開く（URL 文字列はトークに露出しない）
  - `altText` は「オープンチャットのご案内／<大会名>」（400 字上限で切り詰め）
- **再配信は毎回全件を送る**。2回目以降は「すでに N 回配信済みです。全 M 件を改めて送ります」の
  確認ダイアログを出す。ダイアログには**送る全件のラベルを列挙し、前回の配信以降に増えた行に
  「（今回追加）」を付ける**（design-spec の宿題3）
- 配信の記録は**オープンチャット専用の記録先**に持つ。既存 `event_broadcast_messages` は
  「1メール = 1配信」を DB 制約で強制しており再配信と両立しないため使わない（§6 の契約）
- LINE 未紐付けのグループでは配信できない。**保存だけ行い**「LINE グループ未紐付けのため配信しません」と伝える
- 配信の失敗（LINE API エラー等）は保存をロールバックしない。保存は成功・配信は失敗として記録し、再試行できる

#### 3.2.6 閲覧

- 大会詳細画面に保存済みオープンチャット欄を出す。**一般会員にも表示**し、タップで参加画面へ遷移できる
- 表示のみ。**追加・編集・削除はメール詳細の抽出フローからのみ**行う
- **開催日で絞り込まない**。グループに属する全行を、どの開催日の詳細を開いても同じ順序で表示する
  （6/21 の詳細でも 6/20 対象の行が見える）。対象日はラベルに出るので取り違えは起きず、
  「別の日のオプチャが見つからない」事故を防ぐ方を優先する
- **保存済みが0件のときは、見出しごと表示しない**（design-spec の宿題2）。「未設定」と出すと会員に
  「運営が忘れている」と読ませるが、実際は主催者がまだ配っていないだけのことが多い
- 並び順は Flex のボタンと**同一**にする（LINE を見逃した会員が記憶と同じ順序で辿れるようにする）

#### 3.2.7 権限

- 抽出・保存・配信: **admin / vice_admin**（既存 `requireAdminSession()` を踏襲）
- 閲覧（大会詳細）: ログイン済みの全会員

#### 3.2.8 エラー・境界条件

| ケース | 挙動 |
|---|---|
| 対象の大会（申込グループ）未選択で抽出 | ボタンを押せない（無効化） |
| 抽出候補ゼロ | 「見つかりませんでした」＋手入力行の追加を促す |
| URL 欄が空のまま保存 | バリデーションエラー（保存しない） |
| `https://` 以外のスキーム | 拒否する（LINE Flex の `uri` は https 必須） |
| 同一 URL を2行に入れて保存 | 保存時に重複を弾く（同一グループ内で URL は一意） |
| 最終ラベルが重複する行がある | 保存できない。重複行に「ラベルを入力してください」を表示 |
| 対象開催日にグループ外の日を指定 | 拒否する |
| 添付が破損して抽出に失敗 | その添付だけスキップし、他の候補で続行する |
| 配信中に LINE 紐付けが解除された | 配信を中止し `binding_changed` として扱う（既存 `broadcastMailToEvent` の規約に合わせる） |

## 5. Non-goals

**機能面**

- **メール受信時の自動検知・自動配信**（§1 の実測結果により不採用）
- **AI（Claude API）による抽出**。URL 非存在ケースと「出場するか否か」は AI でも解けないため価値が薄い
- 級別に LINE グループを分ける配信（`line_grade_group_bindings` は使わない。現行0件の未運用機能）
- 短縮 URL のサーバー側展開・リダイレクト追跡
- LINE 公式アカウント内にしか URL が無いケースの自動取得（手入力で救う）
- オープンチャットへの入室状況の把握・未入室者への催促
- 大会詳細画面からのオープンチャット編集（表示のみ）
- 抽出候補の履歴保存・やり直し UI
- メール取込パイプライン（IMAP・分類・添付抽出）自体の変更

**技術面**

- `mail_messages` / `mail_attachments` のスキーマ変更
- 既存 `broadcastMailToEvent`（本文・添付の配信）の挙動変更
- XLSX 添付からの抽出（既存方針どおり `unsupported` のまま）
- QR 生成（読み取りのみ）

## 6. 技術的制約・契約

**壊してはいけない既存挙動**

- `MailProcessForm` の既存フロー（種別選択 → 大会選択 → 名簿採用 → LINE 配信 → 実行）はそのまま動く
- `broadcastMailToEvent` の冪等性（`UNIQUE(eventLineBroadcastId, mailMessageId)`）と送達カウンタ
- ★**オープンチャット配信は `event_broadcast_messages` に記録しない**（契約）。同テーブルの
  `UNIQUE(eventLineBroadcastId, mailMessageId)` は「1メール = 1配信」を DB レベルで強制するため、
  §3.2.5 の「再配信は毎回全件」と原理的に両立しない。同じメールからの2回目の配信が
  **DB 制約違反で失敗する**。オープンチャット配信は**独自の記録先**を持つこと。
  この UNIQUE 制約を緩める解決は禁止する — メール配信の冪等性は本機能と無関係に守られなければならない
- `event_line_broadcasts` のライフサイクル（`invite_pending → joined_waiting_code → linked → revoked/released`）
  と自動解放バッチ
- `line-flex-attachment.ts` は **pure（node builtins にも依存しない）** 制約を持つ。
  Flex 構築を同種のモジュールに置く場合は sharp / libreoffice 等の重依存を持ち込まない
- `process-candidate-utils.ts` / `roster-adopt-utils.ts` は client バンドルに DB 依存を漏らさない
  **leaf** 制約を持つ。抽出結果の型を client 側で使う場合も同じ制約を守る

**保持すべきデータ・移行**

- 新テーブル追加 + migration が必要（既存テーブルの破壊的変更はしない）
- 既存の openchat データは存在しない（全文検索で0件）。移行不要

**セキュリティ・権限**

- Server Action は冒頭で `requireAdminSession()`（admin / vice_admin）
- 大会詳細の閲覧は `session.user.id` の有無で判定（既存の申込ボード等と同じ境界）
- QR デコードは**信頼できない添付バイト列**を入力に取る。ページ画像化は既存の
  `pdftoppm` / `libreoffice` 経路（同じ信頼プロファイル）を通し、デコーダは
  ネイティブビルド不要のもの（純 JS / wasm）を選ぶ
- 抽出した URL は外部へ送信しない（短縮 URL の展開をしないのはこの制約とも整合する）

**利用技術上の制約**

- LINE Flex の `uri` アクションは **https 必須**
- `altText` は 400 字上限。切り詰めはコードポイント境界で行う（既存 `truncateToUtf16Units` を踏襲）
- LINE push は 5 メッセージ/バッチ・バッチ間 1.5 秒 sleep・429 は `Retry-After` に従い最大3回リトライ
  （既存 `line-broadcast.ts` の規約を再利用する）
- データ変更後は該当パスの `revalidatePath()`

**未解決の技術論点（技術計画フェーズで解決する）**

- 独自の配信記録の**形**（別テーブルにするか、申込グループ側に配信回数・最終配信日時を持つか）。
  **`event_broadcast_messages` を使わないことは §6 で確定済み**で、ここで決めるのは形だけ
- QR デコードライブラリの選定（`jsQR` / `zxing-wasm` 等）と、PDF ページ画像化のキャッシュ再利用可否
- 抽出候補シートを既存 `AIExtractConfirmDialog` の型に寄せるか、独立コンポーネントにするか

## 7. 設計判断の根拠

| 判断 | 理由 |
|---|---|
| 自動検知でなく人間トリガー | 当会と無関係なメールが93%。大会紐付けは人間しか決められず、その操作は既に存在する |
| AI を使わない | URL 非存在・出場可否は AI でも解けない。決定的抽出＋人の確認で 100% にできる |
| 保存単位を `entry_groups` に | LINE 紐付けが `entry_group_id` UNIQUE。同じ単位に揃えると「どの日の詳細から操作しても同じ」になる |
| 級・日付の2属性＋自由ラベル | 実データの分かれ方は級別・開催日別・部門別の3種。前2つは構造化し、3つ目はラベルで吸収する |
| 級別に LINE グループを分けない | 大会単位でグループを作る現行運用に合わせる。`line_grade_group_bindings` は0件で未運用 |
| Flex 1バブル・ボタン縦並び | carousel はスワイプしないと他の級に気づかない。1通で全体像が見える形を優先 |
| 短縮 URL を展開しない | 外部 HTTP 依存・タイムアウト処理が増える割に、管理者が自分で踏めば済む |
| 再配信は毎回全件 | 受け手が常に最新の全体像を受け取れる。差分配信は「前に何が送られたか」を受け手が覚えている前提になる |
| 大会詳細は全会員に表示 | LINE を見逃した会員の救済。招待制の身内アプリで、閲覧できるのは会員のみ |
| パスワードも自動抽出を試みる | 実例0件だが、抽出できれば手入力の手間が消える。推定できなくても正常動作する設計にする |

## デザインへの宿題（→ /design-screen openchat-broadcast）

1. **抽出候補シートのレイアウト** — 1候補あたり URL・出典バッジ・級チップ・開催日・ラベル・
   パスワードと項目が多い。375px でどう畳むか（候補が5件並ぶ実例あり＝中学生選手権）
2. **「未検証」短縮 URL の見せ方** — 危険ではないが確度が違うことを、警告色を使わずに伝える
3. **出典バッジ**（本文 / 添付 / QR / 手入力）の表現。既存の添付バッジ（PDF赤・Word青）との整合
4. **候補ゼロ時の空状態**と手入力行の追加導線
5. **Flex バブルの実寸デザイン** — 見出し・ボタン縦並び・パスワード行。LINE の Flex は
   Tailwind トークンが使えないため色を直接指定する必要がある（既存 `line-flex-attachment.ts` と同じ流儀）
6. **パスワードのコピー可否** — LINE Flex にクリップボードアクションは無い。長押しコピーできる
   テキストとして置くか、参加画面へ遷移した先で手入力してもらう前提にするか
7. **大会詳細のオープンチャット欄** — `design-mock/redesign.html` に `SCOPE-OUT` 付きの UI 案が
   既にある（級ごとの表・`.ocurl`）。今回の「級＋日付＋自由ラベル」モデルに合わせて更新する
8. **再配信の確認ダイアログ**の文言と、配信済み回数の見せ方
