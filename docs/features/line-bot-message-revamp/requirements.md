# 大会別LINE Bot メッセージ改訂 要件定義書

改修モード（delta）＋新規機能。大会別 Bot（プール30個・申込グループ単位で紐付け）が送る
メッセージ群を全面的に書き換え、あわせて**会計へのメンション**と**名簿確定後の振込連絡**を新設する。

## 1. 概要

### 目的

大会別 Bot の連絡を、会員が読んで即座に行動できる文面へ揃える。あわせて、これまで
口頭・手動で流していた「会計への振込依頼」を Bot 経由に載せる。

### 背景

現行の全メッセージを棚卸ししたところ（2026-08-22）、以下が分かった。

- 文面が `✅【大阪A】への参加申込が完了しました。` のように**大会名を毎回名乗る**が、
  宛先は1グループ＝1大会なので冗長
- 参加費の金額を通知に載せているが、実際に金額を知りたいのは**会計だけ**で、
  参加者全員に流す必要がない
- **会計への振込依頼が自動化されていない**。E-2（申込完了時の2通目）は
  申込時点の振込情報を流すが、実際に振り込むのは**名簿確定後**（当選者が確定してから）
- 「会計」という属性を景虎が持っていないため、誰に向けた連絡かを名指しできない

### この文書の位置づけ（★重要）

**文面そのものの正典は、その通知を所有する既存機能の要件定義書にある。** ここには重複して書かない。

| メッセージ | 正典 |
|---|---|
| A-1（join時ガイダンス廃止）・A-3（紐付け完了→①〜④に分割） | [event-line-broadcast/requirements.md](../event-line-broadcast/requirements.md) §3.1.3 |
| E-1（申込完了）・E-3（支払完了）・F-1〜F-6（日次リマインド） | [event-lifecycle-notify/requirements.md](../event-lifecycle-notify/requirements.md) §3.2.1 |
| E-2（会計向け2通目） | [entry-notify-lottery-treasurer/requirements.md](../entry-notify-lottery-treasurer/requirements.md) §3.2.3 |

**この文書が所有するのは次の3つだけ**: 会計フラグ / メンション送信基盤 / 名簿確定後の振込連絡。

## 2. ユーザーストーリー

- **会計担当**: 名簿が確定したら「誰の分をいくら、いつまでに、どこへ振り込むか」が
  LINE に届き、自分がメンションされるので見落とさない
- **管理者**: 抽選結果を見て人数を直してから送れる。全自動で誤った金額が流れない
- **一般会員**: 大会グループの連絡が短く、自分が何をすべきかだけが書かれている

## 3. 機能要件

### 3.1 会計フラグ

#### 3.1.1 データ

`users.is_treasurer`（boolean・NOT NULL・default false）を追加する。

**ロール（`user_role` enum）は変更しない。** 会計の権限は既存の副管理者と同じなので、
会計担当には `role='vice_admin'` を付与して運用する。`is_treasurer` は
**「@会計 で誰をメンションするか」の識別にのみ使い、認可判断には一切使わない**。

> なぜロールを増やさないか: `role !== 'admin' && role !== 'vice_admin'` の判定が
> **43ファイル・58箇所にインライン展開**されており、enum 値を増やすと全箇所の改修が要る。
> 権限が副管理者と同一である以上、増やす利益がない。→ §7

#### 3.1.2 画面

- 会員編集（`/admin/members/[id]/edit`）に「会計」トグルを追加する。既存のロール選択と同じ節に置く
- 会員一覧（`/admin/members`）で会計に印を出す
- 更新できるのは `admin` / `vice_admin`（会員編集の既存ガードのまま）

#### 3.1.3 メンション対象の解決

`@会計` は次の条件を満たす会員**全員**をメンションする。

```
is_treasurer = true AND line_user_id IS NOT NULL AND deactivated_at IS NULL
```

- 並び順は `users.id` 昇順（決定的にする）
- **0人のときは `@会計` を素テキストで出す**（メンションが付かないだけ。文面は崩さない）
- `line_user_id` が NULL の会計担当は黙って飛ばす（メンションされないだけで、行は出る）

`@管理者` も同じ規則で、条件が `role IN ('admin','vice_admin')` に変わるだけ。

### 3.2 メンション送信基盤

#### 3.2.1 仕組み

LINE Messaging API の `textV2` メッセージ型を使う。`substitution` の中で
プレースホルダをメンションへ差し替える。

```json
{ "type": "textV2",
  "text": "{everyone}\n大会の申し込み締め切りは…",
  "substitution": { "everyone": { "type": "mention", "mentionee": { "type": "all" } } } }
```

- 全体メンション（@All）は `mentionee.type = "all"`。userId は要らない
- 個人メンションは `mentionee.type = "user"` ＋ `userId`
- `userId` は **`users.line_user_id` をそのまま使う**。イベント用 Bot チャネル30個と
  LINE ログイン用チャネルは**同一プロバイダー**なので値が一致する（2026-08-22 ユーザー確認）
- `substitution` は1メッセージあたり最大100オブジェクト。**ただしメンションはそれとは別に
  最大20件**という制約があるため、実装は厳しい側（20件）で切る（会計・管理者はいずれも数名の
  運用なので実際には到達しない）

#### 3.2.2 設計制約 ★

**メンションを含むメッセージに、自由記述の文字列を混ぜてはならない。**

`textV2` は本文中の中括弧をプレースホルダ構文として解釈するため、ユーザー入力
（大会名・支払情報など）が中括弧を含むと壊れる。これを構造的に避けるため:

- メンションを含むメッセージの動的部分は、**日付・人数・金額といった数値由来の文字列に限る**
- 自由記述（`payment_info` など）は、メンションを持たない従来の `type:'text'` で別メッセージにする

この制約は振込連絡が2通に分かれている理由でもある（1通目＝メンション＋数値のみ、2通目＝口座情報の自由記述）。

### 3.3 名簿確定後の振込連絡（新規）

#### 3.3.1 導線

導線は**2つ**ある。どちらも同じ文面・同じ送信記録（`entry_group_payment_notices`）を共有する。

1. **申込グループページ**（`/admin/entries/[groupId]`）の「振込連絡を送る」— 名簿確定後にいつでも送れる恒久導線
2. **メール処理画面**（`/admin/mail-inbox/mail/[id]`）の「会計へ振込連絡を送る」— 確定名簿メールを処理する流れの中で、そのまま送る導線（§3.3.5）

以下 §3.3.1〜§3.3.4 は 1（グループページ）の規則。2 の差分は §3.3.5 にまとめる。

**出現条件**: そのグループが**名簿確定フェーズにある**とき。すなわち
[confirmed-roster.ts](../../../apps/web/src/lib/events/confirmed-roster.ts) の
`settled = true` かつ 事前払い（`payment_type='advance'`）かつ未振込（`payment_status='unpaid'`）。
これは申込管理ボードの `payment_due` 区画と同じ条件で、手動トグル
（`entry_groups.confirmed_roster_override`）で進めた場合も含む。

現地払い・支払済のグループはこの条件に入らないので、ボタンは出ない（振込が不要なため）。

#### 3.3.2 プレビューと編集

送信前に必ずプレビューを出す。**全自動送信はしない。**

- 級ごとの人数の初期値は、既存の参加費集計と同じ母集団から引く
  （[entry-fee-tally.ts](../../../apps/web/src/lib/entry-fee-tally.ts)。出欠回答「参加」・
  `is_invited`・`eligible_grades` 該当・**ゲスト除外**・複数日は延べ人数）。
  ★ただし対象の日は **§3.3.1 の露出条件を満たす日（申込済 ∧ 事前払い ∧ 未振込）だけ**に絞る。
  グループ全日を合算する `tallyEntryFeesForGroup` は支払済みの日を除外しないので、
  日ごとに支払済みトグルを進めたグループでは**二重請求**になる（2026-08-22 レビュー指摘）。
  振込期限・支払情報も同じ集合から採り、開催日昇順で決定的に1つを選ぶ
- **単価が解決できる対象級は、人数0でも入力欄として出す。** 出欠回答が0人の級を落とすと
  入力欄自体が消え、「集計の母集団は確定名簿ではないから人数を人間が直す」というこの機能の
  目的が果たせない級が出る（文面側は人数0の級の行を出さないので、送信結果は変わらない）
- 管理者は**級ごとの人数だけ**を直せる。**単価は直せない**
  （単価は協会規定額から `resolveEntryFee` が導出する値であり、管理者が上書きしてよい種類の数字ではない）
- 直した人数は保存し、**再送時に同じ数字を再現する**

> **既知の制限（2026-08-22 レビューで確認のうえ受容）**: 一度送信した後にグループ内の1日だけを
> 支払済み・中止にすると、対象の日は減るのに保存済みの人数がそのまま初期値として復元される。
> 支払状態はグループ単位で揃えて運用する前提に立ち、送信前のプレビューで人間が金額を確認する
> 設計なのでこのまま据え置く。振込期限と支払情報も、未振込の日の間で値が食い違う場合は
> それぞれ別の日から選ばれうる（共通項目はグループ全日へ伝播されるため通常は一致する）。

> なぜ人数を手で直せる必要があるか: 集計の母集団は「出欠回答で参加」であって
> 確定名簿ではない。抽選のある大会では落選者が混ざる。さらに確定名簿が
> 添付ゼロの本文だけで届くケースが実在し（Issue #509 の杉並AB）、
> 当選者を機械的に数えられない大会がある。→ §7

#### 3.3.3 文面

**1通目**（メンションあり・数値のみ）:

```
@会計
7/25(金)までに
A級：2500*3 = 7500円、
B級：2500*2 = 5000円

計12500円

を、以下の口座に振り込んでください
```

- 1行目は `@会計`（§3.1.3 の規則でメンション）
- 2行目の日付は `payment_deadline` を `M/D(曜)` 形式で。**`payment_deadline` が NULL なら
  この行ごと省略する**
- 級ごとに1行。`{単価}*{人数} = {小計}円`。人数0の級は行を出さない
- 級の並びは A→E 順
- 明細と `計` の間、`計` と末尾行の間に空行を1つ置く

**2通目**（自由記述・メンションなし）: 支払情報（`payment_info`）をそのまま送る。
**`payment_info` が空なら2通目を送らない**（1通目だけで完結させる）。

#### 3.3.4 送信と再送

- 送信は**手動のみ**。once-ever ではなく**再送できる**（要綱再送・オープンチャット再送と同じ扱い）
- 送信済みかどうか・最後に送った日時を画面に出す
- 紐付けが無いグループではボタンを出さない（送りようがない）

#### 3.3.5 メール処理画面からの振込連絡（2026-09-04 追加）

##### 3.3.5.1 導線と露出条件

メール詳細 `/admin/mail-inbox/mail/[id]` の処理フォーム（`MailProcessForm`。種別 → 対象グループ →
添付採用 → LINE 配信を1フォームに集約したもの）に「**会計へ振込連絡を送る**」セクションを追加する。

セクションを描く条件は次の2つだけ:

- 種別が**確定名簿**（`mailKind='confirmed_roster'`）
- 対象の申込グループが選択済み

★**`settled`（確定名簿あり）は条件に入れない。** この画面での処理そのものが
`mail_kind='confirmed_roster'` ∧ `triage_status='processed'` を書き、
[confirmed-roster.ts](../../../apps/web/src/lib/events/confirmed-roster.ts) のシグナル③を成立させる。
つまり実行後は必ず `settled=true` になるので、§3.3.1 の露出条件から `settled` の項が落ち、
残りの条件（事前払い・未振込・LINE 紐付け）だけを見る形になる。
**添付を1件も採用しない確定連絡メール**（本文だけで確定を伝える Issue #509 の杉並AB型）でも同じく出る。

##### 3.3.5.2 送信できない理由を出す

対象日が無いときも**セクション自体は出し、送信だけを不可にして理由を1行で示す**。黙って消さない
（確定名簿が来ているのにセクションが現れない理由が分からず詰まるのを防ぐ）。

判定は非中止の日だけを見て、上から順に最初に当たったものを理由とする:

| 状況 | 表示 |
|---|---|
| 申込済（`entry_status='applied'`）の日が1つも無い | まだ申込済みになっていません |
| 申込済の日はあるが、すべて現地払い | 現地払いのため振込は不要です |
| 申込済 ∧ 事前払いの日はあるが、すべて支払済み | 支払済みです |
| LINE グループが紐付いていない | LINE グループが紐付いていません |
| 単価を解決できる級が1つも無い | 参加費を算出できる級がありません（非公認・団体戦のみ） |

`entry_status` を自動で `applied` へ倒すことはしない（confirmed-roster-signal の Non-goal を維持）。

##### 3.3.5.3 振込期限・振込先をその場で入力する

確定名簿メールを処理する時点では、振込期限・振込先がまだ埋まっていないことがある
（杉並AB は `payment_deadline=NULL`）。空のままだと1通目の日付行が消え、振込先の2通目も送られず、
連絡として成立しない。そこでセクション内に次の2項目を置く:

- **支払締切**: 日付 ＋ 状態セレクト（`fixed` / `later_notice` / `unspecified`）。既存の共通項目編集
  （`CommonFieldsSection`）と同じ形
- **振込先**: 複数行テキスト

初期値はグループの共通項目から採る（代表値の取り方は §3.3.2 と同じ＝未振込の日から開催日昇順で決定的に1つ）。
編集して送信すると、**グループ内の全日へ保存される**（`propagateFieldsToGroup` を通す。対象は
既存の共通項目一括保存 `saveGroupCommonFields` と同じく**中止の日も含むグループ内の全イベント**。
伝播規則を2種類に分けない）。
グループページの「振込先」行・締切バッジ・会員向け表示にも反映されるので、同じ値を二度入力しない。

- **振込先は必須**。空のままでは送信できない（2通目が送られず、`以下の口座に振り込んでください` だけが届くため）
- **支払締切は任意**。「後日連絡」「未定」は実在する状態なので、空でも送れる（1通目の日付行が消えるだけ・§3.3.3）
- ★**共通項目の保存は送信可否と切り離す。** セクションが描かれている限り、支払締切・振込先は
  チェックの ON/OFF によらず保存する（ゲートが掛かるのは push だけ）。
  「振込先を入力したあとで、送るのはやめておこうとチェックを外したら入力が黙って消え、
  グループページからも送れないまま」という**この機能が無くそうとしている状態**を作らないため。
  送信チェックを OFF にしたときはセクションの中身を畳むが、入力済みの値は保存される
- **振込先が必須なのは送信するとき（チェック ON）だけ**。OFF のときは空のままでも実行できる
  （保存されるのも空のまま）

##### 3.3.5.4 人数の確認・訂正

グループページの `PaymentNoticeSection` と**同じ形**にする。級ごとの人数だけ編集可・単価は編集不可・
単価が解決できる級は人数0でも入力欄を出す・送信文面のプレビューを常時表示（§3.3.2 の規則をそのまま適用）。

初期値の母集団も同一で、**未振込の日だけ**を合算する（§3.3.2 の二重請求ガードを引き継ぐ）。
このためメール画面は独自のローダーを持たず、`payment-notice-context.ts` を共有する（§6）。

##### 3.3.5.5 既定値と再送

- そのグループへまだ振込連絡を送っていない → チェックは**既定 ON**（何もしなければ送られる）
- 既に送信済み → 「送信済 M/D HH:mm」を表示し、チェックは**既定 OFF**。ON にすれば再送する
  （訂正名簿・級別分割で確定名簿メールが2通目・3通目と届くのは日常的なため、意図したときだけ再送する）
- 送信記録は `entry_group_payment_notices`（`entry_group_id` ごと1行）を**グループページと共有する**。
  この画面から送るとグループページの「送信済」表示も同じ値を指す

##### 3.3.5.6 送信のタイミングと失敗の扱い

- 採用・triage の**トランザクションがコミットした後**に送る。push の失敗で採用がロールバックされることはない
- LINE 配信（会員向けに本文・添付を流す既存機能）も ON のときは、**配信 → 振込連絡**の順で送る。
  会員が当落を見た後に会計へ振込依頼が届く順序にする
- 両方とも応答後の `after()` で走り、既存の**世代トークン検証**（`triaged_at` の一致判定。取り消し →
  再処理を跨いだ誤配信を防ぐ）を共有する。取り消されたメールからは振込連絡も送られない
- 応答を待たずに走る以上、失敗を戻り値で返せない。加えて **`processMail` の実行成功後は
  メール一覧へ戻る**（mail-inbox-mailer §3.1.4）ので、そもそも実行画面にエラーを出す場所がない。
  したがって**失敗は `entry_group_payment_notices` に記録し**（最終試行日時と理由）、
  次の2箇所に「送信に失敗しました（M/D HH:mm）」として出す:
  1. 申込グループページの振込連絡セクション（既存。ここから再送できる）
  2. メール詳細の「処理済み」カード（mail-inbox-mailer §3.1.3 の (C)。そのメールへ戻れば分かる）

  `last_sent_at` は成功時だけ進むので、再送できる状態のまま残る
  （オープンチャット配信の `lastAttempt` と同じ規律）
- **送信に成功したら失敗記録をクリアする**（`last_error` を NULL に戻す）。残したままだと
  「送信済」と「送信に失敗しました」が同時に出る
- 人数・支払締切・振込先は push の**前に**保存する（送信が失敗しても入力し直させない）

### 3.4 ビジネスルール・エラーケース

| 状況 | 挙動 |
|---|---|
| 会計フラグが0人 | `@会計` を素テキストで送る（メンションなし）。送信自体は行う |
| 会計に `line_user_id` が無い | その人だけメンションから外す。行は出る |
| `payment_deadline` が NULL | 1通目の日付行を省略 |
| `payment_info` が空 | 2通目を送らない |
| 人数が全級0 | 送信させない（プレビューでエラー表示） |
| 単価が解決できない級（非公認・団体戦） | 明細から除外する（既存の総額計算と同じ規律） |
| LINE 紐付けが無い | ボタンを出さない |
| push 失敗 | 送信済みにしない。画面にエラーを出し、再送できる状態のまま残す |
| `payment_info` が LINE の1通上限（5000文字）超 | 分割して送る（push は1リクエスト5通までなので支払情報は最大4通。超過分は末尾を切って「…（以下省略）」を付ける） |
| メール処理画面で振込先が空 | **送信するとき（チェック ON）だけ**送信させない（入力を促す。§3.3.5.3）。OFF なら空のまま実行できる |

| メール処理画面で push 失敗 | 採用・triage はコミット済みのまま。`last_sent_at` を進めず失敗を記録し、両画面に出す（§3.3.5.6） |

## 6. 技術的制約・契約

- **認可判断に `is_treasurer` を使わない。** 権限は既存 role のまま。この列を
  `role !== 'admin'` 系の判定へ混ぜてはならない
- **メンションを含むメッセージに自由記述を混ぜない**（§3.2.2）
- `users.line_user_id` を `mentionee.userId` として使えるのは、Bot チャネルと
  ログインチャネルが同一プロバイダーである前提に依存する。プロバイダーを分ける
  変更を将来行う場合、この前提が壊れる
- 参加費の単価解決は [entry-fee.ts](../../../apps/web/src/lib/entry-fee.ts) の
  `resolveEntryFee` に委ねる。級→金額の分岐をここで再定義しない
- 「確定名簿あり」の判定は [confirmed-roster.ts](../../../apps/web/src/lib/events/confirmed-roster.ts) が正典。
  4材料の OR をここで再実装しない
- **LINE が 400（メッセージ内容の不備）を返しても LINE グループの紐付けを解除しない。**
  従来は 429 以外の 4xx をすべて「宛先が無効」とみなして紐付けを revoke していたが、
  `textV2` の導入でペイロード起因の 400 が起こりうるようになった。宛先と無関係な不備で
  正常な紐付けを壊すと、その大会の通知が以後すべて止まる。解除対象は 401（トークン失効）と
  403 / 404（Bot 追放・宛先消失）だけにする（2026-08-22 レビュー指摘）
- 既存の push 実装（`line-broadcast.ts` ほか5モジュール）は、重依存を避けるため
  意図的に共通化されていない。メンション基盤は **pure モジュール**として作り、
  sharp / libreoffice / `@kagetra/shared` を持ち込まない
  （`line-flex-attachment.ts` と同じ流儀）

2026-09-04 改修（§3.3.5）で追加する制約:

- **露出条件と初期値の組み立ては [payment-notice-context.ts](../../../apps/web/src/lib/events/payment-notice-context.ts) を共有する。**
  メール画面用に別のローダーを書かない。あちらには「母集団は `dueDays`（未振込の日）だけで、
  `tallyEntryFeesForGroup` を使うと支払済みの日まで載って二重請求になる」というレビューで得た規律が
  埋まっており、書き直すとその不具合が静かに戻る。`settled` の判定だけを外せる入口を足す形にする
- **プレビューは pure な [payment-notice.ts](../../../apps/web/src/lib/payment-notice.ts) だけを client から import する。**
  `server-only` / `@kagetra/shared/schema` / `drizzle-orm` の値 import（型 import も含む）を client 経路へ
  持ち込まない。これは eslint / vitest / check-types のどれでも検知できず `next build` で初めて壊れる
  （`roster-adopt-utils.ts` 冒頭に同じ注意書きがある既知の罠）
- 支払締切の書き込みは `normalizePaymentDeadline` を経由し、`payment_deadline` と
  `payment_deadline_kind` を**同一 UPDATE で揃えて書く**（CHECK 制約
  `(payment_deadline IS NOT NULL) = (kind = 'fixed')`）
- Server Action は client から直接叩けるので、画面が出していない状況で送られないよう
  露出条件をサーバー側で再判定する（fail-closed。グループページ側の既存規律と同じ）
- 振込連絡の push は `processMail` の `after()` 内で既存の**世代トークン検証**
  （`isCurrentGeneration`）を共有する。独自の取り消し検知を書かない
- 失敗記録の列追加は `entry_group_payment_notices` への非破壊 ALTER（マイグレーション1本）

## 7. 設計判断の根拠

1. **ロールを増やさず boolean 1列**: 権限判定が58箇所にインライン展開されているため、
   enum 値の追加は全箇所の改修と回帰リスクを伴う。権限が副管理者と同一なら増やす利益がない
2. **振込連絡を名簿確定後に置いた**: 申込時点では当選者が決まっておらず、金額が確定しない。
   E-2 は「名簿確定時に連絡します」と予告するだけに留める
3. **プレビュー必須・人数のみ編集可**: 集計母集団が確定名簿ではないこと、確定名簿が
   構造化データで残らない大会が実在すること（Issue #509）から、全自動は誤った金額を流す。
   一方で単価は協会規定なので、人間が触れる範囲を人数に限る
4. **2通に分けた**: textV2 の中括弧問題を構造的に回避するため。設計上の必然であって、
   読みやすさのための分割ではない
5. **文面の正典を既存機能側に置いた**: 同じ仕様が2箇所にあると片方だけ直したときに食い違う。
   この文書は索引に徹する
6. **メール処理画面では `settled` を露出条件に入れない**（2026-09-04）: 確定名簿メールの処理そのものが
   シグナル③を成立させるので、処理**前**の状態で `settled` を見ると必ず false になりセクションが永久に
   出ない。条件は「処理後にどうなるか」で組む
7. **振込期限・振込先をその場で入力できるようにした**（2026-09-04）: メール処理はフローの中で
   グループページより**早い**位置にあり、この時点では共通項目が未設定のことがある（杉並AB の
   `payment_deadline=NULL`）。空のまま送ると1通目の日付行も2通目の振込先も消え、連絡が成立しない。
   保存先をグループの共通項目にしたのは、同じ値を二度入力させないため
8. **順序（配信 → 振込連絡）を、送信エラーの即時表示より優先した**（2026-09-04）: 会員が当落を見る前に
   会計へ振込依頼が届くのは運用として不自然。既存の配信は本文の画像化で数十秒かかりうるため同期化できず、
   順序を守るなら振込連絡も `after()` へ載せるしかない。失敗の可視化は戻り値ではなく DB の試行記録で担う
   （オープンチャット配信が同じ理由で同じ形にしている）
9. **送信チェックの既定を「未送信=ON / 送信済=OFF」にした**（2026-09-04）: 初回は何もしなければ送られる
   のが自然だが、訂正名簿・級別分割で確定名簿メールが複数通届くのは日常なので、送信済みのグループへ
   既定 ON のまま実行すると意図しない再送が起きる
