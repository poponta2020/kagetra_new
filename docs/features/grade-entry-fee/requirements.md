# grade-entry-fee 要件定義書

## 1. 概要

公認大会の**級別参加料**（全日本かるた協会が定める規定額）をアプリ内の定数として保持し、
**それを画面と LINE 通知へ配線する**。

第1回（PR #392・出荷済み）で定数と参照関数を用意した。本改修はその表示側で、
`grade-entry-fee` 第1回の Non-goals に「表示に手を入れる回に決める」と明記して持ち越した論点をすべて確定させる。

**背景・動機**: 参加料は大会ごとの裁量ではなく協会が級別に定めており、実額は A・B / C・D / E の
3段階しかない（[reference](../../../.claude/memory/reference_karuta_entry_fee_by_grade.md)）。
現行スキーマは `events.fee_jpy`（integer 1本）のみで、**同日に複数級が開催されると級別金額を表現できない**。

**本改修に踏み切る決め手（本番実測 2026-07-30）**:

| 観測 | 数値 |
|---|---|
| `official=true` のイベント | 37件 |
| `fee_jpy` に値がある | 26件・**うち24件が AI ドラフト由来** |
| 2級以上をまたぐイベント | 14件（**料金帯をまたぐのが12件**） |
| `fee_jpy = 10,000` の行 | 4件・**全て `kind='team'`**（1チーム単価） |
| `payment_type` | NULL 31 / advance 7 / onsite 2 |

- **格納値は実際に誤っている**: id=1 `{A,B,C}`=2500 / id=3 `{A,B,C,D}`=2500（C・D級は本来2,000円）。
  スカラー1本では多級イベントを表現できない。どちらも過去日なのでデータ修正は不要。
- **供給が止まる**: [mail-ai-extract-refinements](../mail-ai-extract-refinements/requirements.md) #411 で
  AI の `fee_jpy` 抽出が廃止される（列は残す）。**今 `fee_jpy` を読んでいる箇所は放置すると金額が消える**。
  したがって本改修は「金額を足す」だけでなく「**金額が消えるのを防ぐ**」作業でもある。
- `payment_type` は AI が触らず、設定箇所は進行管理の select **1箇所だけ**でフォームに項目が無い。
  既定 NULL のまま放置され「参加費は基本前払い」という実運用と食い違っている。

## 2. ユーザーストーリー

- **一般会員**: 大会ページを開いたとき、**自分がいくら払うのか**を申し込む前に知りたい。
- **会計担当**: 支払締切が近づいたとき、**主催者へ振り込む総額**を LINE で受け取りたい。
  内訳（級ごとの人数×単価）も併せて見たい。抽選で落ちた人が出たら自分で引き算したい。
- **管理者 / 副管理者**: 進行管理で総額と内訳を確認し、支払済にしたときに正しい額が参加者へ通知されてほしい。

## 3. 機能要件

### 3.1 画面と遷移

新規画面・遷移の追加は**なし**。既存の `/events/[id]`（イベント詳細）に表示を足すのみ。
レイアウト・配色は動かさないため `design_required: false`。

| 位置 | 対象 | 内容 |
|---|---|---|
| 「参加者」セクション内に1行 | **一般会員含む全ロール** | `あなたの参加費 2,500円` |
| 進行管理 →「支払状態」トグル内（既存） | 管理者 / 副管理者のみ | 既存「参加費」行を導出値へ＋新規「振込総額」行 |

### 3.2 ビジネスルール

#### 3.2.1 単価の解決（すべての表示・通知の基礎）

```
official = true  かつ kind = 'individual' → 級別規定額を常に導出（events.fee_jpy は見ない）
それ以外（非公認 / kind = 'team'）        → events.fee_jpy をそのまま
```

- **`feeJpy ?? derived` ではない。** official 個人戦では格納値を一切参照しない。
  規定外の金額を手入力で表現する手段は無くなるが、公認大会に規定外は存在しないため許容（ユーザー確定）。
  副次的に、#410（AI 抽出廃止）との**出荷順序に依存しなくなる**。
- 対象となる級は `events.eligible_grades`。NULL / 空配列なら全級（A〜E）を対象とする。
- **同一単価の級はまとめる**（`A・B級 2,500円` / `C・D級 2,000円` / `E級 1,500円`）。並び順は A→E。
- 単価が1つに定まるイベントを「**単一料金**」、2つ以上になるものを「**多級**」と呼ぶ。

#### 3.2.2 総額と内訳

- **母集団** = 出欠で `attend = true` かつ `is_invited = true` かつ **対象級に合致**する会員。
  イベント詳細の参加者一覧（`eligibleAttendingList`）と**同一の集合**とし、画面の人数と通知の人数がずれないようにする。
- **級が未設定（`users.grade IS NULL`）の会員は総額に算入しない。** 0円として足さない。
  該当者がいれば `※級未設定 1名は未算入` を添える。
- 総額 = Σ(級ごとの人数 × その級の単価)。
- **団体戦・非公認では総額を出さない**（`kind='team'` は1チーム単価、非公認は規定外で人数×単価が成立しない）。
- **複数日グループでは日ごとに割らず、グループの全日を合算した1つの総額**とする。
  会計はグループ単位で一括請求されるため（ユーザー確定）。
  文面に並ぶ日付とは範囲が異なりうるので、必ず「**振込総額**」というラベルで示す。

#### 3.2.3 LINE 通知（変更するもの）

**支払締切リマインド** `payment_deadline_advance` / `payment_deadline_day` — 総額を載せる唯一の通知

```
⏰【春の大会ABC級】の参加費の支払締切は 6/10（あと 3 日）です。まだ支払いが完了していません。
振込総額 11,000円（A・B級 2名×2,500 / C級 3名×2,000）
※級未設定 1名は未算入
```

- 1行目は**現行文面のまま**。2行目以降を追加する。
- 総額が算出できない・0円のときは**追加行を出さない**（＝現行文面と完全に一致）。
- 級未設定者が0名なら3行目を出さない。
- 複数日バケットでも同じ形（1行目は既存の日別ラベル列挙、2行目はグループ全日の総額）。

**現地払い** `onsite_payment_advance` / `onsite_payment_day` — 単価が消えるのを防ぐ

- **単一料金は現行文面のまま**（バイト互換）: `💰【春の大会】は当日現地払いです。参加費 1,500円 を 6/20 当日お持ちください。`
- **多級のときだけ**級別表記: `…参加費 A・B級 2,500円 / C級 2,000円 を 6/20 当日お持ちください。`
- 単価が解決できないときは現行の金額省略分岐のまま。

**支払完了** `payment_paid` — 1人あたり額から**総額**へ意味を変える

- `✅【春の大会】の参加費（総額 11,000円）の支払いが完了しました。`
- 総額が算出できないときは現行どおり金額を省略。
- **複数日は現行どおり金額を出さない**（据え置き）。
- **総額の範囲は §3.2.2 と同じ「申込グループの全日」**（実装時に確定）。複数日グループの1日だけを
  支払済にした場合でもグループ全日の額を出す。1日ぶんに絞ると、同じグループの支払締切リマインドが
  既に伝えた「振込総額」と食い違い、どちらも once-ever で訂正できないため。

#### 3.2.4 LINE 通知（変更しないもの）★回帰の要

- **`entry_applied_treasurer`（💴会計の方へ）は一切変更しない。**
  [entry-notify-lottery-treasurer](../entry-notify-lottery-treasurer/requirements.md) §6.4 の
  「金額は載せない」というユーザー確定を維持する（今回の合計は支払締切リマインドのみ）。
- `entry_applied` / `entry_deadline_advance` / `entry_deadline_day` は変更しない。
- once-ever 保証・claim/finalize・push 失敗時のリカバリはすべて現行のまま。

#### 3.2.5 会員向け「あなたの参加費」

- 表示条件: `kind='individual'` **かつ** ログイン会員の級が設定済み **かつ** 対象級に含まれる。
  - `official=true` → 導出した規定額
  - `official=false` → `events.fee_jpy`（あれば。無ければ行を出さない）
- **`kind='team'` では出さない**（1チーム単価を個人の額と誤読させない）。
- **出欠の回答状況は問わない**（未回答・不参加でも表示する。申し込む前に金額を知りたいため＝ユーザー確定）。
- **「規定額」ラベルは付けない**（公認大会に規定額以外は存在せず、会員にとって区別の意味がない＝ユーザー確定）。

#### 3.2.6 `events.payment_type` の既定値変更

- 列の既定値を `NULL` → `'advance'` に変更し、**既存の NULL 31件を `'advance'` へ backfill** する
  （`'onsite'` 2件・`'advance'` 7件は据え置き）。
- **理由**: 参加費は基本前払いだが、`payment_type` の設定箇所は進行管理の select 1箇所だけで
  イベント作成・編集フォームに項目が無い。既定 NULL のため支払締切リマインドの発火条件
  （`payment_type='advance'` かつ未払かつ締切一致）を満たさず、**締切が入っているのに通知が黙る**。
- **今日の影響はゼロ**（NULL かつ締切ありの6件は全て過去日 or LINE 未紐付け＝実測）。
  **買うのは今後の挙動**: backfill 後の行や新規イベントに `payment_deadline` が入れば自動的に通知対象になる。
- 副作用として、既存31件の進行管理表示が「未設定」→「未払」に変わり「支払済にする」ボタンが出る。

### 3.3 権限

- 「あなたの参加費」= 全ロール（自分の級の額のみ。他人の額は見えない）。
- 総額・内訳の**画面表示**は `admin` / `vice_admin` のみ（既存の進行管理セクション内）。
- ただし**総額は LINE 参加者グループへ流れる**ため、そのグループの参加者全員が見る。
  会の内部会計情報であり、参加者一覧は元から全ロールに見えているため許容する。

## 5. Non-goals

**機能面**
- `entry_applied_treasurer`（会計向け申込完了通知）への金額追加 — 前回のユーザー確定を維持
- 支払締切リマインドの**発火条件そのもの**の変更（`payment_type='advance'` かつ未払かつ締切一致は維持。
  既定値変更で実質的に広がるが、条件式は触らない）
- 金額の再通知・訂正通知（once-ever を破る新種別の追加）
- 申込管理ボード（`/admin/entries`）への金額表示
- 申込書自動記入への金額配線（公式テンプレートに金額欄が無い）
- 公認料（300円・主催会→全日協の内数）
- 初段認定大会の独立キー化（E級と同値で扱う）
- 会員ごとの支払い状態管理（誰が会計に払ったか）— 現行どおり会レベルの1状態のみ

**技術面**
- `events.fee_jpy` 列の DROP（非公認・団体戦で現役。手入力の受け皿としても残す）
- 過去の誤った `fee_jpy`（id=1 / id=3）のデータ修正 — どちらも過去日で実害が無く、
  official 個人戦では常に導出するため参照されない
- `fee_jpy_a`..`fee_jpy_e` の列追加（第1回で却下済み）
- `eligible_grades` のスキーマ変更
- 通知文面の編集 UI（固定テンプレのまま）

## 6. 技術的制約・契約

- **導出はページ側（Server Component）で行い、`EventLifecycleSection` の既存 props 契約を変えない。**
  総額・内訳は**任意の新規 props**として足す（既存テストを壊さないため／AC-25）。
- 単価解決とグルーピング・整形は**純関数**として切り出し、DB アクセスと分離する
  （`buildLifecycleMessage` と画面の双方から使うため）。
- `buildLifecycleMessage` の既存 `feeJpy` 引数は**残す**。総額・級別単価は追加の任意フィールドで表現し、
  未指定なら現行の分岐にそのまま落ちる（AC-14 / AC-15 のバイト互換はこの設計で担保する）。
- 複数日リマインドの文面テンプレートは `send-lifecycle-reminders.ts` の `buildBucketMessage` が所有する
  （既存コメントの通り）。日別ラベルの整形規則は `event-lifecycle-notify.ts` の
  `sortDays` / `formatDaysLabel` を引き続き共有し、二重定義しない。
- `eligible_grades` は PostgreSQL の enum 配列。Drizzle の raw SQL で渡すときは `ANY(ARRAY[...])` 形式にし、
  **空配列は early-return** する（[feedback](../../../.claude/memory/feedback_drizzle_sql_int_array_binding.md)）。
- マイグレーションは1本（`payment_type` の DEFAULT 変更＋backfill）。番号は実装時に journal の最新を再確認する。
  **backfill を DEFAULT 変更と同じ migration 内で行う**。本番反映は `db:migrate`（`drizzle-kit push` は対話プロンプトで詰む）。
- 既存の公開 HTTP エンドポイント・webhook・systemd / cron の追加は無い。
- **`events.fee_jpy` のセマンティクスは変えない**（「案内に書いてある実額」のまま）。
  official 個人戦で参照しなくなるだけで、列の意味も既存値も書き換えない。

### 破壊的変更（ルール5・承認事項）

1. **既存データの書き換え**: `events.payment_type` の NULL 31件を `'advance'` へ backfill。
2. **既存テストの更新**: `event-lifecycle-notify.test.ts` の `payment_paid` 2件
   （`参加費（1,000円）` → 総額表記）。`onsite_payment_*` と `payment_deadline_*` の既存アサーションは
   バイト互換を保つため**変更しない**（そのまま回帰テストとして機能する）。
3. **既存イベントの見え方**: backfill した31件で支払状態が「未設定」→「未払」に変わり
   「支払済にする」ボタンが出る。

## 7. 設計判断の根拠

- **`??` ではなく「official 個人戦は常に導出」**: 本番で値が入っている26件中24件が AI 由来で、
  その供給が #411 で止まる。残るのは legacy ノイズであり、多級では実際に誤っている。
  常に導出なら #410 との出荷順序に依存せず、判定も「official か個人戦か」の2条件で読みやすい。
- **総額を載せるのは支払締切リマインドだけ**: 申込完了時（`entry_applied_treasurer`）は抽選前で
  額が確定せず、once-ever のため訂正もできない。支払締切リマインドは抽選後に飛ぶことが多く、
  実際に振り込む額とほぼ一致する。前回の「金額は載せない」決定とも矛盾しない。
- **内訳を併記する**: once-ever で訂正できない以上、数字の出どころが見えることが唯一の救済になる。
  落選が出ても会計が自分で引き算できる。
- **母集団を参加者一覧と同一にする**: 画面の人数と通知の人数が食い違うと、どちらが正か分からなくなる。
  通知発火時点では主催者の名簿がまだ届いていないため、出欠以外に選択肢が無いという事情もある。
- **級未設定を 0円で足さない**: `users.grade` は nullable。0円で足すと総額が静かに過少になる。
  除外＋注記なら会計が気付いて手当てできる。
- **団体戦を除外する**: 本番の `fee_jpy=10,000` 4件は全て団体戦の1チーム単価。
  特に `kind='team'` かつ `eligible_grades={E}` の行は、級で導出すると1,500円という大外しになる。
- **`payment_type` の既定を advance にする**: 「基本前払い」という実運用に対し、設定箇所が
  進行管理の select 1箇所しか無く既定 NULL のため、通知が黙る事故が構造的に起きる。
  発火条件を緩めるより既定値を実態に合わせる方が、既存の条件式を触らずに済む。
- **「規定額」ラベルを付けない**: 第1回の方向性メモでは付ける案だったが、公認大会に規定額以外は
  存在しないため会員にとって区別の意味がない。管理者向けには内訳（人数×単価）が根拠を示す。

## 8. 開発・テスト戦略

- **ユニット（Vitest）**: 単価解決・グルーピング・整形の純関数（AC-5〜8）／`buildLifecycleMessage` の
  全分岐（AC-13〜20。**バイト互換は既存アサーションを変更しないことで担保**）／総額算出（AC-9〜12）。
- **統合（Vitest + 実 DB）**: 母集団クエリが参加者一覧と一致すること（AC-9）／複数日グループの合算（AC-12）／
  マイグレーションの backfill（AC-26/27）。
- **フロント（Testing Library）**: 会員向け1行の表示・非表示条件（AC-21〜23）／進行管理の総額行（AC-24）／
  既存 props 契約の維持（AC-25）。
- **デプロイ**: migration（`db:migrate`）→ apps/web リビルド（`.next/static` + `public` のコピー忘れ注意）→
  `LINE_NOTIFY_DRY_RUN=1` で1グループぶん文面確認 → 本番。新規 systemd / cron なし。
  **列の変更を含むため、各 worktree のテスト DB は破棄して作り直す。**
