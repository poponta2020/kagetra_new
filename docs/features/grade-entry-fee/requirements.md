# grade-entry-fee 要件定義書

## 1. 概要

公認大会の**級別参加料**（全日本かるた協会が定める規定額）を、アプリ内の定数として保持する。
今回は**データを持つところまで**で、画面表示・通知・申込書自動記入への配線は行わない。

**背景・動機**: 参加料は大会ごとの裁量ではなく協会が級別に定めており、実額は A・B / C・D / E の
3段階しかない（[reference](../../../.claude/memory/reference_karuta_entry_fee_by_grade.md) / 一次資料 `C:/tmp/karuta-entry-fee.md`）。
現行スキーマは `events.fee_jpy`（integer 1本）のみで、同日に複数級が開催されると級別金額を表現できない。
列を増やすより定数＋参照に倒す方が、規定改定時の変更点が1箇所で済む。

なお公式の「公認大会統一申込書」テンプレートは級別**人数**を COUNTIF/SUM で集計するだけで、
単価も金額の計算式も持たない。金額を扱うならアプリ側が持つ必要がある。

## 2. ユーザーストーリー

- **対象**: 開発者（この機能に直接触れるエンドユーザーはいない）
- **目的**: 後続機能（会計向けの合計額算出、管理者向け表示など）が参照できる、出典の明確な級別金額を1箇所に用意する
- **シナリオ**: 消費側の実装時に `packages/shared` から import して級→金額を引く

## 3. 機能要件

### 3.1 画面と遷移

**なし。** UI 変更を一切伴わない（`design_required: false`）。

### 3.2 ビジネスルール

| 級 | 参加料 |
|---|---|
| A | 2,500円 |
| B | 2,500円 |
| C | 2,000円 |
| D | 2,000円 |
| E | 1,500円 |

- 出典: 全日協「公認大会の参加料・公認料の改正について」（2021-04-28 発出 / **2021-07-01 施行**）。
  会員ページ `member-document/2187` 添付 `member-download/2178`。2024-03 の「公認大会案内 見本」も同額。
- 初段認定大会（公認大会）も 1,500円 で、**E級と同じ値として扱う**。根拠は別通達（`member-download/3507`）
  なので、将来どちらか一方だけが改定されたら独立キーへ分ける。
- **級が不明（null）のときは金額を返さない**（既定値へフォールバックしない）。`users.grade` は nullable。

## 4. Acceptance Criteria

| ID | 条件 | 検証手段 |
|----|------|------|
| AC-1 | A→2500 / B→2500 / C→2000 / D→2000 / E→1500 を返す | auto-test |
| AC-2 | 級が null・undefined・未知の文字列のとき `null` を返す（0 や既定額を返さない） | auto-test |
| AC-3 | 定数テーブルは `Grade` 型に対して網羅的で、級を追加/削除すると型エラーになる | auto-test |
| AC-4 | `packages/shared` の公開エントリから import できる | auto-test |
| AC-5 | 既存テスト・lint・typecheck が CI で green（既存挙動に変更なし） | auto-test |

## 5. Non-goals

**機能面**
- 画面表示（イベント詳細・一覧・管理画面）への反映 — **今回は UI を一切変更しない**
- LINE 通知文面への反映
- 申込書自動記入への配線
- 会の合計振込額の算出
- 公認料（300円・主催会→全日協の内数）— 会員が払う額ではない
- 初段認定大会の独立キー化（E級と同値で扱う）

**技術面**
- DB マイグレーション（`fee_jpy_a`..`fee_jpy_e` の列追加は却下済み）
- `events.fee_jpy` のセマンティクス変更・既存データの書き換え
- `official` による導出/格納値の出し分け、`feeJpy ?? derived` の解決ロジック — すべて表示側の論点で、
  UI に手を入れる回に決める

## 6. 技術的制約・契約

- 置き場所は `packages/shared`（apps/web と apps/mail-worker の双方から参照しうるため）
- 既存の `Grade` 型（`packages/shared/src/types/index.ts:4`）を使う。新しい級の型を作らない
- 金額の出典（通達名・施行日 2021-07-01・`member-download/2178`）をコード内コメントに残す。
  規定改定は**コード変更**として扱う（設定 UI は作らない）
- [申込書自動記入](../entry-form-autofill/requirements.md) が `settings` テーブル新設を計画中だが、
  協会規定値は会ごとの設定ではないため定数側に置く。設定の家は分けてよい
- 既存の公開挙動に変更を加えない（純粋な追加）

## 7. 設計判断の根拠

- **列追加ではなく定数**: 実額は3段階・全国一律の協会規定。イベントごとに入力させる情報ではない。
  改定時の変更点も1箇所で済む
- **`settings` テーブルではなく TS 定数**: 会ごとに変える値ではなく、改定は年単位。DB に置くと出典と
  施行日を追えなくなる
- **null を返す**: `users.grade` が nullable。既定額へ倒すと「級未設定の会員に誤った金額」が静かに伝播する
- **UI を切り離した**: 導出値の見せ方（規定額ラベル／会員ごと算出）は決定済みだが、表示に手を入れると
  `feeJpy = null` の既存イベントに一斉に金額が出る＝公開済みデータの見え方が変わる。値の保持と分離して段階を切る
