# member-role-management 要件定義書

## 1. 概要

- **目的**: 管理者が、アプリの画面から各会員のロール（管理者 / 副管理者 / 一般会員）を付与・剥奪できるようにする。
- **背景・動機**: `users.role` は 3 値の enum として最初から存在するが、変更する導線がアプリ内に一切ない（会員作成は `role: 'member'` 固定、会員編集画面のコメントにも "role management is deliberately out of scope here" と明記されている）。現状ロールを変えるには本番 DB への直接 UPDATE が必要で、副管理者を増やす・役職者が退いたときに戻す、といった運用がアプリだけで完結しない。

## 2. ユーザーストーリー

- **対象ユーザー**: 管理者（admin）のみ。副管理者・一般会員にはロール変更の UI も操作も存在しない。
- **ユーザーの目的**: 会計や大会運営を任せる会員に副管理者権限を渡し、役目が終わったら一般会員へ戻す。
- **利用シナリオ**:
  1. 管理者が `/admin/members` の一覧から対象会員の「編集」を開く。
  2. 「ロール」セクションで現在のロール（日本語表示）を確認し、変更先を選んで保存する。
  3. 確認ダイアログで了承すると変更が反映され、成功メッセージが出る。
  4. 対象の会員は**再ログインなしで**次の操作から新しいロールの権限になる。
  5. 変更できない相手（自分自身・LINE 未紐付けの会員を昇格 など）については、その理由が画面に書かれている。

## 3. 機能要件

### 3.1 画面と遷移（画面インベントリ＋ナビゲーション地図）

新規画面は作らない。既存の管理画面 2 箇所に手を入れる。

| # | 画面／要素 | 追加・変更内容 |
|---|---|---|
| S1 | 会員編集 `/admin/members/[id]/edit` | 「ロール」セクションを追加（既存の「LINE 紐付け」「退会処理」「会員の削除」と同じカードパターン）。**管理者にのみ表示**。現在のロール表示＋3択の選択＋保存ボタン＋確認ダイアログ。変更できない場合はその理由を文章で示し、操作を無効化する。 |
| S2 | 会員一覧 `/admin/members` | ロール列の生 enum 表示（`admin` / `vice_admin` / `member`）を日本語ラベル（管理者 / 副管理者 / 一般会員）に置き換える。**一覧からの変更操作は追加しない**（S1 への導線は既存の「編集」リンク）。 |

遷移:

```
/admin/members （一覧・ロールは日本語表示）
  └─ 「編集」 → /admin/members/[id]/edit
                  └─ ロールセクションで保存 → 確認ダイアログ → 同画面に留まり成功/エラーを表示
```

見た目は既存セクション・フォームのパターンをそのまま踏襲するため design-spec は作成しない（`design_required: false`）。

### 3.2 ビジネスルール

**R1. 誰が変更できるか**
- **管理者（admin）だけ**がロールを変更できる。副管理者には UI を出さず、Server Action も拒否する。
- 既存の `assertAdminSession()` は `vice_admin` も通すため**流用しない**。同画面の `unlinkLine`（admin 限定）と同じ扱いにする。
- 認可判定には**実効ロール（`session.user.role`）**を使う。したがって role-preview-switch で「副管理者ビュー / 会員ビュー」に切り替えている間はロール変更できない（プレビューの意味を保つため。`realRole` は使わない）。

**R2. 付与できるロールの範囲**
- 管理者は `admin` / `vice_admin` / `member` のどれへでも変更できる（管理者を新たに増やすこともできる）。
- 現在のロールと同じ値を保存した場合は「変更なし」として成功扱いにする（エラーにしない）。

**R3. 対象にできない相手（すべてサーバー側で拒否する）**
- **自分自身**: 自分の行のロールは変更できない（降格も昇格も）。誤操作で自分の管理権限を失う事故を原理的に防ぐ。UI ではセクションに理由を表示して操作を出さない。
- **LINE 未紐付けの会員を `admin` / `vice_admin` へ昇格**: 禁止。`/self-identify` の候補は「LINE 未紐付け ∧ 招待済み」だけで絞られており role を見ていないため、未紐付けの管理者行は招待リンクを開いた第三者に名乗られうる。`member` のままにしておく（紐付け後に昇格させる運用）。
- **退会済み（`deactivated_at` が非 NULL）の会員を `admin` / `vice_admin` へ昇格**: 禁止。`member` への降格は許す（役職者が退会したときの後始末に使う）。
- **有効な管理者が 0 人になる変更**: 拒否する。「有効な管理者」は `role = 'admin'` かつ `deactivated_at IS NULL` の行を数える（退会済み管理者はログインできないので数に入れない）。自分自身を変更できない仕様と合わせて二重の防御にする。

**R4. 反映のされ方**
- 変更は即座に DB に書かれ、対象会員は**再ログイン不要**で次のリクエストから新しいロールで判定される（JWT の `role` クレームは毎リクエスト DB から再同期されるため）。
- 変更後、会員一覧と当該会員の編集画面の表示が更新される。

**R5. エラー・境界条件**
- 拒否された場合は**日本語のエラーメッセージ**を画面に表示し、DB は一切変更しない。
- 対象会員が存在しない／enum 外のロール値が送られた場合も拒否する。
- 保存操作には確認ダイアログを挟む。キャンセルした場合は何も起きない。
- 管理者 2 人が互いを同時に降格させるような並行操作でも、有効な管理者が 0 人になってはならない。

## 5. Non-goals

**機能面**
- ロール変更の履歴・監査ログ（誰がいつ誰をどう変えたか）は残さない
- 新しいロール種別の追加、既存 3 ロールの権限マトリクスの変更（何ができる/できないの中身は一切変えない）
- 会員一覧からのインライン変更（ロール列は表示のみ。日本語化だけ行う）
- 会員作成時・招待登録時にロールを指定する機能（引き続き `member` 固定）
- ロール変更を対象会員へ通知する（LINE / Web Push）
- 副管理者による限定的なロール操作（副管理者は一切ロールを触れない）

**技術面**
- `/self-identify` の候補クエリの変更（今回は「未紐付け行を昇格させない」側で塞ぐ）
- 退会処理（`toggleMemberDeactivation`）で最後の管理者を退会させられてしまう既存の穴の修正（別件）
- ロール判定の共通ヘルパー（`requireAdminSession()` 等）への既存コードの一括リファクタ

## 6. 技術的制約・契約

- **マイグレーション不要**: `user_role` enum は `admin` / `vice_admin` / `member` を既に持ち、`users.role` 列も存在する。スキーマ変更は行わない。
- **認可**: ロール変更 Server Action は冒頭で `await auth()` し、`session.user.role === 'admin'` のみ通す（実効ロール判定。`realRole` は使わない）。既存 `assertAdminSession()` は `vice_admin` を通すため使わない。
- **競合の直列化**: 「有効な管理者が 0 人になる変更の拒否」は読み取り→書き込みの間に他の変更が入りうる。既存の `deleteMember` と同じくトランザクション＋行ロック（`FOR UPDATE`）、および対象条件を UPDATE の `WHERE` 句に埋め込む方式で直列化する（チェックと書き込みの間に条件が変わっても静かに通らない形にする）。
- **`unlinkLine` の対象を `member` 限定にする（レビュー R1 の blocker 対応・既存挙動の変更）**: 昇格時に LINE 紐付けを要求するだけでは「昇格 → 紐付け解除」の順で未紐付けの権限持ち行を作れてしまい、`/self-identify` 経由の乗っ取り経路が開いたままになる。対象条件は UPDATE の `WHERE` に埋め込む（ロール変更と並行しても確定後のロールで再評価させる）。管理者・副管理者の紐付けをやり直させたい場合は、先に一般会員へ降格してから解除する運用に変わる。
- **維持すべき既存挙動**:
  - 会員編集画面・会員一覧に対する副管理者のアクセス権（閲覧・プロフィール編集）は変えない
  - `updateMemberName` / `deleteMember` が対象を `role = 'member'` に限定している既存の防御は残す
  - `unlinkLine` に存在しない `userId` を渡したときは従来どおり無害に返す（誤った id で画面を壊さない）
  - JWT の `token.role`＝本物のロール、`session.user.role`＝実効ロールという role-preview-switch の契約を壊さない
- **日本語ラベル**: `管理者` / `副管理者` / `一般会員` の対応は既存の `roleViewLabel`（`apps/web/src/lib/role-preview.ts`）に定義済み。新しいラベルマップを作らず再利用する。
- **UI 規約**: 確認ダイアログは同画面の `DeleteMemberSection` と同じ `window.confirm` パターン。エラー表示は `role="alert"`、成功表示は `role="status"`（既存フォームに倣う）。

## 7. 設計判断の根拠

- **管理者限定にした理由**: 副管理者に許すと、副管理者が自分または仲間を管理者へ昇格でき、3 層 RBAC が実質 2 層に崩れる。既存コードも監査上重要な操作（`unlinkLine`）は admin 限定にしている。
- **自分自身を変更できなくした理由**: 誤操作で自分の管理権限を失うと、他に管理者がいない場合は DB 直接操作でしか復旧できない。表示上の見え方を確認したいだけなら role-preview-switch（表示ロール切替）があるので、本物のロールを下げる必要がない。
- **未紐付け行の昇格を禁止した理由**: `/self-identify` は「LINE 未紐付け ∧ 招待済み」の行を候補として出し role を見ていない。未紐付けの管理者行を作ると、招待リンクを開いた第三者がその行を名乗って管理者になれる。今回は入口（昇格）側で塞ぎ、認証フローには手を入れない（影響範囲を小さく保つため）。
- **退会済みの昇格だけ禁止し降格は許した理由**: 退会済みはログインできないので昇格は無意味かつ復帰時に危険。一方、役職者が退会したときにロールを戻す運用は必要。
- **監査ログを持たない理由**: 実質 1 人管理者の身内アプリで「誰がやったか」の追跡価値が低く、テーブル追加とマイグレーションのコストに見合わない。必要になった時点で追加する。
- **実効ロールで判定する理由**: 既存の認可はすべて `session.user.role`（実効ロール）を読む。ここだけ `realRole` を使うと、プレビュー中に管理操作ができてしまい「会員にはこう見える／触れない」を確認するというプレビュー機能の目的が崩れる。
