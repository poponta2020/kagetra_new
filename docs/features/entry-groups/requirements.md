# entry-groups（申込グループ）要件定義書

> 事前調査・方向性合意: `.claude/memory/project_entry_groups_direction.md`（2026-07-26 の設計相談。
> 本番DB実データ調査に基づく）。
> **実装開始は event-detail-redesign 出荷後**（同一画面 /events/[id] の二重改修を避けるため。§6 参照）。

## 1. 概要

### 目的
大会は開催日ごとに別イベントとして登録される（例: 多摩A=8/15、多摩B=8/11…）。参加者にとって
開催日単位の見え方は正しいが、実運用の申込・締切・名簿・抽選・LINE連絡は「同じ案内メール×同じ
申込締切」のまとまり（＝**申込グループ**）単位で行われる。この単位が DB に存在しないため:

- 管理者は同じ操作（LINE紐付け・申込済トグル・配信）をイベントごとに繰り返す
- 通知は重複する（多摩A/Cで申込完了通知・会計通知が2通ずつ）か、漏れる（未紐付けの日の
  締切リマインドは誰にも届かない）

「申込グループ」を薄い基盤として導入し、LINE紐付け・メール配信・名簿・締切リマインド・
進行操作をグループ単位へ集約する。

### 本番実データで確認済みの根拠（2026-07-26 調査）
- 本番40イベント中、実質のグルーピングは tournament_draft_id（同一案内メール、8グループ22イベント）
- 多摩: 1通の案内→5イベント。締切は AB=7/11 / CDE=7/5 の2系統。後続メール（名簿・入金・抽選結果）も
  AB / CDE クラスタ単位。LINE紐付けは多摩A(=AB用)・多摩C(=CDE用)のみで B/D/E は未紐付け
  （ユーザー確認済み: A/C のグループを AB用/CDE用として手動使い分け）
- 多摩C=申込済・多摩D/E=申し込まない: 同一締切クラスタ内でも日別に申込有無が異なる → 日別状態は必須
- 秋田: 同じメール由来でも ABCD(8/23,締切7/26) と DE(9/20,締切8/30) は実質別大会
  → グループはメール単位でなく**締切クラスタ単位**が正しい

## 2. ユーザーストーリー

- **対象ユーザー（主）**: 管理者・副管理者。大会申込の進行管理（LINE紐付け・申込・支払い・連絡転送・名簿）を行う。
- **対象ユーザー（副）**: 一般会員。LINE グループで大会連絡・リマインドを受け取る。アプリ内の一覧の見え方は変えない。
- **ゴール**:
  - 管理者: 複数日大会で、LINE紐付け1回・申込済トグル1回・配信1回・名簿1回で済む。
  - 会員: 同内容の LINE 通知が2通届かない。未紐付けだった日の締切リマインドも届くようになる。

### 3.2 ビジネスルール

#### 3.2.1 申込グループの定義
- 新テーブル `entry_groups`（薄い基盤: id・作成時刻程度。名前カラムは持たない）
- `events.entry_group_id` は **NOT NULL**。全イベントが必ず1グループに属する。単独イベント
  （会内行事・手動作成）は作成時に自動でシングルトングループを生成
- グループの意味 = 「同じ案内メール×同じ申込締切で運用されるまとまり」。ただし DB 上は
  管理者が自由に付け替え可能（定義はデフォルト生成規則であって制約ではない）
- **グループ表示名は導出**（保存しない）: グループ内イベントのタイトルから共通接頭辞+級文字を結合
  （多摩A+多摩B→「多摩AB」）。同一タイトル複数日（大学生選手権×3）は「大学生選手権」のまま。
  導出不能時は代表イベントのタイトル

#### 3.2.2 LINE 紐付け・配信（グループ単位へ移行）
- `event_line_broadcasts` の帰属を event → entry_group に変更。**1グループ=1LINEグループ=1Bot**
  （現行の「1イベント=1グループ」保証と同等の一意性をグループ単位で維持）
- 招待コード発行・解除・自動解放期限延長・要綱選択・要綱再送・手動再配信は、グループ内の
  どの日の詳細画面から行っても同一の紐付けに作用する（1回で全日に効く）
- メール→LINE 配信（承認時自動・手動再配信）はグループの紐付け先に**1回だけ**送る
- 自動解放の基準は「グループ内で最も遅い開催日」+ 30日（現行の event_date+30日の自然な拡張）

#### 3.2.3 進行状態（日別維持）
- `events.entry_status` / `payment_type` / `payment_status` は**日別のまま維持**
  （「C級の日だけ申し込む」を表現するため。本番で実例あり）

#### 3.2.4 進行操作の一括化と通知集約
- 管理者が代表イベント詳細で申込済/支払済等をトグルすると、**同グループの他の日を
  チェックボックス付き確認ダイアログ**（既定: 該当しうる日は全チェック）で選択し、
  選択した日を**同一トランザクションで**一括更新する
- LINE 通知は選択した日をまとめた**1通**（例:「8/1(土)C級・8/8(土)D級を申し込みました」）。
  会計向け通知も同様に1通
- once-ever 保証は現行どおり **(event_id, type) 単位**を維持し、一括操作では選択した全イベント分を
  同一 tx で claim して1通に集約送信する。後から追加の日を applied にした場合は
  「新たに claim できた日の分だけ」の通知が1通送られる（既送の日は再送しない）
- cancelled の日はダイアログで選択不可・claim しない（既存ルール維持）

> **2026-08-20 変更（操作の入口を撤回）:** 「代表イベント詳細でトグル → 確認ダイアログで他の日を選ぶ」という
> **操作の形**は撤回した。一括操作は申込グループページ `/admin/entries/[groupId]` の**日程表で日を選んでから
> まとめて適用する**1つの形に統一され、伝播確認ダイアログ（`GroupToggleDialog`）は撤去された。
> **通知の規則（この節の本体）は一切変わっていない** — once-ever は `(event_id, type)` 単位、選択した全日を
> 同一 tx で claim して1通に集約、後追いは新規 claim 分のみ、cancelled は claim しない。
> 正典は [entry-group-page/requirements.md](../entry-group-page/requirements.md) §3.2.5。
- 支払いタイプ変更時の状態リセット等、既存の単イベント時のルールは選択された各日に同様に適用

#### 3.2.5 締切リマインド・管理者アラートの集約
- 日次リマインダー（申込締切・支払締切・現地払い）は **(グループ, 通知種別, 締切日) 単位で1通**に
  集約し、対象の日を列挙する。グループ内で締切が同じ日同士が1通にまとまり、
  （伝播を外して）締切が異なる日は別通になる
- 紐付けがグループ単位になることで、従来未紐付けだった日のリマインドも同じ LINE グループへ届く
- entry-overdue-alert（管理者向け会内締切超過サマリー）は**グループ単位で1行**に集約

#### 3.2.6 グループの付け替え（後からの編集）
- `/events/[id]/edit` に「申込グループ」欄を追加:
  - 現在のグループと所属日一覧の表示
  - **単独化**（このイベントを新しいシングルトングループへ分離）
  - **合流**（既存グループへ移動。候補: 同じ tournament_draft 由来のグループ＋開催日が近い順の全グループ検索）
- 付け替え時、移動元グループの LINE 紐付け・名簿はそのまま移動元に残る（帰属はグループ）。
  通知履歴（event 単位）はイベントに付いて移動する
- グループ内の最後の1件が抜けた空グループは自動削除
  - ただし**依存行を持つグループは残す** — LINE 紐付け・名簿は上記のとおり移動元に残る仕様なので、
    それらを持つグループはイベント0件でも削除しない（FK は RESTRICT。削除を試みると付け替え自体が
    ロールバックする）。この状態のグループに割り当てられた Bot は、自動解放スイープが
    「イベント0件のグループ」を期限切れ扱いで回収してプールへ戻す

#### 3.2.7 締切・支払い系フィールドの伝播
- `/events/[id]/edit` で申込締切・会内締切・抽選日・支払締切・支払方法・支払情報・申込方法を
  変更して保存する際、同グループに他の日があれば**伝播確認ダイアログ**（チェックボックス付き・
  既定全チェック）を表示し、選択した日にも同じ値を保存する
- 伝播を外して日別差をつけることは許容（その場合のリマインド動作は §3.2.5 の (グループ, 種別, 締切日) 規則に従う）
- 開催日・級・定員・参加費・タイトル等の日固有フィールドは伝播しない

> **2026-08-20 変更（伝播ダイアログを撤回）:** 「`/events/[id]/edit` で変更 → 伝播確認ダイアログ」の形は撤回した。
> 対象の7項目（＝`PROPAGATABLE_FIELD_KEYS`）は `/events/[id]/edit` から**撤去**され、申込グループページの
> 「共通項目」で**グループ全日（cancelled 含む）へ一括保存**する形になった。
> **維持されるもの:** 対象フィールドの集合・日別差を許容すること（リマインドは (グループ, 種別, 締切日) 単位で
> 別通に分かれる）・日固有フィールドは伝播しないこと。実装基盤（`propagateFieldsToGroup`）も同じものを使う。
> 正典は [entry-group-page/requirements.md](../entry-group-page/requirements.md) §3.2.6。

#### 3.2.8 AI 承認時の自動グループ化
- 承認フォームで、ユニット群を **同一 draft × 同一申込締切** で自動グループ提案
  （多摩→AB/CDE の2グループ、秋田→2グループ）
- ユニットごとに割当を変更可能（別グループへ・新規グループへ）
- 承認時に events と entry_groups を同時に作成し、割当どおりに紐付ける

#### 3.2.9 名簿（グループ単位へ移行）
- `tournament_entry_rosters` の帰属を event → entry_group に変更（版管理の一意性は
  (グループ, roster_type, version) に読み替え）
- アップロード・差し替え・表示（掲載ハイライト含む）はグループ単位。グループ内の
  どの日の詳細からも同一の名簿が見える
- mail-inbox の名簿ドラフト採用（lottery-trends）もグループへ紐付ける
- 名簿由来の下流（抽選実績・出場回数・シリーズ指標・当落線・確定名簿公開。edition 基準の集計）は
  **既存挙動を維持**する（回帰 AC）

#### 3.2.10 既存データの移行（backfill）
- migration で `entry_groups` を作成し、既存全イベントに backfill:
  同一 `tournament_draft_id` × 同一 `entry_deadline` のイベント群 → 1グループ、
  それ以外（draft 無し・単独）→ シングルトングループ
- 既存の `event_line_broadcasts`（linked/revoked/released 全状態）・名簿（本番0件）を
  グループ帰属へ移行。既存の linked 紐付け（多摩A→ABグループ等）は**有効なまま引き継ぐ**
- 通知履歴（event_lifecycle_notifications）は event 単位のまま変更しない

#### エラーケース・境界条件
- 一括操作の対象に他の管理者が並行で状態変更したイベントが含まれる場合: 既存の
  ガード付き UPDATE（WHERE 旧状態）の枠組みを踏襲し、変化しなかった日は結果表示で通知
- グループ紐付けが未 linked のまま一括トグル: 全選択日を skipped で claim（既存規則の集約版）
- 代表イベントが cancelled: 代表選定からは除外しない（詳細画面は到達可能なため）が、
  進行ダイアログでは選択不可
- 承認フォームでユニットが1つだけの場合: グループUIは出さずシングルトン自動生成

## 5. Non-goals

- **会員向け /events 一覧の変更**（日別カード・締切ソート・色帯はそのまま。ユーザー明示選択）
- **既存 LINE グループの統合・作り直しの支援**（多摩の A用/C用グループはそのまま各グループに引き継ぐ。
  グループ分けを変えた際の LINE 側メンバー移動は運用対応）
- **event-grade-group-broadcast（#313）の設計変更**（級別グループへの新着案内はイベント単位のまま。
  本機能の後に実装し、必要なら向こう側で追随）
- **edition（結果ドメイン）との統合**（`events.edition_id` と結果系の紐付けは不変。
  申込グループは edition を参照しない）
- **通知文面の刷新**（複数日の列挙に必要な変更のみ。文体・構成は既存踏襲）
- **過去に送信済みの通知履歴の書き換え・再送**
- **グループの手動命名**（表示名は導出のみ）
- **一般会員向けの新しい操作**（追加されるのは日リンク表示のみ）
- **グループ単位の新しい権限区分**（既存の admin / vice_admin / member 3層のまま）

## 6. 技術的制約・契約

- **互換性（壊してはいけない既存挙動）**: 会員向け /events 一覧・出欠回答（event 単位）・
  lifecycle 通知の once-ever 保証 (event_id, type)・lottery-trends の edition 基準集計・
  確定名簿公開・級別競技人口等の統計系
- **公開契約**: 外部公開 API は無し（Server Actions + 内部 route handler のみ）。
  `api/line-broadcast` 系の共有トークン URL（要綱DL等）は有効なまま維持
- **保持データ**: 既存の event_line_broadcasts 全行（履歴含む）・event_lifecycle_notifications・
  event_broadcast_messages は削除しない。migration は非破壊 + backfill 同梱・`db:migrate` 経路
- **セキュリティ・権限**: グループ操作（紐付け・一括トグル・付け替え・名簿）は admin / vice_admin のみ
  （各 Server Action 冒頭で `await auth()` + role チェック。既存規約どおり）
- **並行制御**: Bot プール予約・一括トグルの claim は既存の FOR UPDATE / ガード付き UPDATE /
  INSERT ON CONFLICT パターンを踏襲
- **着手順序の制約**: 実装開始は **event-detail-redesign 出荷後**（/events/[id] の二重改修回避）。
  event-grade-group-broadcast（#313）は本機能の**後**（承認フォーム領域の衝突回避。#313 側が rebase）
- **CI 委譲**: 回帰検証は CI（DEVFLOW_CI_COVERS）。AC にローカル全実行を要求しない
- **未解決の技術論点（技術計画への申し送り）**:
  1. `event_line_broadcasts` / `tournament_entry_rosters` の FK 付け替え方法（列リネーム vs 新列+移行）と
     一意制約の再定義
  2. backfill migration の具体 SQL（複数の revoked/released 行が同一グループに集まる場合の一意制約設計）
  3. リマインダーバッチ（send-lifecycle-reminders）のグループ集約クエリと claim の原子性
  4. 承認フォーム（ApprovalForm）へのグループ割当 UI の入れ方（既存 unit 分割 UI との整合）
  5. 一括トグルの通知文面組み立て（日列挙フォーマット）と buildLifecycleMessage の拡張方法
  6. グループ表示名導出ロジックの置き場所（shared か web か）

## 7. 設計判断の根拠

- **グループ = 締切クラスタ（同メール×同締切）**: 名簿・入金・抽選結果メールの実際の粒度と一致
  （多摩AB/CDE、秋田の2分割）。メール単位では締切が混在しリマインドが複雑化する（実データで確認）
- **締切カラムは events に残す（グループへ移さない）**: 会員向け一覧・編集フォーム・AI抽出を
  ほぼ無傷に保つ。「同じ締切」はデフォルト生成規則+伝播ダイアログで運用的に維持し、
  意図的な日別差も許容できる（柔軟性と改修範囲のバランス）
- **進行状態は日別維持+操作だけ一括**: 「C級の日だけ申し込む」が本番で実在するため。
  グループ単位ステータスにすると表現できなくなる
- **once-ever を (event, type) のまま維持**: 後から日を追加申込したとき「新しい日の分だけ通知」が
  自然に実現でき、既存の二重送信防止・監査の仕組みを流用できる
- **グループ専用詳細画面を作らない**: 画面の種類を増やさず、代表イベント詳細+伝播ダイアログで
  完結させる（ユーザー提案。見え方の分散による混乱を回避）
- **シングルトングループ必須（nullable にしない）**: 「グループあり/なし」のコード分岐を消し、
  LINE紐付け・名簿・リマインドのロジックを常にグループ単位に単純化する
- **名簿も本機能に含める**: 名簿・抽選結果メールがクラスタ単位で届く実態に合わせる
  （ユーザー選択。lottery-trends への波及は回帰 AC で固定）
