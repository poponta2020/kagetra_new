## 1. 対象と狙い

- **対象画面:** `/admin/entries`（既存。ログイン会員全員が閲覧可）
- **round 13 の動機:** 出荷後の実データで見ると**画面が地味すぎた**。区画の切れ目が弱く、行が均質に縦に並ぶだけで「フェーズごとのまとまり」として読めない
- **狙い:** 1 画面・スクロールなしという round 12 の制約を保ったまま、**区画のまとまりと階層を視覚的に立てる**
- **主ユーザー / 主な使い方:** 変更なし（管理者 1 名が朝に開いて「今日潰すもの」を確認する）

## 2. round 13 で変えたこと

| # | 変更 | 理由 |
|---|---|---|
| 1 | 区画見出しを **13px ゴシック太字・墨 → 15px 明朝 bold(700)・藍（`--kg-brand-fg`）・字間 .03em** | ページ h1 が明朝なので、区画見出しも明朝にすると画面内の階層が「明朝＝構造／ゴシック＝データ」で揃う。★ウェイトは §4 の注意書きを必ず読むこと |
| 2 | 区画を**常に和紙の面（`--kg-surface`）で束ねる**。強調時だけ朱面（`--kg-danger-bg`）へ切替 | 面があることで区画が「まとまり」として読める。canvas（`--kg-bg`）との明度差だけで境界を作り、枠線は足さない |
| 3 | **玉をレール上から区画見出しの行の中へ移動**。常に 13px・藍の輪郭 | 玉が見出しと同じ行にあると「このフェーズの札」として読める。サイズを可変にしないことで区画の位置が状態で動かない |
| 4 | **行間の区切り線（`divide-y`）を全廃** | 面で束ねたので行ごとの罫線は二重の仕切りになる |
| 5 | **複数日グループの日別行への展開を廃止（1 グループ = 常に 1 行）** | ユーザー判断（2026-07-27）。同一グループなら「杉並AB」の 1 行で足り、日ごとの内訳は行タップで大会詳細へ入れば分かる |
| 6 | **区画名の改称**: 要対応→**要申込** / 申込済み・抽選待ち→**申込完了・抽選待ち** / 名簿確定・振込待ち→**名簿確定・要振込** | 「要対応」は何をするのか分からない。動詞（申込・振込）を名前に入れて、その区画で何をすべきかを名前だけで示す |
| 7 | レール線を**最初の玉の中心から始め、最後の大会の行まで伸ばす** | 玉より上へ線がはみ出すと起点が曖昧になる。下は「大会があるところまで」で終端を示す |

**採らなかったもの:**

- **0 件の行動フェーズも朱にする案** — 一度採用しかけたが撤回（2026-07-27）。requirements §3.2.7・設計判断12 の「常時赤くすると赤が背景と化す」という原則が優先。**0 件はグレー（`--kg-fg-muted`）に落とす**
- 行の高さを増やす・カード化する — round 12 で検討済み。1 画面制約と正面から衝突する（§9 参照）

## 3. mock に現れない設計判断

1. **玉の水平位置はレールの中心に厳密に合わせる。** 玉は見出し行（`.ahead`）の子だが、負のマージンでレール列の中心へ引き戻している。`.area` の gap 10px ＋ レール幅 11px ＝ 21px 分左へ戻し、玉の半径 6.5px を足すとレール中心 5.5px に一致する。**px 値を写すのではなく「レール中心と玉中心が一致する」ことを実装の条件にする**（余白を変えたら値も変わる）
2. **区画の面は左へ 6px 食い込ませる。** レールと面が繋がって見えることで、レールが区画の「背骨」として読める。round 12 の強調時の扱いを全区画へ広げたもの
3. **玉のサイズを状態で変えない（常に 13px）。** round 12 は通常 9px・強調 13px だったが、それだと強調が入った瞬間に区画の垂直位置が動く。塗り（輪郭 → ベタ）と色だけで状態を出す
4. **区画見出しは行より 4px 左にぶら下がる。** 玉の負マージンの結果だが、見出しがハンギングすることで「見出し＞行」の階層が強化されるので、そのまま採用した
5. **日別展開の廃止で失う情報を受容する。** グループ内で締切が日ごとに違う場合、round 12 は日別行にそれぞれの締切を出していた。1 行にすると**最も早い日しか出ない**。ユーザーの明示的判断（2026-07-27）として受容する — 食い違いが問題になるのは大会詳細へ入る場面であり、ボードは「どのフェーズにいるか」を見る画面だから
6. **区画ヒント（会内締切／本締切／…）と日付列の右端を一致させる縦の整列は round 12 から維持する。** 実測 375px で両方 175px。**これが崩れると見出しが列見出しとして機能しなくなる**

## 4. 使用コンポーネント

- **既存プリミティブ:** なし（`@/lib/utils` の `cn` のみ）。Card・Pill は使わない — この密度では枠線と余白がコストになる
- **既存コンポーネントへの変更:**
  - `EntryBoardClient` / `AreaBlock` — 見出し・面・玉・レールの見た目を差し替え
  - `EntryRow` — 区切り線を外すのみ
  - **`EntryGroupCard` / `EntryGroupDayRow` は削除**（1 グループ = 1 行になり、日別行が存在しなくなる）
- **トークン逸脱なし。** 使用色は `--kg-brand` / `--kg-brand-fg` / `--kg-danger` / `--kg-danger-bg` / `--kg-danger-fg` / `--kg-accent-fg` / `--kg-surface` / `--kg-border` / `--kg-border-soft` / `--kg-fg` / `--kg-fg-2` / `--kg-fg-3` / `--kg-fg-muted` / `--kg-fg-on-brand` のみ。いずれも `globals.css` に実在し、Tailwind ユーティリティ（`text-brand-fg` 等）も生成される
- 見出しの 15px は `--kg-text-base` と同値

> ⚠️ **見出しのウェイトは 700（`font-bold`）にすること。600（`font-semibold`）にしてはならない。**
> `apps/web/src/app/layout.tsx` は Noto Serif JP を **`weight: ['700']` だけ**で読み込んでいる（`preload: false`）。
> 600 を指定すると CSS のフォントマッチングで 700 へ丸められるか合成太字になり、**指定と実際の描画がずれる**。
> モック側は `file://` で webfont が読めず Yu Mincho / Hiragino Mincho にフォールバックしていたため、
> この差はモック上では見えない（＝モックの見た目 ≠ 実アプリの見た目になる唯一の箇所）。
> 本当に 600 で出したい場合は `layout.tsx` の weight 配列へ `'600'` を足す必要があるが、
> **共有レイアウトの変更＋フォントファイル 1 つ分の追加ダウンロード**になるため、既定は 700 とする。

## 5. 状態（state）

- **通常:** 5 区画すべてを常に描画。面は和紙、見出しは藍、玉は藍の輪郭
- **区画が 0 件:** 見出し・件数・玉をすべてグレー（`--kg-fg-muted` / `--kg-border`）へ落とし、行の代わりに `なし`。**行動フェーズでも朱にしない**
- **行動フェーズに対象があり締切が未到来:** 面は塗らず、**見出しと玉の輪郭だけ朱**（`--kg-danger`）
- **行動フェーズに締切到来済みが 1 件以上（＝強調）:** 面が朱（`--kg-danger-bg`）・見出しが濃朱（`--kg-danger-fg`）・玉が朱のベタ塗り・件数ピルが反転（`--kg-danger` 地に `--kg-fg-on-brand`）
- **空（母集団 0 件）:** ボード全体を「管理対象の大会はありません」の 1 枚に差し替える（round 12 から変更なし）
- **折りたたみ:** 「締切前」のみ開閉可（既定は開）。round 12 から変更なし
- **モック上の再現:** `current.html` が強調ありの状態（デモ行 2 件＝京都EF・名古屋AB。実データに無い名前をわざと使っている）、`redesign-realdata.html` が全件実データ・強調なしの状態

## 9. 残課題・実装への申し送り

- **1 画面制約は round 13 でも守られている。** 実測: 強調あり版 659px / 実データ版 645px（`main` は 758px）。**日別展開の廃止で round 12 より余裕が増えた**（round 12 の実装は同じデータで 703px 相当）

- **モックの CSS 変数名は実コード由来**なので、Tailwind ユーティリティへそのまま対応が付く（`--kg-brand-fg` → `text-brand-fg` 等）。値を読み取って書き直さないこと

- Browser ペインの screenshot はこのセッションでも失敗した（ペイン非表示時は composite されない）。レイアウト検証は `getBoundingClientRect` / `scrollHeight` の実測で行う
