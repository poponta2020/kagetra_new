# 申込管理ボード デザイン仕様（design-spec）

> **レイアウトの詳細は `design-prototype.patch`（実差分）が正。** ここには patch から読み取れない意図・判断・データ要件を書く。
> ロジック（区画の判定条件・母集団・並び順・表示条件）は `requirements.md` §3.2 が正。ここでは再記述しない。

## 1. 対象と狙い

- **対象画面:** `/admin/entries`（新規・管理者専用）／ボトムナビへのタブ追加
- **現状の不満:** 会レベルの申込進捗を見る手段が「`/events` を開いて 1 件ずつ詳細に入り進行管理パネルを見る」しかなく、どの大会がどのフェーズにいるか俯瞰できない
- **狙い:** **1 画面・スクロールなしで、どの大会がどのフェーズにいるかが一目で分かる**こと。行動が必要なフェーズが締切到来時に確実に目に入ること
- **主ユーザー / 主な使い方:** 管理者 1 名が朝に開いて「今日潰すもの」を確認する。眺めて把握し、必要なら大会詳細へ飛ぶ

## 2. 採用した方向性

**タイムライン型の単一画面ボード。** 左に 1 本のレールを通し、5 つのフェーズをその上のノードとして縦に並べる。大会が上から下へ進んでいく構造をそのまま画面の構造にした。1 大会 = 1 行（約 24px）。

**不採用案と理由:**

- **縦積みセクション＋件数ジャンプバー（1 案目）** — 情報量は多いが 21 件で 2.55 画面分のスクロールが必要で、「一目で分かる」を満たせなかった
- **横スクロールタブ（2 案目）** — 各区画は 1 画面に収まるが、タブバー自体が 571px で 375px に収まらず横スクロール必須。初期表示で後ろの 2 区画が見えず、フェーズの全体像が掴めない。件数の少ない区画では画面下半分が空く
- **カード＋ステータスチップ（見た目案）** — いちばん今風に見えるが、1 行 52px と現行の 2 倍以上を使うため 1 画面制約と正面から衝突する。「今風に見える」の実体は面積を使っていることだった
- **強調＝行を大きくする案** — インパクトは最大だが 1 画面の余裕を 3 分の 1 以上消費する
- **強調＝上部サマリーバー案** — 開いた瞬間目に入るが、情報が 2 箇所に重複し、フェーズ自体は目立たないまま

**確定プロトタイプ:** `design-prototype.patch`（ブランチ `design/entry-management`・基点 `8e9d68d`）
**確認 URL:** `/admin/entries`（ダミー 21 件のうち 18 件が 5 区画に入る状態）

## 3. patch に現れない設計判断

1. **1 行 24px という高さは「5 区画 × 全件を 1 画面に収める」から逆算した制約。** 実測で 18 行・5 区画のとき最終区画の下端が余裕 86px。**情報を足したくなったら、まずこの制約に反しないかを確認する。**
2. **0 件の区画も見出しを残して `なし` を出す。** 区画を消すと区画の位置が件数によって動き、「いつも同じ場所を見れば同じフェーズが分かる」という一目性が失われる。空区画の高さコストを払ってでも位置の安定を優先した。
3. **日付の種類名を行から区画見出しへ移した。** 全行に「会内締切 7/14 12日超過」を出すと幅が足りない。区画ごとに見る日付は 1 種類に固定されているので、見出しの右端に 1 回だけ出せばよい。**見出しのラベルは行の日付列と同じ幅・同じ右端に固定**してあり、列見出しとして機能する。
4. **残日数を日付の左に置いた。** 緊急度（あと2日 / 6日超過）の方が日付そのものより先に読まれるべきで、大会名のすぐ隣に置くと視線移動が短い。日付は右端で確認用。
5. **残日数と日付を固定幅の 2 列にした（62px / 52px、いずれも右寄せ）。** 行ごとに位置が揺れると縦に目で追えない。日付が無い行は左列が空になるだけで、右列の位置はずれない。
6. **強調は面の塗りとノードの拡大だけで、枠線を付けない。** タイムラインのレールが既に左の縦線なので、枠線を足すと二重の囲みになって騒がしい。塗りは左へ 6px 食い込ませてレールとつながって見えるようにしている。
7. **強調を締切到来時に限定した（`requirements.md` §3.2.7）。** 行動フェーズを常時赤くすると赤が背景と化す。行動フェーズであること自体は、締切が未到来のときは**赤い輪郭のノードと赤い見出し文字**だけで示す。
8. **曜日を省いた（`8/16(日)` → `8/16`）。** 4 文字ぶんの幅は通称の表示に回す方が価値が高い。曜日が要るのは詳細画面。
9. **参加希望者数を大会名の直後に置き、大会名だけを省略対象にした。** 人数が名前の長さで消えると「人が集まっている大会」を探せない。

## 4. 使用コンポーネント

- **既存プリミティブ:** なし（`@/lib/utils` の `cn` のみ）。Card・Pill は使っていない — この密度では枠線と余白がコストになるため、区画はレール＋背景、行は素の flex で組んだ
- **新規:**
  - `EntryBoardClient`（ボード本体）・`AreaBlock`（フェーズ区画＋レール）・`EntryRow`（1 大会 1 行）
  - `entry-board-utils.ts`（純関数：区画判定 `classify` / 並び替え `sortArea` / 区画別の日付バッジ `deadlineBadgeOf` / 表示名 `displayName` / 強調判定 `isAreaHot` / 折りたたみ時の残留判定 `isPinnedWhenCollapsed`）
- **トークン逸脱なし。** 色は既存の `danger` / `danger-bg` / `danger-fg` / `accent-fg` / `ink-*` / `border-*` / `surface` トークンのみ

## 5. 状態（state）

- **通常:** 5 区画すべてを常に描画。件数は見出しに `N件` で出す
- **空（母集団 0 件）:** ボード全体を「管理対象の大会はありません」の 1 枚に差し替える
- **区画が 0 件:** 見出し＋`なし`。区画は消さない（§3-2）
- **長大:** **件数の上限や「もっと見る」は設けていない。** 実測 18 行で 86px の余裕がある。**35 行を超えると 1 画面に収まらなくなる**が、そのときは縦スクロールが発生するだけで壊れはしない（申し送り §9）
- **不明値:** 日付が NULL のとき、締切系は `締切未設定`、抽選日は日付列に `未定`。通称が無い大会は正式名称にフォールバックし幅で強制的に切る
- **折りたたみ:** 「締切前」のみ開閉可（既定は開）。畳んでも会内締切 3 日以内の行は残り、隠れた行数は `ほかN件`
- **プロトタイプでの再現方法:** `proto-data.ts` の DESIGN-PROTO 固定データ 21 件。長い大会名・通称なし・締切未設定・支払締切超過・抽選日なし・抽選日経過・手動見送り・出欠 0 名を意図的に含めている

## 6. 必要データ

| 表示 | 出所 | 備考 |
|---|---|---|
| 通称 | `tournament_series.short_name` | **`events.edition_id` → `tournament_series_editions.series_id` → `tournament_series` で辿る。** edition 未紐付けの大会は NULL → `events.title` にフォールバック |
| 級 | `events.eligible_grades` | 通称に連結（`札幌` + `AB` → `札幌AB`） |
| 参加希望者数 | `event_attendances` の `attend = true` 件数 | 素通し（`/events` と同じ。requirements §3.2.2） |
| 各種日付 | `events.internal_deadline` / `entry_deadline` / `payment_deadline` / `lottery_date` / `event_date` | 区画ごとに出し分ける |
| 確定名簿の有無 | `tournament_entry_rosters`（`roster_type='confirmed'` かつ `superseded_at IS NULL`） | 区画判定にのみ使い、画面には出さない |

- **集計・導出:** 区画判定・並び順・日付バッジ・強調判定はすべて `entry-board-utils.ts` の純関数。`Date.now()` を呼ばず、サーバーが渡す JST `todayStr` だけで決まる

## 7. インタラクション / レスポンシブ

- **操作:** 行タップ → `/events/[id]`。「締切前」見出しタップ → 開閉。**それ以外の操作は無い**（表示専用）
- **タップ領域:** 折りたたみ見出しは高さ 28px を確保している（初期の 16px は小さすぎた）
- **モバイル:** 375px 実測で横スクロールなし（行幅 365px）・縦スクロールなし（`main` scrollHeight = clientHeight）
- **ボトムナビ:** 7 タブ（管理者のみ）。実測でタブ幅 54px・「申込管理」のラベル 44px、横スクロールなし。タブは**管理者専用ブロックの先頭**（統計の直後・会員の前）

## 8. ガードレール準拠メモ

- 既存トークン・既存の日付表記（`M/D`）に準拠。絵文字は不使用
- **ダークモードは対応していない。** 既存アプリ全体が未対応で、この画面だけ対応させると浮くため（`requirements.md` §5 Non-goals）
- 文言はすべて日本語

## 9. 残課題・実装への申し送り

- **1 行 24px・5 区画で 86px しか余裕が無い。** 実装で要素を足す判断をする前に、375px の実機で最終区画が画面内に収まることを必ず確認する
- 件数が 35 行規模に育つと 1 画面に収まらなくなる。そのとき初めて「区画ごとの件数上限＋もっと見る」を検討する（今は入れない）
- **patch には worktree 限定の認証バイパスが含まれる。実装時には適用してはならない。** `git apply` する場合は次の 2 ファイルを除外し、`page.tsx` の認可ガードは本来の形へ戻すこと:
  - `apps/web/src/middleware.ts`（`/admin/entries` の素通し）
  - `apps/web/src/app/(app)/layout.tsx`（未ログイン時のシェル描画）
- **DESIGN-PROTO スタブ一覧（4 ファイル）:**
  - `apps/web/src/app/(app)/admin/entries/proto-data.ts` — ファイルごと削除する
  - `apps/web/src/app/(app)/admin/entries/page.tsx` — ダミーデータ注入箇所を実クエリへ／認可ガードを本来の形へ
  - `apps/web/src/app/(app)/layout.tsx` — 未ログイン時シェル描画を削除
  - `apps/web/src/middleware.ts` — `/admin/entries` の素通しを削除
  - 完了時に `git grep DESIGN-PROTO` = 0 件
- **プロトタイプの `EntryBoardItem` はフラットな DTO。** 実装時もこの形（サーバーで畳んでクライアントへ渡す）を維持すると、純関数のテストがそのまま使える
- Browser ペインの screenshot はこのセッションで不安定だった（クリップ・拡大が起きる）。レイアウト検証は `getBoundingClientRect` / `scrollHeight` の実測で行うのが確実
