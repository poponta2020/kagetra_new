# entry-management（申込管理）要件定義書

管理者が「いま自分が何をすべきか」を申込グループ単位で一望できる進捗ボード。グループを進行フェーズごとの区画へ自動で仕分け、**1 申込グループ = 1 行**で表示し、**スクロールなしで全フェーズが見渡せる**ことを最優先にする。

**位置づけ:** 新規画面だが、実質は `event-lifecycle-notify`（PR #85 / #118）と `entry-overdue-alert`（PR #312）が LINE 通知として実装してきた「会レベルの申込進捗」を、**画面として可視化する**もの。併せて `entry-overdue-alert` の毎朝アラートに 1 条件を足す delta を含む。

**画面の見た目の正典は [design-spec.md](design-spec.md)（round 13・locked）と [design-mock/](design-mock/) の 2 ファイル。** 本ファイルはロジック（母集団・仕分け条件・並び順・表示項目の定義）を持ち、レイアウトを言葉で再記述しない。
※ `design-prototype.patch`（round 12）は**視覚の正ではない**（二重に古い。design-spec 冒頭の警告を参照）。適用しないこと。

正典の機能仕様は `docs/spec/events-attendance.md`（イベント・進行管理）と `docs/spec/notifications.md`（通知）。

## 1. 概要

### 目的

1. 管理者が**大会ごとの申込進捗を 1 画面で把握**でき、次に手を動かすべき大会が即座に目に入る状態にする。
2. LINE の毎朝アラート（`entry-overdue-alert`）と**同じ定義**で「要申込」を判定し、通知と画面が食い違わないようにする。
3. 管理者がもう手を動かすことのない大会（参加希望者なし・見送り確定）を**画面から自動的に外し**、意識すべき母集団を小さく保つ。

### 背景・動機

- 現在、会レベルの申込進捗を確認する手段は「大会申込一覧 `/events` を開いて 1 件ずつ詳細に入り、進行管理パネルを見る」しかない。一覧には進行状態のピルが出るが、**進行段階での仕分けやグルーピングは一切ない**。
- `entry-overdue-alert` で毎朝の LINE サマリは手に入ったが、これは「会内締切を過ぎた未申込」という**1 段階だけ**の検知であり、申込後の「抽選待ち」「確定名簿待ち」「振込待ち」は依然として無管理。

## 2. ユーザーストーリー

**対象ユーザー:** 管理者・副管理者（admin / vice_admin。実運用は管理者 1 名）

- 管理者として、朝この画面を開けば全フェーズが 1 画面に出ていて、赤くなっているフェーズだけ潰せばよい状態にしたい。
- 管理者として、会内締切がまだ先の大会について「何名が参加希望を出しているか」を眺めたいが、まだ申し込む段階ではないので操作は求めていない。畳んでおけるとなおよい。
- 管理者として、申込者がいない大会は自動的にこの画面から消えてほしい。毎回「これは見送る」と手で押したくない。
- 管理者として、申し込んだ後の大会が「抽選待ち」「振込待ち」「もう何もない」のどれなのかを、詳細を開かずに区別したい。

**利用シナリオ:**

1. 管理者がボトムナビの「申込管理」をタップする。
2. 「要申込」フェーズが薄い赤で塗られている。会内締切を過ぎて参加希望者がいるのに未申込の大会が、本締切の迫っている順に並んでいる。
3. 行をタップすると大会詳細へ遷移し、既存の進行管理パネルで「申込済にする」を押す。
4. 戻ってくると、その大会は「申込完了・抽選待ち」へ移っている。
5. 主催者から確定名簿が届いてメール取込で承認すると、その大会は「名簿確定・要振込」へ移る（事前払いかつ未振込の場合）。
6. 振込を済ませて「振込済にする」を押すと「完了」へ移り、以後は管理者が見る必要がなくなる。**確定名簿がまだ取り込めていなくても、振込が済んでいれば「完了」へ抜ける**（2026-07-27 変更。§3.2.3）。
7. 現地払い・支払い管理のない大会は、「申込済にする」を押した時点で「完了」へ入る（会として次に手を動かすことが残っていないため。2026-07-27 変更）。

### 3.2 ビジネスルール

#### 3.2.1 母集団（この画面に載る大会）

以下をすべて満たす `events` 行を対象とする（JST 基準）。

| # | 条件 | 根拠 |
|---|---|---|
| 1 | `events.event_date >= 今日` | 開催日当日までは表示し、翌日から消える。`/events` と同一ルール |
| 2 | `events.status != 'cancelled'` | 中止大会に進行管理は不要 |
| 3 | `events.kind = 'individual'` | 確定名簿（`tournament_entry_rosters`）が個人戦のみを対象とする仕様のため、団体戦は正しく仕分けられない |
| 4 | **§3.2.4 の「非表示」条件に該当しない** | 管理者がもう手を動かすことのない大会を母集団から外す |

**母集団はイベント（`events` 行）単位で決まるが、表示はグループ単位に畳む。** 上の 4 条件を満たしたイベント（＝可視日）を `entry_group_id` で束ね、**1 グループ = 1 行**として描く（§3.2.5）。同一大会が複数級で複数 `events` 行に分かれていても、同じ申込グループに属していれば 1 行になる。
※ 2026-07-26 版の「`events` 行ごとに 1 行として扱う（集約はしない）」は、entry-groups タスク6（グループ集約）と 2026-07-28 の日別展開廃止により**撤回済み**。

#### 3.2.2 判定に使う導出値

| 名前 | 定義 |
|---|---|
| `baseDeadline`（会内締切） | `COALESCE(internal_deadline, entry_deadline)`。会内締切が主、未入力なら大会申込締切で代替（`entry-overdue-alert` と同一定義） |
| `attendCount` | `event_attendances` のうち `attend = true` の件数。**対象級・`isInvited` で絞らない素通しの件数**（`/events` 一覧と同じセマンティクス） |
| `hasConfirmedRoster` | `tournament_entry_rosters` に `entry_group_id = 当該グループ` かつ `roster_type = 'confirmed'` かつ `superseded_at IS NULL` の行が存在すること。**＝メール取込フローで確定名簿を取り込み承認した時点で true**。名簿の帰属は entry-groups タスク8 で event → entry_group へ移ったので**グループ単位**であり、グループ内のどの日から見ても同じ値になる |
| `shortName`（通称） | `events.edition_id` → `tournament_series_editions.series_id` → `tournament_series.short_name`。`edition_id` 未設定なら NULL |

#### 3.2.3 フェーズ区画の定義（5 区画・相互排他）

大会が進む順（ライフサイクル順）に上から並べる。条件は相互排他で、母集団の各大会はちょうど 1 区画に属する。

| # | 区画名 | 判定条件 | 表示する日付 | 並び順キー |
|---|---|---|---|---|
| 1 | **締切前** | `entry_status='not_applied'` かつ（`baseDeadline` が NULL または `baseDeadline >= 今日`） | 会内締切（`baseDeadline`） | 会内締切 昇順・NULL 末尾 |
| 2 | **要申込** | `entry_status='not_applied'` かつ `baseDeadline < 今日` かつ `attendCount >= 1` | **本締切**（`entry_deadline`） | 本締切 昇順・NULL 末尾 |
| 3 | **申込完了・抽選待ち** | `entry_status='applied'` かつ `payment_type='advance'` かつ `payment_status='unpaid'` かつ `NOT hasConfirmedRoster` | 抽選日（`lottery_date`） | 抽選日 昇順・NULL 末尾 |
| 4 | **名簿確定・要振込** | `entry_status='applied'` かつ `hasConfirmedRoster` かつ `payment_type='advance'` かつ `payment_status='unpaid'` | 支払締切（`payment_deadline`） | 支払締切 昇順・NULL 末尾 |
| 5 | **完了** | `entry_status='applied'` かつ（`payment_status='paid'` または `payment_type='onsite'` または `payment_type IS NULL`）。**確定名簿の有無を問わない** | 開催日（`event_date`） | 開催日 昇順 |

> **2026-07-28 変更（区画名の改称・判定条件は不変）:** 要対応 → **要申込** ／ 申込済み・抽選待ち → **申込完了・抽選待ち** ／ 名簿確定・振込待ち → **名簿確定・要振込**。
> 「要対応」は何をすべきかが名前から分からなかったため、**その区画で管理者が取る行動（申込・振込）を名前に入れた**。締切前・完了は据え置き。
> **判定条件・表示する日付・並び順キーは 1 つも変えていない**（純粋な改称）。`AreaId`（`action_required` / `applied_waiting` / `payment_due` 等の内部識別子）も変えない — 変えると `entry-overdue-alert` との対応関係や既存テストの参照が無駄に壊れるため、**変わるのは `AreaDef.label` の文字列だけ**。

すべての区画で、並び順キーが同値のときは開催日を副キーとする。

**区画定義の補足:**

- **「要申込」だけ会内締切ではなく本締切（`entry_deadline`）を表示・整列に使う。** この区画は会内締切が既に過ぎている大会の集まりであり、管理者が見るべきは「これを逃すと申込漏れが確定する日」＝主催者への申込締切だから。`entry_deadline` が NULL の場合は日付欄を空にし「締切未設定」と出す
- **`baseDeadline` が NULL の未申込大会は「締切前」に入る。** 締切が判定不能な大会を「要申込」に入れると、単に締切を入力し忘れただけの大会が最上部に居座り、本当に危ない大会を押し下げるため。並び順では末尾に置き「締切未設定」と明示する
- **「申込完了・抽選待ち」は抽選の有無を問わない。** 抽選がない大会・抽選日が未設定の大会は日付欄が「未定」になる
- **「名簿確定・要振込」の支払締切超過に専用区画は設けない。** 支払締切の昇順なので超過分は必ず最上部へ来る
- **確定名簿は「完了」の必須要件ではない（2026-07-27 変更）。** 支払いの決着（振込済／現地払い／支払い管理なし）が付いた大会は、確定名簿が未取込でも「完了」へ入る。確定名簿の有無を見るのは、**事前払いかつ未振込**の大会を「抽選待ち」と「振込待ち」のどちらへ置くかを決めるときだけになった（設計判断14・15）
- **`payment_type` が `onsite` または NULL の大会は、申込済みになった時点で「完了」へ入る。** `payment_type=NULL` は既存スキーマで「支払い通知なし」を意味する（`events.ts:61`）。これらの大会には「振込確認」という行為自体が存在しないため、緩めるなら申込済みが唯一の判定点になる（＝抽選待ちを経由しない）
- **`applied` の 4 通りは網羅かつ相互排他:** 事前払い＋振込済 → 完了／事前払い＋未振込＋名簿あり → 名簿確定・要振込／事前払い＋未振込＋名簿なし → 申込完了・抽選待ち／現地払い・支払い管理なし → 完了

#### 3.2.4 この画面に出さない大会（非表示条件）

以下のいずれかに該当する大会は、母集団から除外する（どの区画にも出さない）。

| # | 条件 | 意味 |
|---|---|---|
| 1 | `entry_status='not_applying'` | 管理者が手動で見送りを確定した大会 |
| 2 | `entry_status='not_applied'` かつ `baseDeadline` 非 NULL かつ `baseDeadline < 今日` かつ `attendCount = 0` | 会内締切を過ぎて参加希望者が 0 名＝申し込む理由がない大会 |

**この結果、手動で「申し込まない」にした大会は `/events`・`/admin/entries` のどちらにも現れない。** 復帰導線は大会詳細 URL の直叩きのみ（`entry-overdue-alert` §3.1 の設計をそのまま維持する。2026-07-26 ユーザー判断）。

#### 3.2.5 行の単位と載せる情報

**1 申込グループ = 常に 1 行**（2026-07-28 変更）。載せる情報は以下に限る（**5 区画・全件が 1 画面に収まる密度を維持する**）。

- **名前 = グループ表示名。導出の順序は以下で固定する**（★技術計画で確定。2026-07-28）:
  1. 可視日それぞれの**通称ベースの表示名**を作る＝`shortName + eligible_grades`（例「杉並B」「杉並A」）。`shortName` が NULL（edition 未紐付け）の日は `events.title` にフォールバック
  2. それらを `deriveEntryGroupName` と**同じ規則**（全一致ならそれ／共通接頭辞＋級文字を昇順連結／導出不能なら NULL）で 1 つに畳む（例「杉並B」+「杉並A」→「**杉並AB**」）
  3. 畳めなかった場合のみ、`events.title` から導出した既存の `groupName` へフォールバックする
  - **単独イベントのグループは手順1の結果がそのまま出る**＝現行の「通称 + 対象級」表示（例「札幌AB」）と 1 文字も変わらない。**これが回帰の基準**
  - 幅を超える名前は**幅で強制的に切る**（省略記号）。専用の表示・警告は設けない
  - ★この順序を守らないと退行する: `deriveEntryGroupName` は `events.title`（正式名称）から導くため、**通称を先に作らずに畳むと単独イベントの表示が通称から正式名称へ戻ってしまう**（現行は単独＝通称・複数日＝正式名称ベースという不統一だった）
- **参加希望者数** — 名前の直後に `（N名）` の形で置く。「参加」のラベルは出さない。名前が長くても人数は切り詰めない。0 名なら出さない
- **残日数**（右寄せの固定列）— §3.2.6 の条件を満たすときだけ出す
- **日付**（残日数のさらに右、固定列）— §3.2.3 の「表示する日付」。区画をまたいで縦に揃える
- **開催日を行頭に出す列は設けない**（この画面では重要度が低い）。開催日が日付列に現れるのは「完了」区画だけで、それはその区画が見ている日付が開催日だから

日付の種類名（会内締切／本締切／抽選日／支払締切／開催日）は**各行ではなく区画見出しの右端**に、日付列の真上に揃えて 1 回だけ出す。

行全体が `/events/[id]`（グループの**代表イベント**）へのリンクになる。

##### 3.2.5.1 複数日グループの集約規則（2026-07-28 新設）

グループが複数の可視日を持つ場合、**日別行への展開は行わない**。1 行に畳むにあたり、複数値を取りうる 2 項目だけ集約規則を定める。集約の母集団は**可視日のみ**（§3.2.4 の非表示条件で落ちた日は数にも日付にも含めない）。

| 項目 | 集約規則 | 根拠 |
|---|---|---|
| 日付・残日数 | グループの可視日のうち、**その区画で見る日付が最も早いもの**。全日 NULL ならその区画の NULL 表記（`締切未設定` / `未定`） | 並び順キー（`groupSortKey`）が既に「最も早い日」なので、**並びと表示が同じ値**になり画面が自己矛盾しない |
| 参加希望者数 | グループの可視日の**合計** | 「人が集まっているグループ」を探せることが目的なので、最大値や代表日の値では過少表示になる |

**受容する情報欠落（2026-07-28 ユーザー判断）:**

1. **グループ内で締切が食い違う場合、最も早い日以外の締切は画面から見えない。** 日別行が担っていた役割だが、食い違いが問題になるのは大会詳細へ入る場面であり、ボードは「どのフェーズにいるか」を見る画面だと割り切る。
2. **グループ内で進行状態が食い違う場合、日ごとの状態は画面から見えない。** カードは §3.2.5.2 の優先順位で 1 区画にだけ載るため、例えば 9/5 が「完了」・9/6 が「要申込」のグループは「要申込」にだけ現れる。**「まだ申し込むべき日がある」という判断は正しく伝わる**（安全側）ので受容する。内訳は行タップで大会詳細へ入れば分かる。

##### 3.2.5.2 グループが載る区画の決定

グループ内で日ごとの `classify` 結果が食い違うとき、**最も対応が必要な区画**へ 1 つだけ載せる。優先順位は上ほど「見落とすと実害が出る」順:

`要申込` → `名簿確定・要振込` → `申込完了・抽選待ち` → `締切前` → `完了`

- この優先順位（`GROUP_AREA_PRIORITY`）は**日別展開の廃止後も必要**。1 行になっても「どの区画に置くか」は 1 つに決めなければならない
- 全日が非表示条件に該当するグループは、どの区画にも現れない

#### 3.2.6 残日数の表示条件

| 状態 | 表示 | 出す区画 |
|---|---|---|
| 締切超過 | `N日超過` | 締切前 / 要申込 / 名簿確定・要振込 |
| 締切当日 | `本日` | 同上 |
| 締切まで 1〜3 日 | `あとN日` | 同上 |
| 締切まで 4 日以上 | **出さない**（日付だけ） | — |
| 日付が NULL | `締切未設定`（抽選日は日付列に `未定`） | 同上 |

- **「申込完了・抽選待ち」と「完了」は残日数を一切出さない。** まだ手を動かす段階ではなく、日付だけ分かれば十分なため
- 4 日以上先の残日数を出さないのは、読む必要のない数字で画面を埋めないため。閾値 3 日は既存 `/events` 一覧の `SOON_THRESHOLD` と同一定義

#### 3.2.7 区画の強調

- **「要申込」「名簿確定・要振込」の 2 区画のみ**強調の対象とする（管理者が手を動かす必要があるフェーズ）。
- 強調するのは、**その区画に「締切が到来済み」の大会が 1 件以上あるときだけ**。「締切が到来済み」＝その区画で見ている日付が**今日と等しい、今日より前、または未設定（NULL）**。
  - **未設定を到来済み扱いにするのは fail-safe。** 「要申込」は会内締切を過ぎて参加希望者もいる大会の集まりなので、本締切が未入力という理由だけで強調が外れると、盤上でいちばん危ない行が目立たなくなる。「名簿確定・要振込」も同様に、支払期限不明のまま未払いを静かに放置させない。
- 締切がまだ先の間は強調しない。常時赤い状態を作らないことで、赤い表示への慣れを防ぐ。
- **0 件の区画は、行動フェーズであっても朱にしない**（2026-07-28 明文化）。区画が空＝その行動は今やることが無い、という意味なので、色で注意を引く理由が無い。0 件はどの区画も同じグレー扱いにする。
  - round 13 のデザイン過程で「0 件の行動フェーズも淡い朱で出す」案を検討したが、上記「常時赤い状態を作らない」原則と衝突するため**採用しなかった**（2026-07-28 ユーザー判断）。
- 強調の 3 段階（0 件＝グレー／対象ありで締切未到来＝見出しと玉の輪郭だけ朱／締切到来済み＝面の塗り・玉のベタ塗り・件数ピルの反転）の**見せ方**は `design-spec.md` が正典。

#### 3.2.8 区画の折りたたみ

- **「締切前」区画のみ**、見出しタップで開閉できる。**既定は開いた状態**（出欠の集まり具合を眺めるのが主用途のため）。
- 畳んだ場合でも、**会内締切が 3 日以内に迫った大会の行は表示し続ける**。畳んだまま締切を跨ぐ事故を防ぐため。締切未設定の行は判定不能なので対象外＝畳めば隠れる。
- 畳んで隠れた行数は `ほかN件` として示す。
- 開閉状態は画面内でのみ保持し、永続化しない（再訪すると既定に戻る）。

#### 3.2.9 毎朝アラート（`entry-overdue-alert`）への delta

画面の「要申込」と LINE アラートの対象を**同一定義に揃える**。

- `apps/web/src/lib/entry-overdue-alert.ts` の抽出条件に **`attendCount >= 1`** を追加する。
- 既存 4 条件（`status != 'cancelled'` / `event_date >= 今日` / `entry_status = 'not_applied'` / `baseDeadline < 今日`）は変更しない。
- `attendCount` は既に同ファイルの相関サブクエリ（`attendCountExpr`）で取得済みであり、**文面に出している値をそのまま抽出条件へ回す**だけ。

**この delta のリスク（明示的に受容する）:** `entry-overdue-alert` の Non-goals では「出欠回答者 0 名からの自動判定」を「移行過渡期で参加予定者が必ずしも出欠登録するとは限らない」ため見送っていた。その懸念は依然として有効であり、**出欠登録されていないだけの大会は LINE でも黙る**ことになる。ユーザーの明示的判断（2026-07-26）として受容する。

#### 3.2.10 エラー・境界条件

- **母集団が 0 件のとき**: 画面全体の空状態メッセージを出す。
- **特定区画が 0 件のとき**: 見出しは残し、行の代わりに `なし` を出す。区画を消すと区画の位置が件数によって動き、「いつも同じ場所を見れば同じフェーズが分かる」という一目性が失われるため。
- **日付判定はすべて JST の `YYYY-MM-DD` 文字列比較**。サーバー側で「今日」を確定させクライアントへ渡す（`Date.now()` をクライアントで呼ぶと hydration mismatch になる。既存 `event-list-utils.ts` と同じ制約）。
- **`baseDeadline` が今日と等しい日は「超過していない」**（「締切前」であり「要申込」ではない）。`entry-overdue-alert` の AC-3 と同じ境界。
- 複数の確定名簿バージョンが存在する場合、`superseded_at IS NULL` の行が 1 つでもあれば `hasConfirmedRoster = true`。

## 7. 設計判断の根拠

1. **進行フェーズを永続カラムにせず導出にした:** すべて `entry_status` / `payment_type` / `payment_status` / 各締切 / 確定名簿の組み合わせで一意に決まる。状態カラムを足すと既存の操作すべてに同期処理が必要になり、ずれたときに直す手段がなくなる。
2. **確定名簿の判定を「取込・承認済み」にした:** 主催者の発表時点を捉えようとすると新しい手動フラグと migration が必要になり、取込との二重管理が発生する。発表から取込までのタイムラグの間に管理者がやることは「取り込む」ことなので実害がない。
3. **団体戦を対象外にした:** 確定名簿は個人戦専用の仕様。含めると「確定名簿が永遠に出ない」大会が申込済み区画に滞留し、区画の意味が壊れる。
4. **参加希望者 0 名の大会を自動で非表示にした:** 手動の `not_applying` だけを条件にすると、管理者が毎回「見送る」ボタンを押さないと母集団が減らない。この画面は**表示の仕分けであって不可逆な状態変更ではない**ため、誤判定しても行が 1 つ消えるだけで、大会詳細からいつでも到達できる。
5. **毎朝アラートにも同じ条件を足した:** 画面が「参加希望者なし」と判定した大会を LINE が「申込漏れ」と鳴らし続けると、管理者はどちらかを信用しなくなる。定義を 1 つに保つのは通知の信頼性そのもの。
6. **表示専用にした:** 一覧から「申込済にする」を押せるようにすると、LINE 通知 2 通が飛ぶ操作を誤タップできてしまう。詳細ページへ一度入る 1 ステップが誤操作の防波堤になる。
7. **参加希望者数を `/events` 一覧と同じ素通し件数にした:** 対象級で絞る詳細画面の数え方だと、対象級外の会員が参加を表明したケースで 0 名と判定され、その大会が自動的に非表示になる。除外判定は安全側（拾いすぎる側）に倒すべき。
8. **開催日が今日以降に限った:** 完了区画は終端状態であり、開催日を過ぎた大会を残すと単調に積み上がる。「過去のイベント」画面が既にその管轄を持っている。
9. **「要申込」だけ本締切を見るようにした:** 会内締切は既に過ぎている区画なので、会内締切の超過日数を見ても行動は決まらない。行動を決めるのは「主催者への申込締切まであと何日か」。
10. **締切未設定の大会を「締切前」に置いた:** 「要申込」に入れると、単に締切を入力していないだけの大会が毎日最上部に居座り、本当に危ない大会を押し下げる。
11. **残日数を 3 日以内に絞った:** 全行に「あと24日」まで出すと、読む必要のない数字が画面の 1 列を占領する。閾値は既存 `/events` の 3 段階表示と揃えた。
12. **強調を「締切到来済みが 1 件以上あるとき」に限定した:** 行動フェーズを常時赤くすると、赤が背景と化して効かなくなる。実際に締切が来た瞬間にだけ面が赤くなることで、赤の意味が保たれる。
13. **ボトムナビに 7 個目として追加した:** 「イベント」タブを置換する案は、管理者が会員と同じ大会一覧（申込可能フィルタ・参加者チップ）を見る手段を失わせる。申込管理は進捗の管理であり、大会一覧の上位互換ではない。
14. **支払いの決着を確定名簿より優先した（2026-07-27）:** 確定名簿は「主催者が発表し、それをメールから取り込んで承認した」という**外部要因＋こちらの作業**の両方が揃って初めて true になる。一方で振込済は管理者自身が押す確定的な事実であり、そこから先に会としてやることは残っていない。名簿の取込漏れ・主催者の発表遅れ・そもそも名簿を配らない大会のいずれでも、済んだ大会がボード上で「抽選待ち」に滞留し続けるのは、区画の意味（＝手を動かす必要があるか）を裏切る。**確定名簿は完了の必須要件ではなく、事前払い・未振込の大会を「まだ抽選待ち」と「もう振込できる」に分けるための材料**に位置づけを下げた。
15. **現地払い・支払い管理なしを申込済み時点で完了にした（2026-07-27）:** これらの大会には「振込確認」という判定点が存在しないため、緩めるなら申込済みが唯一の判定点になる。**受容するリスク:** これらの大会は抽選待ちを一切経由せず、申込済にした瞬間に完了へ入る＝抽選の進行をボードで追えなくなる。ボードは「管理者が手を動かす必要のある大会」を出す画面であり、現地払いの大会に対して会が抽選後にすべきことは無いため、追跡価値より滞留の害が上回ると判断した（2026-07-27 ユーザー判断）。
16. **判定を反転させず、支払い決着を先に評価する順序にした（2026-07-27）:** `classify` は上から順に「支払い決着 → 名簿なし → 振込待ち」の 3 段で書く。`hasConfirmedRoster` の条件式そのものは残るので、`page.tsx` のクエリ③・`EntryBoardItem.hasConfirmedRoster`・AC-13 はいずれも生き続け、戻すときは評価順を戻すだけで済む。
17. **区画名に「行動」を入れた（2026-07-28）:** 「要対応」は緊急度は伝わるが**何をすべきか**を伝えない。この画面の目的は「今日潰すものを見つける」ことなので、区画名がそのまま次の動作（申し込む・振り込む）を指しているほうが、詳細を開く前に判断できる。「申込済み・抽選待ち」→「申込完了・抽選待ち」は、隣に「要申込」が並ぶことで「済み／要」の対比が読みやすくなる効果を狙った。**判定条件を一切変えずに名前だけ変えた**のは、改称を挙動変更と混ぜると回帰の切り分けができなくなるため。
18. **複数日グループの日別展開を廃止した（2026-07-28）:** entry-groups タスク6 で入れた日別行は、「グループの中のどの日がどの状態か」を見せるためのものだった。しかし実データで運用してみると、ボードで必要なのは**グループ単位の「次に何をするか」**であり、日別の内訳は行タップで詳細へ入れば分かる。日別行は 1 画面制約を圧迫する一方で、日ごとに違う判断を迫る場面が実際には無かった。**受容するリスク**は §3.2.5.1（締切と進行状態の日別差が見えなくなる）に明記した。区画寄せが「最も対応が必要な区画」へ倒れる設計なので、**見落とし方向には倒れない**（安全側）。
19. **0 件の行動フェーズを朱にしない（2026-07-28）:** デザイン過程で「0 件でも淡い朱にして、そこが行動フェーズだと常に示す」案を検討したが、設計判断12（常時赤くすると赤が背景と化す）と正面から衝突する。**区画が空ということは、その行動は今やることが無いということ**なので、色で注意を引く理由が無い。行動フェーズであること自体は区画名（要申込・要振込）が担う。
