# entry-group-page（申込グループページ）要件定義書

> **グループ実体の正典**: `docs/features/entry-groups/requirements.md`（`entry_groups` の定義・帰属・backfill）。
> 本機能は同ファイル §3.1 の「**グループ専用画面なし**」決定と AC-15 / AC-16 / AC-19 を**撤回**する。
> **ボードの描画仕様の正典**: `docs/features/entry-management/`（本機能はボードの遷移先だけを変える）。
> **日ページの視覚の正典**: `docs/features/event-detail-redesign/design-spec.md`（locked。本機能はそこへの delta）。

## 1. 概要

### 目的
大会の申込・締切・名簿・LINE 連絡・入金は「申込グループ」（同じ案内メール × 同じ申込締切のまとまり。
例: 杉並A 9/6 と 杉並B 9/5 で「杉並AB」）単位で行われる。実体 `entry_groups` と group 帰属のデータは
PR #377 で導入済みだが、**画面が存在しない**ため、グループ単位の運用が「代表イベントの日ページ」に
間借りしている。

その結果:
- 管理者は「どの日を開いたか」で見え方が揺れる。日ページは会員向けの情報（参加者・級別定員・出欠回答）と
  管理者の運用（進行管理・LINE紐付け・申込書・振込総額）が同居して長い
- グループ内で日ごとに違う進行状態（本番実例: 多摩C=申込済 / D・E=申し込まない）を**一覧できる場所がない**。
  一括操作は「代表イベントの詳細でトグル → 伝播確認ダイアログ」という間接的な形になっている

**申込グループページを新設し、管理者の申込運用の起点をそこへ移す。** 日ページは会員が「その日に出るか」を
答える画面に純化する。

### 背景・動機（ユーザーの言葉）
> 大会をグループ単位でまとめたページが欲しい。申込とかは基本グループ単位で行うので。
> 杉並ABなら、会員の申込で主に使う杉並A・杉並Bのページがあって、それとは別に管理者等の申込用に
> 杉並ABのページがあるイメージ。

## 2. ユーザーストーリー

- **主: 管理者・副管理者** — 会として主催者へ申し込む一連の運用（どの日を申し込むか決める・申込済/支払済を
  記録する・LINE グループを紐付ける・申込書を作る・振込総額を把握する・名簿を確認する）を、
  **大会（グループ）単位で1画面**から行いたい。
- **副: 一般会員** — 日ページで自分の参加可否を答える動線は**変わらない**。グループページは
  「会全体の進行がどこまで進んだか」「自分がどの日に参加すると答えたか」を見直す場所として閲覧できる。
- **ゲスト** — 申込管理ボードと同じく立ち入れない（/403）。

## 3. 機能要件

### 3.1 画面と遷移（画面インベントリ＋ナビゲーション地図）

見た目の正は `docs/features/entry-group-page/design-spec.md`（`/design-screen` で確定させる。§3.3 の宿題を参照）。

| 画面 | 変更 |
|------|------|
| **`/admin/entries/[groupId]`（新設）** | 申込グループページ。**全ロール閲覧・操作 UI は管理者/副管理者のみ**・ゲストは /403。**すべてのグループで開ける**（過去大会・中止・団体戦を含む） |
| `/admin/entries`（申込管理ボード） | **行タップの遷移先を `/events/[代表イベントid]` → `/admin/entries/[groupId]` へ変更**。シングルトングループを含む**全行**。区画・仕分け・並び順・表示項目は変えない |
| `/events/[id]`（大会申込詳細＝日ページ） | 管理者向け3セクション（**進行管理・LINE配信・関連メール**）を撤去。日リンク帯（`GroupDayLinks`）を撤去し、**固定文言のグループ導線1本**に置換（シングルトンでも常時表示） |
| `/events/[id]/edit`（イベント編集） | **グループ共通7項目を撤去**し日固有項目のみに。保存時の**伝播確認ダイアログを撤去** |
| `/admin/entry-form/[groupId]`（申込書ウィザード） | 画面自体は変更なし。入口が日ページの進行管理 → グループページへ移る |
| `/events`（会員向け一覧）・`/dashboard`（ホーム） | **変更しない** |

**ナビゲーション地図**

```
ボトムナビ「申込管理」
  └─ /admin/entries（ボード：1グループ=1行）
       └─ /admin/entries/[groupId]（グループページ）★新設
            ├─ 日程表の行 → /events/[id]（日ページ）
            │                    └─ 固定文言のグループ導線 → /admin/entries/[groupId]（戻る）
            ├─ 共通項目の編集（管理者・グループページ内）
            ├─ /admin/entry-form/[groupId]（申込書ウィザード）
            └─ 関連メール → /admin/mail-inbox/mail/[id]

/events（会員向け一覧） → /events/[id]（日ページ） → グループ導線 → /admin/entries/[groupId]
```

URL を `/admin/entries/` 配下に置くのは、ボトムナビ「申込管理」タブの active 判定が前方一致
（`matches: ['/admin/entries']`）なので**追加設定なしでタブが点灯**し、ボード→グループ→日 の階層が
URL に現れるため。`/admin` 配下だが**会員も閲覧できる**（ボード `/admin/entries` 自体が PR #378 で
開放済みなのと同じ扱い）。

**グループページのセクション構成（上から）**

| # | セクション | 可視 | 内容 |
|---|---|---|---|
| 1 | ヘッダー | 全ロール | グループ名・開催日の並び・グループ共通の締切 |
| 2 | 申込フロー帯 | 全ロール | 会内締切→大会申込→抽選→支払→開催（§3.2.4 の集約規則） |
| 3 | 日程表（日×状態） | 全ロール | 開催日・大会名・対象級・申込状態・支払状態・参加希望者数・自分の回答印。行タップで日ページへ。管理者には選択チェックボックス |
| 4 | 進行管理 | 管理者 | 申込状態・申込書（`/admin/entry-form/[groupId]` へ）・支払状態（振込総額・級別内訳・振込先・申込方法）。操作は §3.2.5 |
| 5 | 共通項目の編集 | 管理者 | §3.2.6 の7項目 |
| 6 | LINE配信 | 管理者 | 招待コード発行・解除・要綱選択・要綱再送・手動再配信・配信履歴・級別グループ配信 |
| 7 | 名簿 | 全ロール | パース済み名簿＋採用済み原本ファイル（**日ページにも残す**） |
| 8 | オープンチャット | 全ロール | 保存済み招待 URL（**日ページにも残す**） |
| 9 | 関連メール | 管理者 | **グループ全日分の UNION**（日ページからは撤去） |

**日ページに残るもの**: ヘッダー（大会名・開催日・場所・編集リンク）／申込フロー帯（**日別のまま**）／
グループ導線／オープンチャット／参加者一覧＋あなたの参加費／級別定員／備考／名簿／出欠回答ボタン。

### 3.2 ビジネスルール

#### 3.2.1 到達と権限
- グループページはログイン済みなら**全ロールが閲覧**できる。ゲストは middleware の許可リストに
  該当しないため /403（ページ側にも fail-safe の `redirect('/403')` を置く）
- **操作 UI（進行管理・共通項目の編集・LINE配信・申込書・関連メール）は管理者/副管理者にのみ描画する。**
  非管理者には RSC payload にも載せない（`/events/[id]` で確立した規約と同じ。値を計算してから
  JSX の条件分岐で隠すのでは不十分）
- 表示ロールのプレビュー中（role-preview-switch）は**表示ロールに従う**（一般会員としてプレビュー中の
  管理者には操作 UI が出ない）
- 存在しない `groupId`・イベントが0件のグループは 404

#### 3.2.2 グループ名とヘッダー
- グループ名は **`deriveEntryGroupName`（既存）で導出**する。**保存しない**（`entry_groups` に列を足さない）
- 導出が `null` を返す場合（本番実例: `九段E` + `九段CDE`）は**代表イベントのタイトル**へフォールバックする。
  代表イベント = 既存 `selectRepresentativeEvent`（今日以降で最も近い開催日、無ければ最新。同着は id 昇順）
- ヘッダーには開催日の並び（例: `9/5・9/6`）とグループ共通の締切を出す
- 締切の表示は §3.2.4 の「共通値の決め方」に従う

#### 3.2.3 日程表（日×状態）
- 行 = グループ内の**全イベント**を**開催日昇順**（同着は id 昇順）。`cancelled` の日も**表示する**が、
  §3.2.5 の一括操作では**選択できない**（既存の伝播ダイアログのルールを踏襲）
- 各行に出す情報: 開催日・その日の大会名（例: 杉並B）・対象級・申込状態・支払状態・参加希望者数・
  **自分の回答印**
- **参加希望者数**は `/events` 一覧・ボードと同じセマンティクス（`attend=true` の素通し。対象級・
  `isInvited` で絞らない）。**ゲストは数えない**（guest-role AC-19 と同じ。会として何人分申し込むかの数値）
- **自分の回答印**は全ロールに出す。未ログインはこの画面に到達しない
- 行タップで `/events/[id]`（日ページ）へ遷移する

#### 3.2.4 申込フロー帯の集約規則
グループの帯は、既存の日別ロジック（`buildEntryFlow`）を**変更せずに**、グループから集約した入力を
渡して描く。集約は以下の純関数規則による。

**判定母集団** = グループ内の `status <> 'cancelled'` のイベント（＝**対象日**）。

| 入力 | 集約規則 |
|---|---|
| 開催日 | **対象日の最も早い開催日**（＝「当日は最初の開催日として扱う」） |
| 申込状態 | **申込対象日**（`entry_status <> 'not_applying'` の対象日）が **0件** → `not_applying`（帯は「申込なし」）。申込対象日が**すべて** `applied` → `applied`。それ以外 → `not_applied` |
| 支払タイプ | 申込対象日に `advance` が**1件以上**あれば `advance`。無く `onsite` があれば `onsite`。どちらも無ければ `null` |
| 支払状態 | 申込対象日のうち `advance` の日が**すべて** `paid` なら `paid`、そうでなければ `unpaid` |
| 確定名簿の有無 | **変更なし**（`tournament_entry_rosters` / `tournament_entry_roster_files` はもともとグループ帰属） |
| 会内締切・申込締切・抽選日・支払締切 | 下記「共通値の決め方」 |

**本番データでの検算**（2026-08-20 実測）:
- 多摩CDE（C=applied/paid・D/E=not_applying/unpaid）→ 申込対象日={C}・全て applied → **大会申込=完了**
- 全日本30周年（ABC=applied/paid・A=not_applying/paid）→ 申込対象日={ABC} → **完了**
- 杉並AB（両日 applied/unpaid）→ 申込=完了・**支払が現在地**
- 九段E+CDE（両日 not_applied）→ **大会申込が現在地**

**共通値の決め方**（締切・抽選日・支払方法・振込先・申込方法）:
- 対象日で**値が一致していればその値**を出す
- **食い違う場合は最も早い日付（日付以外の項目は代表イベントの値）を出し、「日により異なる」旨を示す**。
  食い違いは §3.2.6 の共通項目編集で解消するのが正しい運用であり、この表示はその検知手段。
  食い違ったまま運用することは許容する（entry-groups §3.2.7 で既に許容済み。リマインドは
  (グループ, 種別, 締切日) 単位で別通に分かれる）

#### 3.2.5 進行管理の一括操作
- 操作は**「日程表で日を選び、まとめて適用する」1つの形**に統一する。既定は**選択可能な日すべてにチェック**。
  `cancelled` の日は選択できない
- 一括対象のアクション（**前進・後退の両方向**）:
  - 申込済にする／**未申込に戻す**／**申し込まない**
  - 支払済にする／**未払に戻す**
  - 支払タイプの変更（未設定 / 事前払い / 現地払い）
- 選択した日は**同一トランザクション**で更新する。既存のガード付き UPDATE（`WHERE 旧状態`）の枠組みを
  踏襲し、他の管理者の並行更新で変化しなかった日は結果として通知する
- **LINE 通知は現行の集約規則をそのまま維持する**（entry-groups §3.2.4）:
  once-ever 保証は `(event_id, type)` 単位、選択した全日を同一 tx で claim して**1通に集約**、
  後追いで追加した日は**新規 claim 分だけ**の1通。未紐付けなら skipped。
  **本機能で文面・通数の仕様は変えない**
- **現行の伝播確認ダイアログ（`GroupToggleDialog`）は役目を終えるため撤去する。**
  日ページに進行管理が無くなり、「代表イベントを操作したついでに他の日へ伝播するか」という問いが
  成立しなくなるため

#### 3.2.6 グループ共通項目の編集
- グループページで、以下**7項目**を**グループ全日へ一括保存**できる（管理者のみ）:
  申込締切 / 会内締切 / 抽選日 / 支払締切（日付＋状態） / 支払方法 / 振込先 / 申込方法
  — これは既存の `PROPAGATABLE_FIELD_KEYS` と**同一の集合**
- 保存は**同一トランザクション**でグループ内の全イベントに同じ値を書く。`cancelled` の日も含める
  （締切は日別状態ではなく大会の属性のため）
- 支払締切は**日付と状態（`payment_deadline_kind`）を必ず同じ UPDATE で揃える**（DB の CHECK 制約。
  既存の `normalizePaymentDeadline` を経由する）
- 日ページの編集フォーム（`/events/[id]/edit`）からは**この7項目を撤去**し、日固有項目のみにする:
  タイトル・正式名称・開催日・場所・対象級・級別定員・全体定員・参加費・主催・区分（個人戦/団体戦）・
  公認/非公認・備考・開催（edition）紐付け・申込グループの付け替え欄
- **伝播確認ダイアログは撤去する**（編集の入口が1つになり、伝播という概念自体が不要になる）

#### 3.2.7 日ページの整理（delta）
- **撤去**: 進行管理セクション（申込状態・申込書・支払状態）／LINE配信セクション（級別グループ配信を含む）／
  関連メールセクション／日リンク帯（`GroupDayLinks`）
- **追加**: グループページへの導線1本。**ラベルは固定文言**（大会名を繰り返さない）で、
  **シングルトングループでも常に表示する**（ボードが常にグループページへ着地するため、
  出さないと group → day で戻り導線が消える）。複数日のグループではグループ名（例: 杉並AB）を添える
- **維持**: 申込フロー帯は**日別のまま**（その日の `entry_status` / `payment_status` で判定）。
  名簿・オープンチャットは**日ページにも残す**（同一データを2箇所に出すだけで、状態は増えない）
- 日ページに残る管理者向け要素は**ヘッダーの「編集」リンクのみ**になる

#### 3.2.8 グループページへのリンク張り替え
- **会内締切超過アラート（LINE）** の本文に載る URL を、代表イベントの日ページから**グループページ**へ変更する
  （`apps/web/src/lib/entry-overdue-alert.ts`。管理者向けアラートなので着地点はグループページが正しい）
- **申込完了通知・支払通知・締切リマインド**（会員向け LINE）の本文・URL は**変更しない**
  （会員の着地点は日ページのままが正しい）

#### エラーケース・境界条件
- 存在しない `groupId` → 404。イベントが0件のグループ（LINE 紐付け・名簿だけが残った空グループ。
  entry-groups §3.2.6 で発生しうる）→ **404**（日程表もヘッダーも成立しないため）
- 全日が `cancelled` のグループ → 日程表は出すが、フロー帯の判定母集団が空になる。
  この場合は**フロー帯を出さない**
- 団体戦（`kind='team'`）のグループ → ページは開ける。**名簿セクション・申込書の導線は出さない**
  （既存 Non-goal を維持）
- 過去大会のグループ → ページは開ける。ボードには元から出ないので到達は日ページのグループ導線か URL 直打ち
- 参加希望者数が0の日 → 数値を出す（空欄にしない）
- 一括操作で1日も選択されていない状態での実行 → 実行不可（ボタンを無効化する）

### 3.3 デザインへの宿題（→ `/design-screen entry-group-page`）★2026-08-20 全件解決

視覚の正は [design-spec.md](design-spec.md)（`status: locked` / `chosen_direction: C`）と `design-mock/`。
**レイアウトはここに言葉で再記述しない。** 各宿題の決着だけ記す。

1. **日程表の 375px レイアウト** → **案C（進行フェーズ1語）**を採用。行は 開催日 → 大会名 → 級 →
   自分の回答印 → 進行フェーズ1語 → 参加希望者数 → シェブロン。行高 38px・大会名 89px（実測）。
   申込状態と支払状態は**1語のフェーズに集約**する（§3.2.3 の「申込状態・支払状態」はこの1語で表す）。
   フェーズの語彙は**申込管理ボードの区画名と同一**（要申込 / 抽選待ち / 要振込 / 完了 / 申込なし /
   締切前 / 中止）。不採用案（表形式・2行組み）の理由は design-spec §2
2. **チェックボックスと行リンクの共存** → チェックボックスは行の左端に**独立したタップ標的**として置き、
   行の残り全体をその日の大会詳細へのリンクにする
3. **一括操作 UI の置き場** → 日程表の直下。選択件数は「N日を選択中」＋全選択/解除。
   前進3種はボタン、**後退3種は「戻す操作」の `<details>` に畳む**（誤操作を1段遠ざける）
4. **戻り導線の固定文言** → 「‹ 大会全体（申込・名簿）」。複数日のときだけ右にグループ名を薄く添える。
   sticky ヘッダーの**外**に置く
5. **共通項目の食い違いの示し方** → 最も早い値を主に出し、朱で「（日により異なる）」を添える。
   アクションは「編集して揃える」1本
6. **共通項目の編集の形** → design-spec では確定させず**技術計画で決める**（インライン／
   `/admin/entries/[groupId]/edit`。どちらでも忠実度チェックリストを満たす）
7. **セクション9本の順序と密度** → §3.1 の表の順序で確定。**フロー帯は sticky ヘッダーの中**に入れる
   （「まず目に入るべきは締切と進行のサマリー」）。運営操作は既定=閉の `<details>`

## 7. 設計判断の根拠

1. **グループページを新設する（entry-groups の「グループ専用画面なし」を撤回）** — 当時は「代表イベント
   詳細＋日リンク」で足りると判断したが、実運用では日ページが会員向け情報と管理者運用の同居で長くなり、
   日ごとに違う進行状態を一覧する場所が無かった。ユーザーの運用単位（申込はグループ単位）と画面単位が
   ずれていたのが根本。
2. **URL を `/admin/entries/[groupId]` にする** — ボトムナビの active 判定が前方一致で自動的に効き、
   ボード→グループ→日 の階層が URL に現れる。`/admin/entry-form/[groupId]` という group スコープ route の
   先例もある。
3. **全ロール閲覧・操作のみ管理者** — ボード `/admin/entries` が PR #378 で会員全員に開放済みなので、
   その遷移先を管理者専用にすると会員に死んだリンクが生まれる。
4. **シングルトンも常にグループページへ着地させる（本番の83%）** — 行によって着地先が変わると、
   「大会名を押したら何が出るか」が予測できなくなる。一貫性を優先し、代わりに日ページ側の戻り導線を
   シングルトンでも常時表示にして袋小路を塞ぐ。
5. **進行管理は日ページから外してグループへ移す** — 「代表イベントを操作したついでに他の日へ伝播するか」
   という間接的な問いが、「どの日を申し込むか選ぶ」という直接的な問いになる。伝播ダイアログという
   概念自体が消える。
6. **フロー帯の集約は「申し込まない日を除いた残りが全部揃ったら完了」** — 本番の多摩CDE
   （C だけ申込済・D/E は申し込まない）と全日本30周年（ABC 申込済・A は申し込まない）で検算した結果、
   「1日でも進んでいれば完了」は楽観的すぎ、「全日揃って完了」は永遠に完了しない。
7. **`buildEntryFlow` を変更せず集約入力を作る** — 日ページの帯（日別判定）とグループの帯を同じ
   ロジックで描けるので、判定規則が2箇所に分裂しない。
8. **名簿・オープンチャットは両方に残す** — どちらもグループ帰属の同一データで、表示を増やしても
   状態が増えない。会員の主動線（日ページ）から名簿が消えるほうが害が大きい。
9. **共通7項目の編集をグループページへ移す** — 集合が既存の `PROPAGATABLE_FIELD_KEYS` と完全に一致し、
   「どこで締切を直すのか」が1箇所に定まる。日ページの編集は日固有項目に純化する。
10. **マイグレーション無し** — 本機能は既存の group 帰属データを「本来の場所へ置き直す」だけで、
    新しい状態を1つも作らない。
