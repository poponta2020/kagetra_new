# 申込グループページ デザイン仕様（design-spec）

> 要件は同ディレクトリの [requirements.md](requirements.md)（completed・2026-08-20 承認）。
> **レイアウトの正は `design-mock/` の HTML。** このファイルはそこから読み取れない意図・判断・データ要件・宿題だけを書く。

## 1. 対象と狙い
- **対象画面:** `/admin/entries/[groupId]`（新設）。あわせて `/events/[id]` から管理者向け3セクションと日リンク帯を撤去し、グループ導線1本を足す delta。
- **現状の不満:** グループ単位の運用（LINE紐付け・名簿・申込書・振込総額）が「代表イベントの日ページ」に間借りしており、どの日を開いたかで見え方が揺れる。日ごとに違う進行状態を一覧できる場所が無い。
- **狙い:** 管理者の申込運用の起点を1画面に集約し、日ページは会員が「その日に出るか」を答える画面に純化する。
- **主ユーザー / 主な使い方:** 管理者＝申込の進行を進める（操作）。一般会員＝会全体の進行と自分の回答を見直す（閲覧のみ）。

## 2. 採用した方向性

**案C — 日程表の状態を「進行フェーズ1語」に集約する**（2026-08-20 確定）。
各行はその日の進行段階を `要申込 / 抽選待ち / 要振込 / 完了 / 申込なし / 締切前 / 中止` の1語で示す。
**語彙は申込管理ボードの区画名と同じ**にして、一覧と詳細で言葉が割れないようにする。

**採用理由**
- 行高 38px（案Aと同じ）のまま、大会名に 89px 残る（案A は 59px）。**実測値**
- ボードと同じ語彙なので、ボードの行をタップして着地した先で同じ言葉に出会う
- 「今この日に何をすべきか」（要申込・要振込）が朱で立つ。既存の朱の使い方（期限超過）と一貫

**不採用案と理由**（蒸し返し防止）
- **案A 表形式**（申込・支払を独立列に）— 申込と支払が縦に揃う利点はあるが、大会名が 59px（約4文字）まで潰れ、同じ接頭辞を持つ日を見分けられなくなる。
- **案B 2行組み** — 大会名に 147px 渡せて状態も素の言葉のまま書けるが、行高が 59px と 1.5 倍になり、3日ぶんの状態が縦に揃わないので「どの日が遅れているか」の比較がしにくい。この表の存在理由が比較なので致命的。

**案C が引き受けたコスト（実装への申し送り）**
- 申込と支払の2軸が1語に潰れる（「申込済・未払」は「要振込」の一語になる）。2軸の生の値は行タップ先の日ページと、進行管理セクションの集約表示で確認する。
- **ボードの区画判定（`classifyEntryBoard`）はグループ単位**なので、日ごとに同じ判定を回す必要がある。

**視覚の正**

| `page-admin.html` | **確定形**。管理者ビューのページ全体（杉並AB・9セクション） |

## 3. 視覚の正に現れない設計判断
- **フロー帯を sticky ヘッダーの中に入れた。** ユーザーが「まず目に入るべきは締切と進行のサマリー」と判断したため。日ページ（event-detail-redesign）と同じ型なので、行き来しても目が迷わない。
- **運営操作は既定=閉の `<details>`。** 開いた直後に見えるのは ヘッダー → フロー帯 → 日程 → 各セクション見出しだけ。日ページで確立した「既定表示では今どの段階かだけが見える」を踏襲。
- **進行管理セクションの中に日ごとのトグルを置かない。** 状態の切り替えは必ず日程表で日を選んでから。「どこで申込済にするのか」を1箇所に定める。
- **一括操作の後退3種（未申込に戻す・申し込まない・未払に戻す）は `<details>` に畳む。** 誤操作を1段遠ざける。前進3種はボタンのまま。
- **中止の日は行を残し `opacity` で落とす。** 「選べない」を色を足さずに伝える（朱は常時出さないという既存原則）。
- **戻り導線は固定文言（大会名を繰り返さない）。** 1日だけのグループでグループ名＝大会名になるため、名前を出すと自己リンクに見える。複数日のときだけグループ名を薄く添える。
- **戻り導線は sticky ヘッダーの外。** 中に入れるとスクロール中ずっと居座り、日ページの主役（大会名と申込フロー）を押しのける。

## 5. 状態（state）
- **通常:** `page-admin.html` / `page-member.html`（杉並AB・2日）
- **複数日で状態が食い違う:** `daytable-options.html`（多摩CDE・C だけ申込済）
- **1日だけ（本番の83%）:** `edge-cases.html` ①
- **締切超過:** `edge-cases.html` ②（フロー帯の該当ステップが warn）
- **共通項目の食い違い:** `edge-cases.html` ③（最も早い値＋朱の「日により異なる」）
- **中止の日が混ざる:** `edge-cases.html` ④

- **団体戦:** `edge-cases.html` ⑥（名簿・申込書のセクションが消えるだけ）
- **全日が中止:** `edge-cases.html` ⑦（フロー帯を丸ごと描かない。要件 AC-14）

## 6. 必要データ
- **表示フィールド:** グループ名（`deriveEntryGroupName` → null なら代表イベントの `title`）／各日の `event_date`・`title`・`eligible_grades`・`status`・`entry_status`・`payment_type`・`payment_status`／参加希望者数（`event_attendances.attend=true`・ゲスト除外）／自分の `attend`／共通7項目（`PROPAGATABLE_FIELD_KEYS`）／振込総額・級別内訳（`tallyEntryFeesForGroup`）／名簿・原本ファイル・オープンチャット・LINE紐付け・関連メール
- **仮データのまま確定した項目 ★実装で必ず実配線する:**
  - 参加希望者数（4名/3名/5名…）— 本番は出欠回答がまだほとんど無いため、密度を判断できるよう実物らしい値を置いた
  - 開催日・締切の一部を未来へずらしてある（生きた状態を見せるため）。**大会名・級・進行状態の組み合わせは本番実データのまま**
  - 名簿の件数・オープンチャット URL・Bot 名・振込先・関連メールの件名／差出人はすべて架空
  - **選手名・会員名はモックに一切出していない**（参加者欄の「青木/井上/遠藤」は架空）
- **集計・導出:** 振込総額＝級別参加料（A/B 2,500・C/D 2,000・E 1,500＝協会規定の実値）× 参加希望者数。フロー帯の集約規則は requirements §3.2.4。

## 7. インタラクション / レスポンシブ
- **選択チェックと行リンクの分離:** チェックボックスは行の左端に**独立したタップ標的**として置き、行の残り全体がその日の大会詳細へのリンク。
- **管理者と会員の差:** 日程表はチェックボックスの有無だけが違う。列も情報量も同じ（要件 AC-9）。
- **モバイル:** 375px 基準。**実測で横あふれゼロ**（`.page` の `scrollWidth == clientWidth == 373`）。日程表の大会名列の実測幅は 案A=59px / 案B=147px / 案C=89px、行高は 案A・案C=38px / 案B=59px。
- **ダーク:** 本アプリは和紙×藍墨の**ライト単一テーマ**（`globals.css` に dark 定義なし）のため対象外。

## 9. ガードレール準拠メモ
- 配色・フォント・角丸・影はすべて `docs/design/colors_and_type.css` の `--kg-*` から取得。**機械チェック済み**（生の hex / rgb / font-family リテラル・未定義トークン参照ともに 0 件）。
- トークン橋（プロジェクト直下 `colors_and_type.css`）は実コード `globals.css` と同期済み。差分は16進の大文字/小文字のみ。**更新不要**。
- 朱（`--kg-accent`）はデータ装飾に使わない既存規約に従い、**期限超過と共通項目の食い違いにだけ**使っている。
- 絵文字は不使用。日付は `M/D(曜)`・`tabular-nums`。

## 10. 残課題・実装への申し送り
- **ボードの区画判定（`classifyEntryBoard`）はグループ単位**なので、日程表のフェーズ1語のために**日ごとに同じ判定を回す**必要がある。純関数の入力単位を event 1件に変えられるかを技術計画で確認する。変えられない場合は、日程表用の軽い判定関数を別に切り出す（**語彙だけは必ず共有する**）。
- 共通項目の編集をインラインにするかサブページ（`/admin/entries/[groupId]/edit`）にするかは技術計画で決める。モックは「編集」リンクだけを描いてあり、どちらでも忠実度チェックリストを満たす。
- 日程表は選択状態を持つので client component。RSC payload に管理情報を載せない規約（`/events/[id]` と同じ）を守ること。

## 11. 要件への宿題（→ /define-feature entry-group-page）
> 収束ゲート＝この欄が空。**空＝収束済み**（2026-08-20）。

なし。round 1 で挙げた3件は round 2 でいずれも**要件変更なし**で決着した:

1. **長い大会名** — 名前は truncate のままにし、**日付と級**で日を見分ける。接頭辞を抜いて差分だけ出す案は、救いたい当の実例（`全日本かるた協会法人化30周年記念ABC` ＋ `〜記念A`）でちょうど破綻する（共通接頭辞が `〜記念A` まで伸び、片方の残りが空文字になる）ため不採用。代わりに**級の列を truncate しない**ことを忠実度チェックリストに固定した。要件 §3.2.3 は変更なし。
2. **導出 null のときの見出し** — 要件 §3.2.2 どおり代表イベントのタイトル（「九段E」）。見出し直下の subline に全開催日、その下の日程表に両方の大会名が出るので情報は失われない。連結見出しは 1 件と N 件で形が変わり一貫性を損なう。変更なし。
3. **シングルトンで日程表を畳むか** — 畳まない。本番の 83% に効く分岐を増やす価値がなく、**その1行がグループページから日ページへ行く唯一のリンク**なので畳むと導線が消える。変更なし。
