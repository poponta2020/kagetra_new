# guest-role 要件定義書

## 1. 概要

- **目的**: 「大会の参加登録だけができる」第4のロール **ゲスト（`guest`）** を追加し、北大かるた会の会員ではないサークル員（＝サークル活動には参加しているが、協会への登録会が他会である人）を、会のシステム上で「大会に出場予定がある人」として登録・保持できるようにする。
- **背景・動機**:
  - 将来 **match-tracker へ「近く大会に出場予定がある人」の一覧を渡したい**。その母集団は会員だけでは足りず、サークル員でも登録会が他会である人を含める必要がある。
  - 一方その人たちは**会経由で大会へ申し込まない**ため、申込書 xlsx にも会計の金額計算にも督促にも乗ってはいけない。
  - 出場予定そのものは既存の `event_attendances.attend = true` × `events.event_date` で既に表現できている。したがって本機能の実体は**新しいデータ構造を足すことではなく、その母集団に会員以外を入れられるようにすること**である。連携 API 自体は今回作らない（§5）。

## 2. ユーザーストーリー

**対象ユーザー**

| 役割 | この機能での関心 |
|---|---|
| ゲスト（サークル員・登録会は他会） | 会のアプリで大会一覧を見て、自分が出る大会に「参加する」と登録する |
| 管理者 | ゲスト用の招待リンクを発行して渡す。ゲストの登録が申込書・会計・督促に混ざらないまま運用できる |
| 会員 | ホームと大会詳細で「この大会に誰が出るか」を見るとき、ゲストも顔ぶれとして（ゲストと分かる形で）見える |

**利用シナリオ**

1. 管理者が会員管理画面から「**ゲスト用**」を選んで招待リンクを発行し、対象者へ渡す
2. ゲストが `/register/<token>` を開き LINE ログイン → **表示名・級・所属会**を入力して登録する
3. ゲストはボトムナビの「イベント」から大会詳細へ入り、「参加する」を押す
4. 会員・管理者は大会詳細の参加者欄とホームの出場タイムラインで、ゲストを含む顔ぶれを見る（ゲストにはその印が付く）
5. 管理者が申込書 xlsx を作ると、対象会員一覧にゲストは現れない。振込総額にも乗らない。申込管理ボードの参加希望者数にも数えられない
6. 登録会が北大に変わったら、管理者が会員編集画面でロールを「一般会員」へ変更する（逆も同様）

## 3. 機能要件

### 3.1 画面と遷移（画面インベントリ＋ナビゲーション地図）

新規画面は作らない。既存画面への追加・出し分けのみ。

| # | 画面 | 追加・変更内容 |
|---|---|---|
| S1 | 招待リンク発行（`/admin/members`） | 発行時に「**会員用 / ゲスト用**」の種別を選ぶ。発行済みリンクの一覧にも種別を表示する |
| S2 | 招待登録 `/register/[token]` | トークンの種別で入力フォームを出し分ける。ゲスト用は**表示名・級・所属会の3項目のみ**（姓名・かな・生年月日・住所・電話・全日協は聞かない） |
| S3 | ボトムナビ | ゲストは「**イベント」「設定」の2タブ**（会員・管理者は現行のまま6タブ。要件初稿の「会員5タブ」は member-mail-search でメールタブが一般会員へ開放される前の記述で、実装時に訂正した）。ログイン直後の入口は `/events` |
| S4 | 大会申込一覧 `/events`・過去 `/events-archive` | ゲストも閲覧可。表示内容は会員と同じ（参加人数にゲストを含む。姓の羅列にゲスト印は付けない） |
| S5 | 大会詳細 `/events/[id]` | 参加者欄にゲストを**ゲスト印つきで**表示し人数にも数える。「あなたの参加費」の行は**ゲストには出さない**。回答条件は R3 |
| S6 | ホーム `/dashboard` | 出場タイムラインの出場者チップにゲストを**ゲスト印つきで**載せる。**ゲスト自身はこの画面にアクセスできない** |
| S7 | 設定 `/settings` | ゲストには**表示のみ**（表示名・級・所属会）＋ログアウト。通知設定・申込書設定・会員一覧などの項目は出さない |
| S8 | 会員一覧・編集 `/admin/members`・`/admin/members/[id]/edit` | ロール表示に「ゲスト」を追加。ロール変更セレクトを**4択**（管理者/副管理者/一般会員/ゲスト）にする |
| S9 | 申込管理ボード `/admin/entries` | 参加希望者数からゲストを除く。**ゲスト自身はアクセスできない** |

**遷移（ゲスト視点）**

```
招待リンク /register/<ゲスト用token>
  └─ LINE ログイン → 表示名・級・所属会 → 登録完了
        └─ /events （ログイン後の既定の入口）
              ├─ /events/[id] → 「参加する」/「参加をキャンセル」
              └─ /events-archive
        └─ /settings （表示のみ＋ログアウト）
   上記以外の URL（/dashboard, /players, /tournaments, /mail, /admin/**, /events/new など）
   → すべて /403
```

見た目は既存のセクション・フォーム・チップのパターンをそのまま踏襲するため design-spec は作成しない（`design_required: false`）。ゲスト印の表現は「既存の級添字の隣に短いラベルを添える」程度で、視覚設計の判断を要さない。

### 3.2 ビジネスルール

#### R1. ゲストとは何か・どう作られるか

- ゲストは `users.role = 'guest'` の行。想定する対象は**サークル員だが協会への登録会が他会である人**に限る（無関係な外部の人を入れる運用はしない。ただしシステム上の制約としては課さない）。
- **作られる経路は「ゲスト用の招待リンクからの本人登録」だけ**。管理者が会員管理画面からゲスト行を直接作る導線は設けない。
- 招待リンクは**発行時に種別が固定される**。ゲスト用リンクを踏んだ人は必ずゲストになり、自己申告で会員になることはできない。1リンクを複数人が使い回せる既存仕様はそのまま。
- 登録時の入力は**表示名（必須）・級（必須）・所属会（必須）**の3項目。級は大会の対象級判定に使うため必須、所属会は「どこの会の人か」の記録として必須にする。姓名・かな等の PII は**取得しない**（申込書 xlsx に載せないため使い道がない）。
- 表示名は既存会員と同じ `users.name`（UNIQUE）に入る。既存の誰かと同名なら登録は失敗し、会員登録時と同じエラー表示になる。**姓と名の間にスペースを入れて入力してもらう**（一覧・参加者欄の苗字チップは `users.name` を最初の空白で分割して作るため。スペースが無い場合は表示名がそのまま苗字として出るだけで壊れはしないが、会員の表示と揃わない）。
- ゲスト行は `is_invited = true` で作られる（出欠回答の前提条件のため。§6 も参照）。

#### R2. ゲストができること（許可リスト方式）

ゲストに許すのは次だけ。**これ以外の画面・操作はすべて拒否する**（新しい画面が増えても既定で閉じている側に倒す）。

- 大会申込一覧 `/events`・過去のイベント `/events-archive` の閲覧
- 大会詳細 `/events/[id]` の閲覧と、自分の出欠回答（参加する／参加をキャンセル）
- 設定 `/settings` での自分の情報の閲覧とログアウト

特に**統計・戦績（`/players`・`/tournaments`）とメール（`/mail`）は一切使えない**。管理画面（`/admin/**`）・イベント作成編集・申込管理ボード・ホームも使えない。ナビに出さないだけでなく、**URL を直接叩いても `/403`** になる。

大会詳細の中で会員に見えているもの（参加者名・名簿・オープンチャット欄・級別定員・備考）は**ゲストにも同じように見える**。管理者専用の要素（進行管理・LINE 配信・関連メール）は従来どおり管理者だけに見える。

**API ルートハンドラ（`apps/web/src/app/api/**`）も同じ許可リストで塞ぐ ★重要**。これらは `(app)/` の配下ではないため、画面側のガードだけでは一切保護されない。「ログイン済みなら誰でも叩ける」会員向けのルートが実在する（`api/mail/attachments/[id]`・同 `preview/[page]` = 受信メールの添付本体とページ画像）ので、ゲストがこれを直接叩けば §6 で構造的に塞ぐと言っている情報に到達できてしまう。

| ルート | ゲスト |
|---|---|
| `api/auth/**` | 許可（認証そのもの） |
| `api/roster-files/[id]`・同 `preview/[page]` | **許可**（大会詳細の名簿ファイルビューア。R2 でゲストに見せると決めたもの） |
| `api/mail/attachments/**` | **拒否**（会員向け受信メール） |
| `api/admin/**` | 拒否（従来どおり管理者のみ。ゲスト対応は不要だが AC で確認する） |
| `api/line-broadcast/**`・`api/webhook/line`・`api/line-link/callback`・`api/zip` | 対象外（セッションではなくトークン／外部連携で保護される経路） |

#### R3. 出欠回答の条件

| | 一般会員 | ゲスト |
|---|---|---|
| 対象級（`eligible_grades`）に自分の級が含まれること | 必要 | **必要**（同じ） |
| 会内締切（`internal_deadline`）当日以前であること | 必要 | **不要（縛らない）** |
| `is_invited = true` | 必要 | 必要（登録時に必ず true） |

- 会内締切は「会が主催者へ申し込む準備の締切」であり、会経由で申し込まないゲストには意味がない。ゲストは締切後でも出場予定を追加・取消できる（match-tracker へ渡すデータの鮮度を保つため）。
- 級未設定のゲストは原理的に生じない（登録時必須）が、万一 NULL の行があれば対象級ありの大会には回答できない（会員と同じ扱い）。
- 回答不可のときに出す理由の文言は、ゲストでは「会内締切超過」を出さない。

#### R4. 会の申込作業からの除外 ★本機能の核

ゲストは会経由で申し込まないので、次の 5 箇所から**必ず除外する**。

| # | 対象 | 現在の母集団 | 対応 |
|---|---|---|---|
| E1 | 申込書 xlsx の対象会員（`/admin/entry-form/[groupId]` ステップ2） | `attend=true` ∧ 退会していない（role も招待フラグも見ない） | `role='guest'` を除外 |
| E2 | 参加費の集計（振込総額・級別内訳。支払締切リマインド／支払完了通知／進行管理パネルの3経路） | `attend=true` ∧ `is_invited=true` ∧ 対象級 | `role='guest'` を除外 |
| E3 | 申込管理ボードの参加希望者数 | `event_attendances` を単独で数える（`users` を join していない） | `users` を **inner join** して `role='guest'` を除外 |
| E4 | 毎朝の未申込督促 LINE（entry-overdue-alert） | **E3 とはコードを共有していない独立実装**。`collectOverdueEntries` の相関サブクエリが `event_attendances` を単独で数え、その式を「参加1名以上」の抽出条件・件数表示の両方で使い回している | 同サブクエリに `users` を join して `role='guest'` を除外（1つの式を共有しているので、抽出条件と文面の「参加 N名」が同時に直る） |
| E5 | 抽選の出場回数プレフィル | E1 の対象会員に対して算出 | E1 の除外により自動的に対象外 |

**結果として、ゲストだけが参加希望している大会は「参加希望者 0 名」として扱われ、督促も申込書も発生しない**（会として申し込む相手がいないので正しい）。

#### R5. 表示（誰にどう見えるか）

- **大会詳細の参加者欄**: ゲストも同じ欄に並べ、ゲストと分かる印を付ける。**人数（「参加者 N名」）にはゲストを含める**。
- **一覧（`/events`・`/events-archive`）の参加人数**: 詳細と数字が食い違わないよう**ゲストを含める**。姓の羅列にはゲスト印を付けない（情報密度を優先。誰がゲストかは詳細で分かる）。
- **ホームの出場タイムライン**: ゲストを出場者チップに載せ、ゲスト印を付ける。
  - ホームの出場者リストは「確定名簿があればそれが正・無ければ出欠回答へフォールバック」という 2 系統だが、**ゲストは会の申込名簿に載らないため、確定名簿があるグループでもゲストだけは出欠回答（`attend=true`）をそのまま採用して合流させる**。会員は名簿が正、ゲストは自己申告が正、という非対称を意図的に持つ。
- **「あなたの参加費」**: ゲストには出さない（会へ振り込むと誤解させないため）。
- **会員一覧**: ゲストは「ゲスト」ロールとして一覧に並ぶ。

#### R6. 通知

- **ゲストへはアプリから一切通知を送らない**（LINE 個別通知・Web Push とも）。通知対象を引くクエリにゲストが入らないことを保証する。
- 設定タブに通知設定の項目を出さない。
- 級別 LINE グループのメンバーシップは LINE 側で管理されておりアプリの管轄外なので、本要件の対象外（グループに実際に居るかどうかはアプリが決めない）。

#### R7. ロールの変更

- 会員編集画面のロール選択を **4 択（管理者 / 副管理者 / 一般会員 / ゲスト）** にする。管理者だけが変更できる、という既存の制約はそのまま。
- 一般会員 → ゲスト、ゲスト → 一般会員の双方向を許す（登録会の移動に対応）。
- **ゲストへの変更は昇格ではないので、既存の昇格制限（LINE 未紐付け・退会済みは `admin`/`vice_admin` にできない）は適用しない**。ゲストは `member` と同じ「制限なしで変更できる側」に置く。
- ゲストを直接 `admin` / `vice_admin` にする操作も、既存の昇格制限（LINE 紐付け済み・退会していない）を満たせば許す（禁止する理由がない）。
- ロール変更は即時反映され、対象者は再ログインなしで次のリクエストから新しい権限になる（既存挙動のまま）。
- **表示ロールのプレビュー切替（role-preview-switch）の選択肢に「ゲスト」は加えない**。認可は実効ロールで判定されるため、管理者がゲストビューへ切り替えると設定画面がゲスト向けの「表示のみ」に変わり、**ビューを戻すための切替セクション自体が消えて復帰できなくなる**。ゲストとしての見え方を確認したいときは、実際のゲストアカウントで確認する。したがってプレビューの選択肢は従来どおり管理者 / 副管理者 / 一般会員の3つ。

#### R8. エラー・境界条件

- ゲストが許可外の URL を直接開いた場合は `/403`。Server Action を直接呼んだ場合もサーバー側で拒否する（画面を出さないだけの防御にしない）。
- ゲスト用リンクで登録しようとした表示名が既存ユーザーと重複した場合は登録を拒否し、日本語のエラーを表示する。
- 級・所属会が未入力のゲスト登録は拒否する。
- 退会（`deactivated_at`）はゲストにも適用でき、退会済みゲストは会員と同様にログイン・回答ができない。
- 招待リンクの有効期限・失効（`revoked_at`）の扱いはゲスト用でも会員用と同じ。

## 6. 技術的制約・契約

- **マイグレーション（0057 想定）**:
  - `user_role` enum へ `guest` を追加する。PostgreSQL の `ALTER TYPE ... ADD VALUE` はトランザクション内での取り扱いに制約があるため、drizzle の migration ファイル上で単独ステートメントとして発行する。
  - `registration_invites` にリンク種別の列を追加する（既定は会員用。既存行は会員用として扱われ、挙動が変わらないこと）。
- **既存の権限判定との整合**: 既存コードの管理者判定は `role === 'admin' || role === 'vice_admin'` の形なので、`guest` は自動的に「非管理者」に落ちる。**危険なのは「ログイン済み会員なら誰でも」を前提にしている箇所**（`/admin/entries` など）で、ここは `guest` を明示的に弾く必要がある。**許可リスト（fail-closed）で塞ぎ、今後画面が増えてもゲストには既定で閉じている状態にする**。
- **`is_invited` は「ゲストかどうか」の判別に使えない**: ゲストも出欠回答のために `is_invited=true` が必要なため、参加費集計など `is_invited` で絞っている母集団には `role='guest'` の除外を**追加で**書く必要がある。
- **許可リストの実装場所**: 画面側だけでなく**ルートハンドラ（`src/app/api/**`）も同じ判定を通す必要がある**。`api/` は `(app)/` の配下ではないため、`(app)/layout.tsx` に書いたガードは API に一切効かない。判定そのものは 1 箇所（純関数＋共通ヘルパー）に置き、ページと API の両方から呼ぶ。
- **母集団定義の同期**: 参加費集計（`entry-fee-tally.ts`）と大会詳細の参加者一覧（`events/[id]/page.tsx`）が「1文字も違わない条件」であることは、既存機能の生きた契約として `docs/features/grade-entry-fee/requirements.md` の AC-9 に書かれている。今回この2つは**意図的に条件が分かれる**（参加者欄はゲストを含み、参加費はゲストを除く）ため、**同ファイルの AC-9 を「ゲスト除外を除いて同一」へ改訂し**、`entry-fee-tally.ts` のコメントにも分岐の理由を残す。改訂しないと、将来のレビューで実装が要件違反に見える。
- **申込管理ボードと督促の定義共有**: `/admin/entries` の区画判定（`entry-board-utils.ts` の純関数）と毎朝の督促バッチは同じ対象定義を使っている。ゲスト除外は**両方に同時に効く場所**（人数を数えるクエリ）で行い、定義の二重化を作らない。なお `/admin/entries` の人数クエリは現在 `event_attendances` を単独で数えており `users` を join していないため、ゲスト除外には join の追加が要る（`/events` 一覧のクエリとは別実装なので、片方だけ条件を変えられる）。
- **維持すべき既存挙動（回帰）**:
  - 会員・管理者・副管理者の権限、出欠回答条件、参加者欄、申込書の対象会員、参加費の総額と内訳、申込管理ボードの区画判定、督促の発火条件は**ゲストが存在しない環境では従来と完全に同一**であること
  - 会員用の招待リンク・登録フローの挙動と入力項目は変わらないこと
  - `unlinkLine` を `member` 限定にしている既存の防御（member-role-management で入れたもの）を**そのまま変えない**＝**ゲストの LINE 紐付けは解除できない**。ゲストは招待リンク登録時に必ず紐付いた状態で作られるので、この制限を維持すれば「未紐付けのゲスト行」という状態自体が発生しない（`/self-identify` の候補に現れる余地も無くなる）。ゲストが LINE アカウントを変えたときは、管理者・副管理者と同じく「一般会員へ降格 → 解除 → 再紐付け → ゲストへ戻す」の手順で対応する
- **セキュリティ**: ゲストは外部の会に所属する人なので、会員の PII（生年月日・住所・電話・全日協情報）へ到達する経路が無いことを構造的に担保する。現状これらは会員編集画面（管理者専用）と申込書作成画面（管理者専用）にしか出ないため、R2 の許可リストで塞がれる。
- **UI 規約**: 日本語表示。ロールの日本語ラベルは既存の `roleViewLabel`（`apps/web/src/lib/role-preview.ts`）に「ゲスト」を追加して再利用する（新しいラベルマップを作らない）。

## 7. 設計判断の根拠

- **新テーブルではなく既存の出欠データに乗せた理由**: 「出場予定がある人」は `event_attendances.attend=true` × `events.event_date` で既に完全に表現されている。ゲスト専用の出場予定テーブルを作ると、同じ事実が2箇所に書かれ、どちらが正かを常に判断し続けることになる。母集団に人を足すだけなら既存の画面・クエリがそのまま使える。
- **`users.role` に足し、別テーブルに分けなかった理由**: ゲストはログインし、出欠を回答し、参加者欄に並ぶ。会員とまったく同じ経路を通る主体なので、別テーブルにすると出欠・認証・表示のすべてに UNION が必要になる。除外が必要なのは 5 箇所（R4）だけなので、そちらを明示する方が総量が小さい。
- **`is_invited` を流用せず `role` で判別する理由**: ゲストは出欠回答のために `is_invited=true` が必要で、このフラグでは会員と区別できない。既存の `is_invited` ベースの母集団に**追加の条件**として `role` を書く形にする。
- **許可リスト（fail-closed）で塞ぐ理由**: 個別画面に「ゲストなら弾く」を書いて回ると、今後追加される画面が既定でゲストに開いてしまう。ゲストは会員でない人なので、漏れの方向を「閉じている」側に倒す。
- **会内締切でゲストを縛らない理由**: 会内締切は「会が主催者へ申し込む準備の締切」で、会経由で申し込まないゲストには意味を持たない。締切後に出場が決まった／取りやめたときに更新できないと、match-tracker へ渡すデータが実態からずれる。
- **参加者欄の人数にゲストを含め、申込管理ボードの人数には含めない理由**: 大会詳細の参加者欄は「誰が出るか（顔ぶれ）」を見る場所で、申込管理ボードの参加希望者数と督促は「会として何人ぶん申し込む必要があるか」を見る場所。同じ「人数」でも問いが違うので母集団を分ける。分けた事実はコード側にコメントとして残す。
- **確定名簿があるグループでもゲストは出欠回答を採用する理由**: 確定名簿は「会が申し込んだ結果」の権威であり、会経由で申し込まないゲストは原理的にそこに載らない。名簿を唯一の正としたままだと、確定名簿が入った瞬間にゲストが顔ぶれから消える。ゲストについては自己申告が唯一の情報源である、という非対称をそのまま仕様にする。
- **「あなたの参加費」をゲストに出さない理由**: 金額そのものは協会規定で共通だが、この行は会の振込フローの文脈にある。ゲストに見せると「会へ払う」と誤解させ、会計側にも「払ってくるはず」の期待を生む。
- **ゲストへの昇格制限を課さない理由**: 既存の昇格制限（LINE 未紐付け・退会済みは管理者になれない）は「権限を持つ行を第三者に名乗られない」ための防御。ゲストは権限を持たないので、同じ制限を課す理由がない。
- **PII を取得しない理由**: 会員から姓名・かな・住所等を集めているのは申込書 xlsx と協会への申込のためで、ゲストはそこに載らない。使い道のない個人情報を、外部の会に所属する人から集めない。
