# roster-file-adoption 要件定義書 — 名簿ファイル採用（パース不能名簿の救済導線）

## 1. 概要

### 目的
名簿（申込名簿・確定名簿）を**構造化パースせずファイル原本のまま採用**できる導線を作り、
「名簿がパースできないと大会の申込フェーズが進まない」問題を解消する。

### 背景・動機
- 決定論パーサ（roster-deterministic-v1）は本番で試した実名簿 3 件すべてで採用不能だった
  （ヘッダ誤検出・氏/名 2 列非対応・重複検証の全面ブロック）。様式は主催者ごとに無限に多様で、
  ルールベースでの完全対応は原理的に不可能。
- 構造化取込の本命は AI 抽出＋人間承認（P3「AI名簿→反映」）だが、腰を据えた別機能として取り組む。
  本機能は**それまでの間もフェーズ管理を止めない**ための恒久的な逃げ道（AI 取込導入後も、
  抽出に失敗する原本の受け皿として残る）。
- **2026-08-01 改修**: 初版出荷後の実運用で 3 点の課題が判明した。
  1. 名簿は基本「同グループの全級が 1 つの Excel」で来るが、**級ごとに別ファイル**で来る場合もある。
     現行は entry_group 単位でしか採用できず、級別名簿を区別して登録できない。
  2. 採用シートの対象候補が「直近の個人戦イベント全部」の列挙で、申込状況・取込状況を
     反映しない。取り込むべき大会を探す・選び間違えるコストが高い。
  3. パース取込（決定論パーサ→ドラフト承認）は実名簿で一度も機能せず、ファイル採用が
     事実上の唯一の取込経路になった。パース導線が並んでいると迷いを生むだけなので
     **UI 導線を退役**する（コード・テーブルは温存し、将来の AI 取込で再利用する）。

## 2. ユーザーストーリー

- **管理者・副管理者**: 主催者からメールで届いた名簿（Excel/PDF 等）を、パースの成否に関わらず
  「この大会の申込名簿／確定名簿の原本」として数タップで登録し、申込フェーズを進めたい。
  名簿がグループ全級まとめて 1 ファイルでも、級ごとに別ファイルでも、そのままの単位で登録したい。
  採用先の候補には「いま取り込むべき大会」だけが並んでいてほしい。
- **一般会員**: 大会詳細ページで確定名簿の原本ファイルを開き、自分や仲間の当落・組み分けを確認したい
  （構造化表示がなくても、原本さえ見られれば実用上は足りる）。

## 3. 機能要件

### 3.1 画面と遷移（画面インベントリ）

| 画面 | 変更 | 内容 |
|---|---|---|
| メール詳細 `/admin/mail-inbox/mail/[id]`（管理者） | 変更 | 各添付の「名簿ファイルとして採用」シートに**取込単位の選択（グループ統一／級別）**を追加し、候補を **3.2.7 の候補提示規則**で絞る。採用済み添付には採用状態（種別・対象・級）を表示し、解除もここから行う。**「大会名簿の取込」セクション（解析ボタン・名簿ドラフトカード）は表示しない**（3.2.8） |
| 大会詳細 `/events/[id]`（全会員） | 変更 | RosterSection のファイル名簿カード・補助リンクに、級別採用のファイルは**級ラベル**を付ける（表示規則は 3.2.3） |
| 名簿ファイルビューア `/roster-files/[id]`（全会員） | 不変 | 採用済みファイルをアプリ内で閲覧するページ（既存のまま） |
| 名簿ドラフト確認 `/admin/mail-inbox/roster-drafts/[id]`（管理者） | 導線退役 | ページ自体は温存（直 URL では従来どおり動く）。メール詳細からのリンクを消す |

見た目の詳細は既存パターン踏襲（採用シートは現行ボトムシートの拡張）。design-spec は作らない。

### 3.2 ビジネスルール

#### 3.2.1 採用（adopt）
- 採用できるのは **admin / vice_admin** のみ。
- 採用元は**メール添付（mail_attachments）のみ**。手動アップロードは対応しない
  （メール以外で入手した名簿は自分宛にメールして取り込む運用）。
- 採用時に指定するもの:
  - **名簿種別**（applicant / confirmed）
  - **取込単位**: 「グループ統一名簿」（＝グループの全級をカバーする 1 ファイル）か
    「級別名簿」（＝特定の級の名簿）かを選ぶ
  - **対象**: グループ統一なら**大会グループ（entry_group）**を 1 つ選ぶ。
    級別なら**グループ×級**を選ぶ（同一グループ内なら複数の級を同時に選べる —
    「A・B級名簿」のように複数級を 1 ファイルでカバーするがグループ全級ではない場合に使う）
  - **発表日**（任意。既定=メール受信日）
- 級の列挙元はグループ内イベント（個人戦・cancelled 除外）の `eligible_grades` の和集合。
  級情報が無いグループはグループ統一でのみ採用できる。
- **edition 紐付け・級別設定・抽選事実（lottery facts）は一切要求しない**（現行どおり）。
- 同一 entry_group × 種別に**複数ファイルを採用できる**（例: 秋田大会の「参加者一覧」と
  「参加費一覧」。候補フィルタで隠れている対象へは「すべて表示」トグルで到達する — 3.2.7）。
- **同一添付の二重採用は不可**（同じ添付は 1 箇所にしか採用できない。付け替えは解除→再採用。
  複数級をカバーする添付は、1 回の採用で複数級を指定する）。
- ファイルの実体は mail_attachments を正とし、**複製しない**（採用はポインタの登録）。
- Server Action が強制するのは**基本条件のみ**（対象グループが実在し個人戦の日を持つ・
  cancelled 除外・開催日が過去 30 日以降・指定した級がグループの級集合に含まれる・添付未採用）。
  3.2.7 の候補フィルタ（申込済み・未取込）は**強制しない** — 「すべて表示」トグル経由の採用が
  正規の逃げ道であるため。

#### 3.2.2 解除（release）
- admin / vice_admin は採用を解除できる。解除するとボード分類・大会詳細表示が採用前の状態に戻る。
- 解除してもメール添付そのものは消えない。

#### 3.2.3 大会詳細の表示規則（RosterSection）
- 種別ごとに:
  - **パース済み名簿（tournament_entry_rosters の有効版）がある** → 現行の構造化表示を主とし、
    採用済み原本ファイルがあれば補助リンクとして併記する。
  - **パース済みがなく、採用済みファイルがある** → 「〔確定名簿|申込名簿〕（原本ファイル）」として
    ファイル名の一覧カードを表示。各ファイルはビューアへ遷移できる。
  - どちらもない → 現行どおり（非表示）。
- **級別採用のファイルには級ラベルを付ける**（例「D級」「A・B級」）。グループ統一の採用
  （既存データ含む）はラベルなし。表示スコープは現行どおり entry_group 単位
  （グループ内のどの日の詳細からも全ファイルが見える）。
- 一般会員へ渡す情報は**ファイル名・採用種別・級・発表日・ビューア導線のみ**
  （取込元メール ID・採用者などの内部情報は RSC payload に含めない。PR #376 の教訓を踏襲）。

#### 3.2.4 申込フェーズ（申込管理ボード）との連動
- `hasConfirmedRoster` の定義は現行のまま:「**有効なパース済み confirmed 名簿がある ∨
  confirmed のファイル採用がある**」。級別採用の行も 1 行として数える（＝一部の級の確定名簿
  だけでもフェーズは進む。級単位の細分化はしない）。
- applicant のファイル採用は**ボード分類に影響しない**（現行仕様どおり。表示・記録のみ）。
- classify の判定条件・評価順・並び順キーは一切変えない。

#### 3.2.5 閲覧（ビューア）
- **ログイン済みの全会員**が閲覧・ダウンロードできる（現行どおり・変更なし）。
- 閲覧できるのは**採用済みファイルのみ**（fail-closed）。採用されていない添付・解除済みの添付は
  会員向け経路では 404。管理者向け既存ビューア（/admin/mail-inbox/attachments/[id]）は従来どおり。
- 表示は既存の添付プレビュー基盤（libreoffice → PDF → ページ画像）を流用（変更なし）。

#### 3.2.6 エラー・境界
- 対象グループに個人戦の日が 1 つも無い場合は候補に出さない（採用しても表示されずフェーズも
  動かない dead-end を防ぐ。現行の「個人戦のみ」制約のグループ版）。
- 既存の名簿ドラフト（pending_review / rejected）とは**独立**。ファイル採用はドラフトの状態を変えず、
  ドラフトの有無もファイル採用を妨げない。
- 添付が属するメールが削除されても採用レコードが宙に浮かないこと（FK CASCADE。現行どおり）。

#### 3.2.7 候補提示規則（2026-08-01 新設）★本改修の核
採用シートの対象候補は、既定で「いま取り込むべき対象」だけに絞る。

**基本条件（すべてのモード共通・「すべて表示」でも維持）**:
- グループ内に個人戦・cancelled 除外・開催日が過去 30 日以降の日が 1 つ以上あること。

**用語**:
- 「申込済み」= グループ統一候補では、グループ内のいずれかの日が `entry_status='applied'`。
  級別候補では、その級を `eligible_grades` に含む日のいずれかが `entry_status='applied'`。
- 「統一ファイルあり」= そのグループ×種別に級指定なしの採用がある。
- 「級ファイルあり」= そのグループ×種別×級の採用がある（複数級指定の採用は各級それぞれに数える）。

**既定フィルタ（種別×取込単位の 4 象限）**:

| | グループ統一の候補に出す条件 | 級別の候補に出す条件 |
|---|---|---|
| **申込者名簿** | 申込済み ∧ applicant の統一ファイルなし ∧ applicant の級ファイルが全級をカバーしていない | その級が申込済み ∧ applicant のその級ファイルなし ∧ applicant の統一ファイルなし |
| **確定名簿** | 申込済み ∧ confirmed の統一ファイルなし ∧ confirmed の級ファイルが全級をカバーしていない | その級が申込済み ∧ confirmed のその級ファイルなし ∧ confirmed の統一ファイルなし |

- **確定名簿の候補条件は申込名簿ファイルの有無を問わない**。「申込済みかつ名簿ファイル未取込」
  （抽選不要で申込者名簿がそのまま確定名簿として届くケース）と「申込名簿取込済みかつ確定名簿未取込」
  （通常フロー）の和集合は、上表の「申込済み ∧ 確定名簿未取込」に簡約される。
- 「未取込」の判定は**ファイル採用（tournament_entry_roster_files）のみ**を見る。パース済み名簿
  （tournament_entry_rosters）は判定に含めない（パース取込は UI 退役済み＝新規に増えない。
  ボードの hasConfirmedRoster 判定は現行どおりパース済みも見る — 3.2.4）。
- 級別ファイルが一部の級だけ採用済みのグループは、**全級がカバーされるまでグループ統一の
  候補にも出し続ける**（ユーザー判断 2026-08-01。級別で始めても統一 1 ファイルで残りをまとめて
  カバーする運用を許す）。
- **「すべて表示」トグル**: シート内のトグルで既定フィルタを外し、基本条件のみの全候補
  （グループまたはグループ×級）を出す。複数ファイル採用（秋田パターン）・申込済みマーク忘れの
  大会への採用はここから行う。
- 候補の表示名は申込管理ボードと同じグループ表示名規約（通称ベース。級別候補は「表示名＋級」）。

#### 3.2.8 パース取込導線の退役（2026-08-01 新設）
- メール詳細の**「大会名簿の取込」セクションを表示しない**（解析ボタン
  `RosterParseButton`・名簿ドラフトカード・確認画面へのリンクを含めて非表示）。
- **コードは削除しない**: パーサ・Server Action（triggerRosterParse / 承認 / 却下）・
  `/admin/mail-inbox/roster-drafts/[id]` ページ・関連テーブル（tournament_roster_import_drafts /
  tournament_entry_rosters ほか）・既存テストはすべて温存する。直 URL では従来どおり動く。
  将来の AI 取込（P3）で承認 UI・materialize を再利用する想定。
- パース済み名簿の**表示系は不変**: RosterSection の構造化表示・ボードの hasConfirmedRoster の
  パース済み判定はそのまま（本番にパース済み名簿は現状 0 件のため実表示への影響はない）。

## 5. Non-goals

- 決定論パーサの修正・削除（UI 導線の退役のみ。コード・テーブル・テストは温存）
- AI による名簿構造化取込（P3「AI名簿→反映」として別機能で腰を据えて実施）
- 「却下済みドラフトの原本を再解析できない」バグの修正（独立バグ。別途 quickfix）
- edition 紐付け導線の改善・抽選事実（lottery facts）・当落線への反映（ファイル名簿は統計に一切寄与しない）
- 手動ファイルアップロード（メール添付以外の取込元）
- ファイル名簿からの会員突合・出場回数カウント（構造化データがないため原理的に不可）
- 申込名簿の有無をボード分類に組み込む変更
- hasConfirmedRoster の級単位細分化（一部の級の確定でもグループごとフェーズが進む現行を維持）
- 候補フィルタ条件の Server Action 強制（「すべて表示」トグルが正規の逃げ道）

## 6. 技術的制約・契約

- **壊してはいけない既存挙動**: classify の判定条件・評価順・並び順キー／hasConfirmedRoster の
  定義（パース済み ∪ ファイル採用）／パース済み名簿の表示・版管理・承認フローのコード動作
  （UI 導線退役後も直 URL・テストで動くこと）／メール添付の既存管理者ビューア／
  会員向けビューア 3 経路の認可・disposition 規約。
- **データ**: ファイル実体は mail_attachments が唯一の正（複製禁止）。採用レコードは entry_group に
  帰属し、級別採用は級情報を追加で持つ。**既存行は級なし＝グループ統一として解釈**する
  （backfill 不要のスキーマ進化にする）。同一添付の二重採用不可（UNIQUE）は維持
  — 複数級カバーは 1 採用レコードで表現する。
- **セキュリティ**: 採用・解除は admin / vice_admin。会員向け配信 route は現行のまま。
  RSC payload への内部列漏洩禁止（級は公開情報として追加してよい）。
- **未解決の技術論点（→技術計画）**: 級情報の持ち方（grade 配列列 vs 別表）／候補クエリの構成
  （グループ集約・表示名導出・採用状況の突合を 1 クエリでどこまでやるか）／採用 Server Action の
  シグネチャ変更（eventId → entryGroupId + grades）と既存テストの改修範囲。

## 7. 設計判断の根拠

- **ファイル採用を「恒久的な逃げ道」と位置づける**: AI 取込導入後も抽出失敗はゼロにならない。
  フェーズ管理（会の進行）と構造化データ（統計）を分離し、前者はファイルだけで進められるようにする。
- **メール添付のみ**: 今回の実例 3 件は全てメール経由。手動アップロードは面を増やすだけで、
  メール転送運用でカバーできる（ユーザー判断）。
- **会員全員に原本公開**: パース済み名簿が既に氏名・所属を全会員に表示しており、原本も同等の情報。
  会員が自分の当落を確認できる実用価値を優先（ユーザー判断）。
- **confirmed のみフェーズ連動**: 現行 classify が見るのは confirmed のみ。applicant まで組み込むのは
  判定ロジックの変更＝リスク増で、得られるものがない（ユーザー判断）。
- **パース済み優先・ファイルは補助**: 構造化表示の方が情報量が多い。原本への導線は常に残す（ユーザー判断）。
- **候補フィルタは UI の案内・Server Action は強制しない**（2026-08-01）: 「すべて表示」トグルが
  複数ファイル採用（秋田パターン）と申込済みマーク忘れの正規の逃げ道。フィルタをサーバー強制すると
  トグルの意味が消える。
- **級別が一部済みでもグループ統一候補は全級カバーまで残す**（ユーザー判断 2026-08-01）:
  級別で届き始めても、残りが統一 1 ファイルでまとめて届く運用があり得るため。
- **パース UI は退役・機能は温存**（ユーザー判断 2026-08-01）: 実名簿で一度も機能せず、導線が
  並ぶと迷いを生む。将来の AI 取込（P3）が承認 UI・materialize を土台に使うため削除はしない。
- **確定名簿候補の条件簡約**: 「申込済み∧名簿未取込」∨「申込名簿取込済み∧確定未取込」は
  「申込済み∧確定未取込」と同値（申込名簿の有無は確定名簿の取込可否に影響しない）。
