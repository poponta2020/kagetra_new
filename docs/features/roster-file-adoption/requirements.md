# roster-file-adoption 要件定義書 — 名簿ファイル採用（パース不能名簿の救済導線）

## 1. 概要

### 目的
名簿（申込名簿・確定名簿）を**構造化パースせずファイル原本のまま採用**できる導線を作り、
「名簿がパースできないと大会の申込フェーズが進まない」問題を解消する。

### 背景・動機
- 決定論パーサ（roster-deterministic-v1）は本番で試した実名簿 3 件すべてで採用不能だった
  （ヘッダ誤検出・氏/名 2 列非対応・重複検証の全面ブロック）。様式は主催者ごとに無限に多様で、
  ルールベースでの完全対応は原理的に不可能。
- 構造化取込の本命は AI 抽出＋人間承認（P3「AI名簿→反映」）だが、腰を据えた別機能として取り組む。
  本機能は**それまでの間もフェーズ管理を止めない**ための恒久的な逃げ道（AI 取込導入後も、
  抽出に失敗する原本の受け皿として残る）。
- 現行の実害: 事前払い・未振込の大会は、確定名簿が取り込めない限り申込管理ボードで
  「申込完了・抽選待ち」に滞留し続ける（`classify` が `hasConfirmedRoster` を要求）。

## 2. ユーザーストーリー

- **管理者・副管理者**: 主催者からメールで届いた名簿（Excel/PDF 等）を、パースの成否に関わらず
  「この大会の申込名簿／確定名簿の原本」として数タップで登録し、申込フェーズを進めたい。
- **一般会員**: 大会詳細ページで確定名簿の原本ファイルを開き、自分や仲間の当落・組み分けを確認したい
  （構造化表示がなくても、原本さえ見られれば実用上は足りる）。

## 3. 機能要件

### 3.1 画面と遷移（画面インベントリ）

| 画面 | 変更 | 内容 |
|---|---|---|
| メール詳細 `/admin/mail-inbox/mail/[id]`（管理者） | 変更 | 各添付に「名簿ファイルとして採用」導線を追加。対象イベント（→ entry_group）と名簿種別（申込／確定）を選んで採用する。採用済み添付には採用状態（種別・対象大会）を表示し、解除もここから行う |
| 大会詳細 `/events/[id]`（全会員） | 変更 | RosterSection に「原本ファイル」表示を追加（表示規則は 3.2.3） |
| 名簿ファイルビューア（全会員・新設） | 新規 | 採用済みファイルをアプリ内で閲覧するページ（既存の添付プレビュー基盤＝ページ画像化を流用）。ダウンロード導線も持つ |

見た目の詳細は既存パターン踏襲（メール取込系の管理 UI・RosterSection の既存カード）。design-spec は作らない。

### 3.2 ビジネスルール

#### 3.2.1 採用（adopt）
- 採用できるのは **admin / vice_admin** のみ。
- 採用元は**メール添付（mail_attachments）のみ**。手動アップロードは対応しない
  （メール以外で入手した名簿は自分宛にメールして取り込む運用）。
- 採用時に指定するもの: **対象イベント**（そのイベントの entry_group に帰属。グループ内の全日から同一に見える）・
  **名簿種別**（applicant / confirmed）・**発表日**（任意。既定=メール受信日）。
- 対象イベントの候補条件は既存のメール⇔イベント紐付けと同じ（cancelled 除外・開催日が過去30日以降 = `linkable-events.ts` の条件を共有）。
- **edition 紐付け・級別設定・抽選事実（lottery facts）は一切要求しない**（これが現行承認フローとの本質的な違い。
  entry_group さえあれば採用できる）。
- 同一 entry_group × 種別に**複数ファイルを採用できる**（例: 秋田大会の「参加者一覧」と「参加費一覧」）。
- **同一添付の二重採用は不可**（同じ添付は 1 箇所にしか採用できない。付け替えは解除→再採用）。
- ファイルの実体は mail_attachments を正とし、**複製しない**（採用はポインタの登録）。

#### 3.2.2 解除（release）
- admin / vice_admin は採用を解除できる。解除するとボード分類・大会詳細表示が採用前の状態に戻る。
- 解除してもメール添付そのものは消えない。

#### 3.2.3 大会詳細の表示規則（RosterSection）
- 種別ごとに:
  - **パース済み名簿（tournament_entry_rosters の有効版）がある** → 現行の構造化表示を主とし、
    採用済み原本ファイルがあれば補助リンクとして併記する。
  - **パース済みがなく、採用済みファイルがある** → 「〔確定名簿|申込名簿〕（原本ファイル）」として
    ファイル名の一覧カードを表示。各ファイルはビューアへ遷移できる。
  - どちらもない → 現行どおり（非表示）。
- 一般会員へ渡す情報は**ファイル名・採用種別・発表日・ビューア導線のみ**
  （取込元メール ID・採用者などの内部情報は RSC payload に含めない。PR #376 の教訓を踏襲）。

#### 3.2.4 申込フェーズ（申込管理ボード）との連動
- `hasConfirmedRoster` の定義を「**有効なパース済み confirmed 名簿がある ∨ confirmed のファイル採用がある**」に拡張する。
  これにより事前払い・未振込の大会が「申込完了・抽選待ち」→「名簿確定・要振込」へ進む。
- applicant のファイル採用は**ボード分類に影響しない**（現行仕様どおり。表示・記録のみ）。
- classify の判定条件・評価順・並び順キーはこの定義拡張以外一切変えない。

#### 3.2.5 閲覧（ビューア）
- **ログイン済みの全会員**が閲覧・ダウンロードできる（パース済み名簿が既に氏名・所属を全会員へ表示している
  のと同等の扱い）。
- 閲覧できるのは**採用済みファイルのみ**（fail-closed）。採用されていない添付・解除済みの添付は
  会員向け経路では 404。管理者向け既存ビューア（/admin/mail-inbox/attachments/[id]）は従来どおり。
- 表示は既存の添付プレビュー基盤（libreoffice → PDF → ページ画像。xlsx 対応済み）を流用し、
  iOS PWA の添付 disposition 問題（白画面死）を踏まないこと（ページ画像 inline 表示を主、
  ダウンロードは副導線）。

#### 3.2.6 エラー・境界
- 対象イベントに entry_group がない状態は存在しない（全イベントが group を持つ。0 件なら採用フォームにイベント候補が出ないだけ）。
- 既存の名簿ドラフト（pending_review / rejected）とは**独立**。ファイル採用はドラフトの状態を変えず、
  ドラフトの有無もファイル採用を妨げない。
- 添付が属するメールが削除されても採用レコードが宙に浮かないこと（FK の挙動を技術計画で確定）。

| AC-1 | 管理者はメール詳細から添付を対象イベント＋種別（申込/確定）を指定してファイル名簿として採用できる（Server Action が採用レコードを作る） | auto-test |

## 5. Non-goals

- 決定論パーサの修正（ヘッダ検出・氏/名 2 列・重複判定の緩和）— AI 取込機能の要件定義時に統廃合を判断
- AI による名簿構造化取込（P3「AI名簿→反映」として別機能で腰を据えて実施）
- 「却下済みドラフトの原本を再解析できない」バグの修正（独立バグ。別途 quickfix）
- edition 紐付け導線の改善・抽選事実（lottery facts）・当落線への反映（ファイル名簿は統計に一切寄与しない）
- 手動ファイルアップロード（メール添付以外の取込元）
- ファイル名簿からの会員突合・出場回数カウント（構造化データがないため原理的に不可）
- 申込名簿の有無をボード分類に組み込む変更

## 6. 技術的制約・契約

- **壊してはいけない既存挙動**: classify の判定条件・評価順・並び順キー（hasConfirmedRoster の定義拡張のみ）／
  パース済み名簿の表示・版管理・承認フロー／メール添付の既存管理者ビューア。
- **データ**: ファイル実体は mail_attachments が唯一の正（複製禁止。ストレージ肥大対策の既存方針に従う）。
  採用レコードは entry_group に帰属。添付削除時に採用レコードが残骸にならない FK 設計。
- **セキュリティ**: 採用・解除は admin / vice_admin。会員向け配信 route は「採用済みファイルのみ」の
  fail-closed 認可＋既存の blocklist / disposition 規約（iOS PWA 白画面死対策の inline ページ画像方式）に従う。
  RSC payload への内部列漏洩禁止。
- **未解決の技術論点（→技術計画）**: 採用レコードのテーブル設計（新テーブル vs tournament_entry_rosters の
  拡張）／会員向けビューアの route 構成（既存 attachment-preview 流用の具体形）／FK の onDelete 挙動。

## 7. 設計判断の根拠

- **ファイル採用を「恒久的な逃げ道」と位置づける**: AI 取込導入後も抽出失敗はゼロにならない。
  フェーズ管理（会の進行）と構造化データ（統計）を分離し、前者はファイルだけで進められるようにする。
- **メール添付のみ**: 今回の実例 3 件は全てメール経由。手動アップロードは面を増やすだけで、
  メール転送運用でカバーできる（ユーザー判断）。
- **会員全員に原本公開**: パース済み名簿が既に氏名・所属を全会員に表示しており、原本も同等の情報。
  会員が自分の当落を確認できる実用価値を優先（ユーザー判断）。
- **confirmed のみフェーズ連動**: 現行 classify が見るのは confirmed のみ。applicant まで組み込むのは
  判定ロジックの変更＝リスク増で、得られるものがない（ユーザー判断）。
- **パース済み優先・ファイルは補助**: 構造化表示の方が情報量が多い。原本への導線は常に残す（ユーザー判断）。
