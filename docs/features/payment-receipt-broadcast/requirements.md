# payment-receipt-broadcast 要件定義書

## 1. 概要

- **目的**: 会計が参加費を振り込んだあと、その支払明細（振込明細の写真）を証憑として景虎に登録し、大会別 LINE グループへ「振込完了 ＋ 景虎上の想定金額 ＋ 明細の写真」を1回の操作で流せるようにする。
- **背景・動機**: 現在は「支払済にする」を押すと LINE グループへ `参加費の振り込みが完了しました。` の固定文だけが流れる。実際に正しい金額が振り込まれたかはグループ内で目視確認しているが、明細は会計が手作業で LINE に貼っており、景虎側には何も残らない。金額の確認も「いくらのはずだったか」がグループに出ていないため各自の記憶頼みになっている。
- **改修対象**: 既存の申込グループページ（`/admin/entries/[groupId]`）の一括操作「支払済にする」。**ボタン名は「支払報告」へ改称する。**

> ★ご依頼文では「申込済みにするボタン」でしたが、ヒアリングの結果、振込は**名簿確定後**（`@会計` への振込連絡を受けてから）に行う運用と確認できたため、対象は**「支払済にする」ボタン**とします。

## 2. ユーザーストーリー

- **対象ユーザー**: 管理者・副管理者（実運用では会計担当。会計フラグ `users.is_treasurer` は識別専用で権限ではないため、認可は既存どおりロールで判断する）
- **ユーザーの目的**: 振り込んだ事実と証憑を記録として景虎に残しつつ、確認相手（大会 LINE グループ）へ1回の操作で届けたい。
- **利用シナリオ**:
  1. 名簿確定後、グループページから `@会計` へ振込連絡（金額つき）を送る（**既存機能**）
  2. 会計が銀行で振り込み、振込明細の写真を撮る
  3. グループページの日程表で日を選び「**支払報告**」を押す
  4. 開いたシートで明細写真を最大3枚選ぶ → 送信内容（文言＋画像）をプレビューで確認 → 実行
  5. 大会 LINE グループに「振込完了＋想定金額＋確認依頼」のテキストと明細画像が流れ、グループ内で金額の一致を確認する
  6. 証憑はグループページに記録として残り、送信に失敗したときは同じ内容を再送できる

## 3. 機能要件

### 3.1 画面と遷移（見た目は design-spec.md 参照）

| 画面 | 位置づけ | 今回の変更 |
|------|----------|------------|
| 申込グループページ `/admin/entries/[groupId]` | 管理者の申込運用の中心（既存） | ①一括操作バーのボタン名を「支払済にする」→「**支払報告**」 ②押下でシートを開く ③進行管理「支払状態」行の中に**支払報告の履歴**（回ごと・証憑サムネ・再送）を追加 |
| 支払報告シート（**新規**・グループページ内） | 証憑の選択とプレビュー | 写真選択（最大3枚）→ 送信内容プレビュー（文言＋画像）→ 実行／スキップ |
| 証憑画像の公開取得 URL（**新規**・認証なし） | LINE の画像フェッチャが取りに来る先 | 推測不能トークンでのみ1枚を返す |
| 大会別 LINE グループ | 確認の場（既存 Bot） | テキスト1通＋証憑画像 1〜3通 |

遷移:

```
グループページ ──「支払報告」押下──▶ 支払報告シート
                                       ├─ 写真0枚のまま実行 ──▶ 現行と同一の挙動（回帰）
                                       └─ 写真1〜3枚 ──▶ プレビュー ──▶ 実行
                                                                    └─▶ 状態更新＋LINE送信＋履歴に1行追加
グループページ（履歴の行）──「再送」──▶ 同じ内容をもう一度 LINE へ
```

### 3.2 ビジネスルール

#### 3.2.1 対象と権限

1. 「支払報告」の対象条件は現行 `setPaymentsPaid(ids, true)` を一切変えない: **事前払い（`payment_type='advance'`）∧ 未払 ∧ 同一グループ**の日だけが `paid` に遷移し、`cancelled` の日は LINE 通知の対象から外れる。
2. 操作できるのは管理者・副管理者（現行の `requireAdminSession` と同じ）。一般会員には証憑もシートも履歴も見えない（グループページの管理者専用領域）。
3. 現地払い・支払タイプ未設定の日は現行どおり「支払報告」の対象にならない（ボタンが有効にならない）。**証憑を必須にしないので、この分岐は今回も一切変わらない。**

#### 3.2.2 証憑のアップロード

4. 証憑は**任意**。0枚のまま実行した場合は、現行の「支払済にする」と完全に同一の挙動になる。
5. **1回の支払報告につき最大3枚**。4枚目以降は選べない（運用で回避する前提）。
6. 受け付ける形式は **JPEG / PNG のみ**。PDF・HEIC は受け付けない（`sharp` のプリビルドバイナリが HEVC 方式の HEIC をデコードできないため。iOS はカメラロールから選んだ写真を既定で JPEG に変換して渡すので、実運用の支障は小さい）。HEIC を選ばれたときは「カメラロールから選び直す」よう促すエラーを出す。
7. LINE の画像メッセージ制約（JPEG・10MB 以内・4096×4096 以内）に収まるよう、サーバー側で必要に応じて縮小する。縮小しても収まらない画像は、その1枚だけ送信から外し、画面に理由を出す。
8. **画像の内容は一切チェックしない**（金額の読み取り・照合・OCR はしない）。一致確認は LINE グループ上で人がやる。

#### 3.2.3 想定金額の決定

9. 文言に載せる「景虎上で想定される金額」は次の優先順で決める:
   1. そのグループの**振込連絡が送信済み**（`entry_group_payment_notices.last_sent_at` が非 NULL）なら、そのとき保存された総額（`total_jpy`）。＝「振り込んでくださいと伝えた額」と必ず一致する
   2. 送信済みの振込連絡が無ければ、その場で `tallyEntryFeesForGroup` により集計した振込総額
   3. いずれも算出できない（`totalJpy` が `null`）なら**金額行と確認依頼文をまるごと省く**
10. 金額は**状態を `paid` へ変える前に確定させる**。`tallyEntryFeesForGroup` の母集団は「非中止 ∧ 事前払い」で支払済の日を除外しないため現時点では順序で値は変わらないが、支払済を除外する集計（`payment-notice-context`）が隣にある以上、順序を仕様として固定しておく。
11. 級未設定で総額に未算入の人がいるときは注記（`※級未設定 N名は未算入`）を文言に入れる。**注記が付くのは金額を 9-ii（その場の集計）で出したときだけ**。9-i の振込連絡の額は管理者が人数を確認して送った確定値なので注記しない。
12. 金額はグループ全体の総額を使う（選択した日だけの部分集計はしない）。振込は実務上グループ単位で1回であり、振込連絡の額とも揃うため。

#### 3.2.4 LINE への送信

13. 送信は **1回の push で テキスト1通 ＋ 画像1〜3通**。文言は既存の完了通知に追記する形にする:

```
参加費の振り込みが完了しました。

景虎上の想定金額は 12,500円 です。
※級未設定 2名は未算入
添付の明細と金額が一致しているかご確認ください。
```

  - 証憑0枚のときは現行どおり `参加費の振り込みが完了しました。` の1通のみ（金額行も確認依頼文も出さない＝完全な回帰）
  - 金額が出せないとき（9-iii）は `参加費の振り込みが完了しました。` ＋ 画像のみ
14. **証憑が1枚以上あるときは、`payment_paid` の once-ever 判定（`UNIQUE(event_id, type)`）に関わらず必ず送信する。** 未払に戻して再度支払報告した場合に証憑が届かなくなるのを避けるため。証憑0枚のときは現行どおり claim できた集合だけに送る（既存の重複防止をそのまま維持）。
15. グループに `linked` な LINE 連携が無いときは送信をスキップし、状態変更と証憑の保存だけ行う。画面に「LINE 未連携のため送信していない」旨を出す。
16. 送信の失敗は状態変更を巻き戻さない（既存の best-effort 規律を維持）。失敗は履歴の行に残り、再送で回復する。

#### 3.2.5 記録と再送

17. 証憑は**支払報告1回ぶんを1件の記録**としてグループに紐づけ、時系列で残す（誰が・いつ・どの日を対象に・いくらの想定額で・何枚送ったか・送信できたか）。
18. 履歴の各行に**再送**ボタンを置く。再送は**その回の送信を丸ごと送り直す**（文言は送信時の金額スナップショットを再現し、そのときの画像をそのまま送る）。
19. 「未払に戻す」を実行しても**証憑と履歴は消さない**。再度支払報告すれば新しい記録が1件増える。
20. 証憑を送らずに支払報告したあと、後日明細だけを追加送信する導線は作らない（運用で会計が LINE に直接貼る）。

#### 3.2.6 エラー・境界

21. 4枚目以降の選択、対応外の形式、送信中の二重実行はいずれも画面側で防ぎ、サーバー側でも fail-closed に拒否する（クライアントの入力を信用しない）。
22. 選択した日に対象（advance ∧ unpaid）が1日も無いときは現行どおりボタンが無効。
23. 送信前プレビューでは、実際に送られる文言と画像をそのまま見せる（振込連絡と同じ規律）。

## 5. Non-goals

- **画像内容のチェック**（OCR・金額読み取り・自動照合・改竄検知）。確認は LINE グループ上で人がやる
- 4枚以上の証憑（運用で回避）
- PDF の証憑アップロード（JPEG / PNG のみ）
- HEIC の証憑アップロード（サーバー側でデコードできないため。変換ライブラリの追加もブラウザ側変換もしない）
- 「申込済にする」への証憑添付（振込タイミングは名簿確定後のため対象外）
- 一般会員向けの証憑閲覧 UI（管理者・副管理者のみ）
- 証憑を上げずに支払報告したあと、後日証憑だけを追加送信する導線
- 現地払い・支払タイプ未設定への支払報告の拡張
- 会計フラグ（`users.is_treasurer`）を認可に使うこと（識別専用のまま）
- 証憑の自動削除・保存期間ポリシー（当面は消さない）
- 振込連絡（`entry_group_payment_notices`）側の仕様変更

## 6. 技術的制約・契約

### 守るべき既存挙動

- `setPaymentsPaid` の対象条件（advance ∧ unpaid ∧ 同一グループ ∧ cancelled 除外）と、状態変更を巻き戻さない best-effort 送信の規律
- 証憑0枚の経路は現行と**同一の文面**（`参加費の振り込みが完了しました。`）
- `event_lifecycle_notifications` の `UNIQUE(event_id, type)` による once-ever 判定そのものは変更しない（証憑ありのときに送信を claim から独立させるだけ）
- 「支払済にする」→「支払報告」は**表示ラベルの変更のみ**。内部の状態名（`payment_status='paid'`・`payment_paid`）は変えない
- 振込連絡（`entry_group_payment_notices`）は読み取るだけで書き換えない

### 契約・データ

- LINE 画像メッセージ: `originalContentUrl` / `previewImageUrl` は **HTTPS 必須・JPEG・10MB 以内・4096×4096 以内**（`PUBLIC_BASE_URL` の https 検証は既存）
- 証憑は記録として**永続保存**する（既存の `image-cache.ts` はプロセス内メモリで永続ではないため、そのままでは証憑の置き場にできない）
- `attachment_share_tokens` は `mail_attachment_id` が `NOT NULL UNIQUE` の FK で、**証憑のトークンをそのままは載せられない**
- 権限: 管理者・副管理者のみ。証憑の公開取得 URL だけは認証なし（LINE のフェッチャが取りに来るため。既存の添付共有トークンと同じ考え方で、推測不能トークン＋失効で守る）

### 未解決の技術論点（→ 技術計画フェーズで解決する）

1. 証憑バイト列の保存先（`bytea` の新テーブル。既存 `mail_attachments` / `entry_form_drafts` に前例あり）とテーブル分割（送信1回＝親 / 画像1枚＝子）
2. 公開取得 URL の方式（新トークン列を持つか、既存 `attachment_share_tokens` を汎用化するか）と失効の扱い
3. ~~`sharp` の HEIC デコード可否~~ → **解決済み（2026-09-04）**。sharp 0.34 / libvips 8.17.3 の `heif` 入力は対応拡張子が `.avif` のみで HEVC 方式の HEIC はデコード不可。ユーザー判断により **JPEG / PNG のみ**へ後退（§3.2.2-6）
4. アップロードのトランスポート（Server Action の `FormData` に `File` を載せる経路。既存の前例は `admin/entry-form/[groupId]/Step1Template.tsx` の1件のみ）とサイズ上限
5. 送信メッセージ本文をスナップショットとして保存するか、金額だけ保存して都度組み立てるか（再送の再現性 AC-18）

## 7. 設計判断の根拠

- **対象を「支払済にする」にした**: 支払明細は振込の証憑であり、この会の運用では振込は名簿確定後（`@会計` への振込連絡を受けてから）に行われる。申込時点は抽選前で振込額が確定しない（`entry_applied_treasurer` の文面が「振込連絡は名簿確定時に連絡します。」と予告しているのはこのため）
- **証憑を任意にした**: 必須にすると、明細が手元に無い状態で支払報告できなくなり既存フローが止まる。現地払い・未設定は元よりボタンの対象外なので、任意化だけで回帰を避けられる
- **金額は振込連絡の保存値を優先**: 「振り込んでくださいと伝えた額」と「一致を確認してほしい額」がズレないため。名簿がその後変動しても、確認の基準は伝えた額であるべき
- **証憑ありのとき送信を claim から独立させた**: once-ever は「同じ完了通知を2度流さない」ための仕組みで、証憑の配達を止めるためのものではない。未払へ戻して再度支払報告する運用で証憑が届かないのは事故になる
- **ボタン名を「支払報告」にした**: 押下時の行為が「状態を変える」だけでなく「証憑を添えて報告する」に広がるため

## 8. 画面の作り方の指針（/design-screen は実施しない）

ユーザー判断により design-screen（視覚の作り込み）は行わない。**既存プリミティブと既存画面の規約をそのまま踏襲する**こと。新しい色・フォント・余白体系を発明しない。

- **支払報告シート**: 既存のボトムシート規約（`createPortal(document.body)` + `.modal-overlay-h`）を踏襲。1枚のシート内で「写真を選ぶ → 送信内容プレビュー → 実行」を縦に並べ、ステップ分割はしない
- **写真の見せ方**: 選択済みは正方形サムネの横並び（最大3枚）＋各サムネに削除ボタン。3枚に達したら追加ボタンを消す
- **プレビュー**: 実際に送る本文を `whitespace-pre-wrap` でそのまま表示（`PaymentNoticeSection` のプレビューと同じ流儀）
- **実行ボタン**: 写真0枚のときもラベルは「支払報告」のまま（スキップ用の別ボタンを作らない）。押下時の確認ダイアログは既存の `GroupDayTable` の文言をそのまま使う
- **履歴**: 進行管理セクションの「支払状態」行の中に `FlatTable` の行として時系列で置く。1行＝1回の支払報告（日時・実行者・想定額・枚数・状態）＋サムネ＋「再送」リンク
- **注意表示**: 送信失敗・LINE 未連携・画像除外（サイズ超過）は既存の `warn` / `danger` トークンで出し分ける（`warn` と `danger` は 2026-08 の配色刷新で分離済み）
- 375px 基準・日本語 UI・絵文字はデータ装飾に使わない
